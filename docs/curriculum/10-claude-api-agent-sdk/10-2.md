# 10-2. Messages API: 시스템 프롬프트, 멀티턴, 스트리밍, 구조화된 출력(JSON)

|---|---|
| 예상 시간 | 4시간 |

| 경험치 | 80 |

## 이 단원을 마치면

- 요청의 네 기둥 `model`, `max_tokens`, `system`, `messages`를 쓸 수 있고, **API는 상태가 없다**(stateless)는 것을 코드로 체감한다(대화를 이어 가려면 이전 메시지를 전부 다시 보낸다).
- `stop_reason`(`end_turn`, `max_tokens`, `tool_use`, `refusal` 등)을 읽고 각각에 대응할 수 있다.
- 스트리밍으로 답을 한 글자씩 받아 텔레그램·터미널에 흘려보낼 수 있다.
- **구조화된 출력**(JSON 스키마 강제)으로 모델의 답을 코드가 바로 쓸 수 있는 형태로 받는다. 11과정 AI 직원들이 서로 결과를 주고받는 형식이다.

## 왜 배우나 (나에게 어떤 쓸모)

10-1의 첫 호출은 "질문 하나, 답 하나"였다. 실제 자동화는 (1) 매번 같은 역할·규칙을 주고(시스템 프롬프트 = 7-2 스킬 본문) (2) 대화를 이어 가고(멀티턴) (3) 답을 **프로그램이 파싱**해야 한다(JSON). 특히 세 번째가 중요하다. "잘한 점 2개, 고칠 점 2개"를 말로 받으면 사람은 읽지만 코드는 못 쓴다. JSON으로 받으면 인사부·재무부 데이터에 바로 들어간다.

## 핵심 개념

(공식 working-with-messages·features overview·structured-outputs, 확인일 2026-10-23.)

### 1. 요청의 네 기둥

```python
message = client.messages.create(
    model=MODEL,                 # .env 에서 (6-4)
    max_tokens=1024,             # 출력 상한. 넘으면 stop_reason 이 max_tokens 로 잘린다
    system=TRADE_REVIEW_RULES,   # 역할·규칙. 7-2 의 SKILL.md 본문을 그대로 넣어도 된다
    messages=[{"role": "user", "content": today_record}],
)
```

- `system`: 대화 전체에 적용되는 지시. 6-3의 역할·맥락·형식이 여기 들어간다. 10-5에서 캐싱 대상 1순위.
- `messages`: `user`와 `assistant`가 번갈아. 첫 메시지는 `user`.
- 주의(공식): 현재 모델(4.7 이후)은 `temperature` 같은 샘플링 파라미터를 받지 않는다(400 에러). 행동은 프롬프트로 조절한다.

### 2. 상태가 없다: 멀티턴은 내가 쌓는다

공식 문서: "Messages API는 상태가 없다(stateless). 항상 **전체 대화 이력**을 보낸다." 6-1의 "모델은 기억이 없다"가 API에서는 문자 그대로다.

```python
history = []
def ask(text):
    history.append({"role": "user", "content": text})
    reply = client.messages.create(model=MODEL, max_tokens=1024, system=RULES, messages=history)
    answer = next(b.text for b in reply.content if b.type == "text")
    history.append({"role": "assistant", "content": answer})   # 답도 이력에 넣어야 다음에 기억한다
    return answer
```

이력이 길어지면 토큰(비용)이 매번 늘고(6-1), 결국 컨텍스트가 찬다. 대처: 오래된 턴을 요약해 교체하거나(Claude Code의 compact가 하는 일), 작업 단위로 이력을 비운다. 이전 `assistant` 메시지를 내가 **지어서** 넣어도 된다(공식: "synthetic assistant messages") — 예시 대화를 심는 기법.

### 3. `stop_reason` 읽기

| 값 | 뜻 | 대처 |
|---|---|---|
| `end_turn` | 다 말함 | 정상 |
| `max_tokens` | 길이 제한에 잘림 | `max_tokens` 늘리거나 "이어서"를 보내기. 잘린 JSON은 파싱 실패 |
| `tool_use` | 도구를 부르려 함 | 10-3의 왕복 |
| `stop_sequence` | 내가 지정한 중단 문자열 | 필요 시 |
| `refusal` | 정책상 거절 | `stop_details`에 사유. 재시도 대신 요청을 바꿈 |

코드에서 `if message.stop_reason == "max_tokens": ...`를 **항상** 둔다.

### 4. 스트리밍

긴 답을 다 기다리지 않고 조각(delta)으로 받는다. SDK는 `messages.stream`을 제공한다:

```python
with client.messages.stream(model=MODEL, max_tokens=1024, system=RULES, messages=history) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)   # 터미널에 타자 치듯
    final = stream.get_final_message()    # usage 등은 여기서
```

언제: 사람이 보는 화면(진행감), 긴 생성. 언제 아님: 배치·백그라운드(10-5). 텔레그램은 메시지 단위라 다 받은 뒤 보내는 게 낫다.

### 5. 구조화된 출력(Structured outputs)

**한 줄 정의**: 응답이 **내가 준 JSON 스키마에 맞게** 나오도록 보장하는 기능(공식 features overview: "JSON outputs"와 "strict tool use" 두 방식).

**왜 중요한가**: "JSON으로 답해 줘"라고만 하면 가끔 설명이 섞이거나 따옴표가 틀려 파싱이 깨진다. 스키마를 강제하면 `json.loads()`가 항상 성공한다. 공식 문서는 예전 기법인 prefill(assistant 메시지로 답 시작 유도)이 4.6 이후 모델에서 **지원되지 않으니** 구조화 출력을 쓰라고 안내한다.

복기 결과 스키마 예:
```python
REVIEW_SCHEMA = {
    "type": "object",
    "properties": {
        "good": {"type": "array", "items": {"type": "string"}, "maxItems": 2},
        "fix":  {"type": "array", "items": {"type": "string"}, "maxItems": 2},
        "rule_tomorrow": {"type": "string"},
        "violations": {"type": "array", "items": {"type": "string", "enum": ["stoploss", "chase", "average_down", "none"]}},
    },
    "required": ["good", "fix", "rule_tomorrow", "violations"],
    "additionalProperties": False,
}
```
요청에 붙이는 모양(2026-10-23 공식 페이지 기준): `client.messages.create(..., output_config={"format": {"type": "json_schema", "schema": REVIEW_SCHEMA}})`. 예전 이름 `output_format`은 폐기됐다(그대로 쓰면 400). 파이썬 SDK 는 Pydantic 모델을 `client.messages.parse()`에 주면 스키마 변환·검증까지 해 주고 결과를 `parsed_output`으로 돌려준다(쓰기 전에 공식 페이지에서 한 번 더 확인 — SDK 버전에 따라 다를 수 있다). 받은 뒤 `json.loads()` → `violations`를 세어 인사부 통계에 넣는 식으로 **코드가 소비**한다.

### 6. 이미지 입력

`content`를 블록 배열로 주면 이미지(base64/URL/파일)를 넣을 수 있다. 차트 캡처를 보내 "이 패턴에서 내 규칙 위반이 보이나?"를 묻는 식. 토큰이 많이 들어가니(이미지 1장 ≈ 1,000토큰 안팎, 공식 예시 usage 참고) 필요할 때만.

## 따라하기

### 1. 시스템 프롬프트로 복기 코치 (40분)

`skills/trade-review/SKILL.md`의 본문을 읽어 `system`으로 넣고, 오늘 기록을 `user`로 보낸다. 10-1 숙제 2를 제대로 완성. `usage`를 로그.

### 2. 멀티턴 (30분)

2절 `ask()`로 "복기해 줘" → "고칠 점 1번을 더 구체적으로" → "내일 규칙을 체크리스트로". 세 번째 요청의 `input_tokens`가 첫 번째보다 얼마나 큰지 본다(이력이 쌓이는 비용).

### 3. 잘림 체험 (20분)

`max_tokens=50`으로 보내 `stop_reason == "max_tokens"`를 확인하고, 그 상태의 답이 왜 쓸 수 없는지(문장·JSON이 중간에 끊김) 본다.

### 4. 스트리밍 (30분)

4절 코드로 터미널에 타자 치듯 출력. `get_final_message().usage`가 일반 호출과 같은 형식인지 확인.

### 5. 구조화된 출력 (60분)

공식 "Structured outputs" 페이지의 예제를 열어 5절 스키마를 적용한다. 응답을 `json.loads()`로 파싱해 `violations` 개수를 출력. 일부러 스키마에 없는 키를 요구하는 질문을 던져도 스키마대로 오는지 확인. 결과를 `docs/review/YYYY-MM-DD.json`으로 저장(7-3의 저장처).

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 답을 이력에 안 넣음 | 다음 턴에 맥락 상실 | assistant 메시지도 append |
| 이력 무한 증가 | 비용·컨텍스트 폭증 | 요약·초기화 |
| stop_reason 무시 | 잘린 답 사용 | 항상 검사 |
| "JSON으로"만 지시 | 파싱 실패 | 구조화된 출력 |
| temperature 지정 | 400 에러 | 제거, 프롬프트로 조절 |
| prefill 사용 | 400 에러(최신 모델) | 구조화된 출력·시스템 지시 |

## 확인 퀴즈

**1. "API는 상태가 없다"가 코드에서 뜻하는 것.**

<details><summary>정답과 해설</summary>
서버가 이전 대화를 기억하지 않으므로, 대화를 이어 가려면 user/assistant 메시지 전체를 매 요청에 다시 보낸다.
</details>

**2. 시스템 프롬프트에 7-2의 SKILL.md를 넣는 이유와 10-5와의 연결.**

<details><summary>정답과 해설</summary>
역할·규칙·절차를 매 호출에 일관되게 주기 위해. 긴 고정 텍스트라 10-5 캐싱의 1순위 대상이다.
</details>

**3. `stop_reason`이 `max_tokens`인 JSON 응답을 그대로 파싱하면?**

<details><summary>정답과 해설</summary>
중간에 끊겨 파싱이 실패한다. max_tokens를 늘리거나 출력을 줄이고, 코드에서 stop_reason을 먼저 검사한다.
</details>

**4. prefill 대신 쓰라고 공식 문서가 안내하는 것.**

<details><summary>정답과 해설</summary>
구조화된 출력(스키마 강제) 또는 시스템 프롬프트 지시. prefill은 4.6 이후 모델에서 400 에러.
</details>

**5. 스트리밍이 맞는 상황과 아닌 상황.**

<details><summary>정답과 해설</summary>
사람이 보는 화면·긴 생성에는 맞고, 배치·백그라운드·메시지 단위 알림(텔레그램)에는 불필요.
</details>
