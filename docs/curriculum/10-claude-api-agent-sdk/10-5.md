# 10-5. 프롬프트 캐싱, 배치, 비용 최적화, 로그와 모니터링

| 과정 | 10. Claude API와 Agent SDK |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 10-4 |
| 경험치 | 60 |

## 이 단원을 마치면

- 프롬프트 캐싱의 원리(접두 캐시, `cache_control`)와 비용 효과(읽기 0.1×, Opus/Sonnet 5.5는 0.05×)를 설명하고, 반복되는 긴 지시서에 적용할 수 있다.
- 배치 API(50% 할인, 비동기)가 맞는 작업과 안 맞는 작업을 구분한다.
- 호출마다 `usage`를 로그에 남기고, 일·주 단위 비용을 집계해 상한과 비교하는 **모니터링**을 만든다.
- 11과정 AI 직원의 월 비용을 설계 단계에서 추정하고 줄이는 여섯 가지 방법을 쓴다.

## 왜 배우나 (나에게 어떤 쓸모)

AI 직원은 매일 같은 긴 지시서(SKILL.md, 데이터 설명)를 읽는다. 캐싱 없이 돌리면 그 입력 비용을 **매번** 낸다. 밤새 돌리는 뉴스 요약은 급하지 않으니 배치로 반값에 한다. 그리고 4-4에서 배운 "알림 없는 자동화는 고장을 모른다"가 비용에도 적용된다: 로그 없는 API 호출은 **얼마가 나가는지 모른다.** 이 단원은 11과정의 재무 담당이다.

## 핵심 개념

(공식 prompt-caching·pricing·features overview, 확인일 2026-10-21.)

### 1. 프롬프트 캐싱

**한 줄 정의**: 요청의 앞부분(접두, prefix)을 서버에 잠시 저장해 두고, 다음 요청의 앞부분이 **바이트 단위로 같으면** 다시 처리하지 않고 재사용하는 기능.

**비유**: 매일 같은 두꺼운 매뉴얼을 들고 출근하는 직원에게, 매뉴얼을 사무실에 두고 다니게 하는 것. 바뀐 부분만 들고 온다.

**규칙**(공식):
- 캐시 순서: `tools` → `system` → `messages`. 앞이 바뀌면 뒤도 무효.
- 두 방식: **자동 캐싱**(요청 최상위에 `cache_control` 하나 → 마지막 캐시 가능 블록이 자동 기준점) / **명시적 기준점**(블록마다 `cache_control`, 최대 4개).
- 최소 길이: Opus 5.5·Sonnet 5.5·Haiku 5.5는 **512토큰**(모델별 다름). 미달이면 오류 없이 그냥 캐시 안 됨.
- 수명: 5분(쓸 때마다 무료 갱신) 또는 1시간 옵션.
- 가격: 쓰기 5분 1.25×, 1시간 2×. **읽기 0.1×**, Fable 5.1은 0.025×, Opus 5.5·Sonnet 5.5는 0.05×.
- 깨지는 조건: tools 정의 변경(전체 무효), 이미지 추가/제거·thinking·effort 변경(messages 무효), 내용이 1바이트라도 다름, 수명 초과.
- 응답 `usage`에 `cache_creation_input_tokens`(새로 씀), `cache_read_input_tokens`(읽음)가 온다. **이 숫자로 효과를 확인**한다.

```python
# 시스템 프롬프트(긴 지시서)를 캐시. 1시간 수명
system=[{"type": "text", "text": LONG_INSTRUCTIONS, "cache_control": {"type": "ephemeral", "ttl": "1h"}}]
```

**효과 계산**: 지시서 5,000토큰, Sonnet 5.5, 하루 100회. 캐시 없음: 5,000×100×$2/M = $1.0/일. 캐시: 쓰기 1회 5,000×$2.5/M ≈ $0.0125 + 읽기 99회 5,000×99×$0.1/M ≈ $0.05 → **약 $0.06/일**. 16배 차이.

### 2. 배치 API

**한 줄 정의**: 요청을 여러 개 묶어 보내면 비동기로 처리하고 **50% 할인**(공식 features overview). 결과는 나중에 받는다.

맞는 일: 밤새 뉴스 50건 분류, 월말 리포트, 과거 복기 100건 일괄 분석. 안 맞는 일: 사용자가 기다리는 대화, 실시간 알림. 11과정에서 "긴급하지 않은 부서"는 배치로.

### 3. 비용 줄이는 여섯 가지

1. **모델 맞추기**(6-4): 분류·추출은 Haiku, 일상은 Sonnet, 설계만 Opus.
2. **캐싱**: 반복 입력(지시서, 문서, 도구 정의)은 앞쪽에 두고 캐시.
3. **배치**: 급하지 않으면 50%.
4. **effort 낮추기**: 생각 토큰은 출력 과금. 단순 작업은 `effort` 낮게(10-2).
5. **입력 다이어트**: 필요한 부분만. 긴 로그는 미리 걸러서(9-3 훅의 원리).
6. **출력 제한**: `max_tokens`와 형식(JSON, 150자)으로 길이 통제. 구조화 출력(10-2)은 군더더기를 줄인다.

### 4. 로그와 모니터링

**한 줄 정의**: 모든 호출에 대해 "언제, 어떤 모델, 입력/출력/캐시 토큰, 추정 비용, 어떤 작업"을 한 줄씩 남기고, 매일 합계를 알림으로 받는다.

```python
# usage_log.py  (10-1 숙제 1의 확장)
import csv, datetime, pathlib
PRICE = {"claude-sonnet-5-5": (2, 10), "claude-haiku-5-5": (0.10, 0.50), "claude-opus-5-5": (4, 20)}  # $/M, 공식 가격표 확인

def log_usage(message, task):
    u = message.usage
    p_in, p_out = PRICE.get(message.model, (0, 0))
    cached = getattr(u, "cache_read_input_tokens", 0) or 0
    cost = (u.input_tokens * p_in + cached * p_in * 0.1 + u.output_tokens * p_out) / 1_000_000  # 캐시 읽기는 0.1x로 근사
    row = [datetime.datetime.now().isoformat(timespec="seconds"), task, message.model,
           u.input_tokens, cached, u.output_tokens, round(cost, 5)]
    path = pathlib.Path("logs/api-usage.csv")
    path.parent.mkdir(exist_ok=True)
    with open(path, "a", newline="", encoding="utf-8") as f:
        csv.writer(f).writerow(row)
    return cost
```

- 일일 합계 스크립트를 4-4 스케줄러에 등록해 "오늘 API 비용 $0.42, 이번 달 누적 $6.1 / 상한 $20"을 텔레그램으로.
- 콘솔 Usage 페이지와 월 1회 대조(로그는 추정, 콘솔이 청구 기준).
- 이상 감지: 하루 비용이 평균의 3배를 넘으면 알림 + 작업 중단 플래그(11-3).

### 5. 토큰 세기

호출 전에 토큰 수를 알고 싶으면 토큰 카운팅 엔드포인트(공식 features: token counting)를 쓴다. 긴 문서를 넣기 전에 "이게 몇 토큰이지?"를 확인해 캐시 최소 길이(512)를 넘는지, 비용이 얼마일지 미리 안다.

### 6. 설계 단계의 월 비용 추정 (6-4 따라하기 3 재방문)

| 직원 | 모델 | 1회 입력(캐시) | 출력 | 횟수/월 | 월 비용(근사) |
|---|---|---|---|---|---|
| 뉴스 분류 | Haiku, 배치 | 3,000(2,500 캐시) | 200 | 1,500 | ≈ $0.3 |
| 보유 종목 요약 | Sonnet | 6,000(5,000 캐시) | 800 | 30 | ≈ $0.3 |
| 주간 리포트 | Opus | 20,000(15,000 캐시) | 3,000 | 4 | ≈ $0.4 |

합계 1달러 안팎. **설계만 잘하면 AI 회사는 싸다.** 비싸지는 건 설계 없이 Opus를 매번 긴 컨텍스트로 부를 때다.

## 따라하기

### 1. 캐싱 효과 측정 (40분)

10-2의 복기 코치 시스템 프롬프트를 1,000토큰 이상으로 늘리고(규칙·예시 추가), `cache_control`을 붙여 같은 요청을 3번 보낸다. 각 응답의 `cache_creation_input_tokens`/`cache_read_input_tokens`를 출력해 두 번째부터 읽기가 되는지 확인. 5분 뒤 다시 보내 만료를 본다.

### 2. 깨뜨리기 (20분)

시스템 프롬프트 한 글자를 바꿔 보내 캐시가 깨지는지(`cache_creation`이 다시 생기는지) 확인. 도구 정의를 바꿔도 확인.

### 3. 로그 붙이기 (40분)

4절 `log_usage`를 10-1~10-4의 모든 스크립트에 붙인다. `logs/api-usage.csv`를 3-6의 pandas로 읽어 일별 합계를 출력.

### 4. 일일 비용 알림 (30분)

`daily_cost.py`: 오늘 합계와 월 누적을 계산해 텔레그램으로(4-4). 스케줄러에 23:30 등록. 콘솔 Usage와 비교해 오차를 적는다.

### 5. 배치 체험 (30분)

공식 배치 API 문서를 보고, 지난 복기 10건을 한 배치로 보내 "반복 위반 패턴"을 각각 뽑는다. 완료까지 걸린 시간과 비용(50%)을 로그에.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 캐시 대상이 512토큰 미만 | cache_read가 0 | 짧으면 캐시 안 됨. 합쳐서 길게 |
| 바뀌는 내용을 앞에 둠 | 매번 캐시 생성 | 고정(지시서) 앞, 변동(오늘 데이터) 뒤 |
| 도구 정의를 자주 바꿈 | 전체 캐시 무효 | 도구는 고정 |
| 로그 없음 | 비용 파악 불가 | 모든 호출에 log_usage |
| 콘솔 대조 안 함 | 추정과 청구 불일치 | 월 1회 대조 |
| 급한 작업을 배치로 | 결과가 늦게 옴 | 비동기 가능한 일만 |

## 확인 퀴즈

**1. 캐시 순서 tools → system → messages가 뜻하는 설계 원칙.**

<details><summary>정답과 해설</summary>
앞이 바뀌면 뒤가 무효이므로, 고정된 것(도구, 지시서)을 앞에, 매번 바뀌는 것(오늘 데이터, 질문)을 뒤에 둔다.
</details>

**2. Sonnet 5.5에서 캐시 읽기 배율은? 5,000토큰 지시서를 100회 읽으면 얼마?**

<details><summary>정답과 해설</summary>
0.05×(공식 가격표의 Opus/Sonnet 5.5 예외). 5,000×100×$2/M×0.05 = $0.05. (일반 모델은 0.1×.)
</details>

**3. 배치 API가 안 맞는 작업의 예.**

<details><summary>정답과 해설</summary>
사용자가 기다리는 대화, 실시간 알림처럼 즉시 응답이 필요한 작업. 배치는 비동기라 결과가 나중에 온다.
</details>

**4. 로그에 남길 최소 항목.**

<details><summary>정답과 해설</summary>
시각, 작업 이름, 모델, 입력/캐시/출력 토큰, 추정 비용. 콘솔과 월 1회 대조.
</details>

**5. AI 직원 세 명을 월 1달러 안팎으로 돌리는 설계의 핵심 세 가지.**

<details><summary>정답과 해설</summary>
역할별 모델 배치(Haiku/Sonnet/Opus), 지시서 캐싱, 급하지 않은 작업은 배치.
</details>
