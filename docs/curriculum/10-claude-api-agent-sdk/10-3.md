# 10-3. 도구 사용(tool use): 함수 호출 흐름, JSON 스키마, 실제 함수 연결

| 과정 | 10. Claude API와 Agent SDK |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 10-2 |
| 경험치 | 80 |

## 이 단원을 마치면

- 도구 사용(tool use, function calling)의 **왕복**(도구 정의 → 모델이 `tool_use` 블록 → 내 코드가 실행 → `tool_result` 반환 → 최종 답)을 그림으로 그리고 코드로 돌릴 수 있다.
- 도구 정의의 세 요소(`name`, `description`, `input_schema`)를 JSON Schema로 쓸 수 있고, `description`이 "언제 쓸지"를 정한다는 것을 안다(7-2 스킬과 같은 원리).
- 클라이언트 도구(내가 실행)와 서버 도구(Anthropic이 실행: 웹 검색 등)의 차이를 안다.
- 내 가계부·루틴 데이터를 읽는 도구를 만들어 "이번 달 식비 얼마야?"에 **코드로 계산한 숫자**로 답하게 할 수 있다(7-3의 "계산은 코드가").

## 왜 배우나 (나에게 어떤 쓸모)

10-2까지는 모델이 **말만** 했다. 도구 사용부터 모델이 **행동**한다: 내 함수를 골라 부르고 결과를 받아 답한다. Claude Code가 파일을 읽고 명령을 실행하는 것도 이 메커니즘이다(8-1의 "맥락 수집 → 행동"). 11과정 AI 직원은 "도구 몇 개 + 지시서"다. 이 단원에서 처음으로 **AI가 내 데이터를 직접 만지는** 코드를 쓴다. 그래서 "어떤 도구를 줄 것인가"가 곧 "어디까지 허용할 것인가"다(8-4).

## 핵심 개념

(공식 tool-use overview·structured-outputs, 확인일 2026-10-23.)

### 1. 왕복 한 바퀴

```
① 요청: messages + tools=[{name, description, input_schema}]
② 응답: stop_reason "tool_use", content에 {type:"tool_use", id, name, input}
③ 내 코드: input으로 실제 함수 실행 → 결과 문자열
④ 요청: 이전 메시지 + assistant(②의 content) + user([{type:"tool_result", tool_use_id, content}])
⑤ 응답: 최종 텍스트 (또는 또 다른 tool_use → ③으로)
```

**비유**: 사장이 "이번 달 식비 얼마야?"라고 물으면 비서(모델)가 "회계 장부 조회 도구 써야겠다"며 **조회 요청서**(`tool_use`)를 쓴다. 실제 조회는 **내 코드**가 하고 결과를 돌려준다. 비서는 그걸 읽고 사장에게 답한다. 비서는 장부를 직접 못 만진다. 이것이 안전의 핵심이다.

### 2. 도구 정의

공식 예제(`get_weather`)를 우리 것으로:

```python
tools = [
    {
        "name": "get_monthly_expense",
        "description": "이번 달(또는 지정한 달)의 카테고리별 지출 합계를 가계부 백업 JSON에서 계산해 돌려준다. 지출·식비·얼마 같은 질문에 사용.",
        "input_schema": {
            "type": "object",
            "properties": {
                "month": {"type": "string", "description": "YYYY-MM 형식. 생략하면 이번 달"},
                "category": {"type": "string", "description": "food, transport 등 카테고리 코드. 생략하면 전체"},
            },
            "required": [],
        },
    }
]
```

- `description`: 7-2 스킬·9-1 서브에이전트의 description과 **같은 역할**. 모델은 이것을 보고 도구를 고른다. "무엇 + 언제".
- `input_schema`: JSON Schema. `properties`에 인자, `required`에 필수. 모델이 이 모양대로 `input`을 만든다. `strict: true`를 붙이면 스키마와 **정확히** 일치하도록 보장(공식 "strict tool use").
- 인자가 부족하면 Opus는 되묻는 경향이 있고, Sonnet은 추측해 채울 수 있다(공식 문서). 중요한 인자는 `required`에.

### 3. 왕복 코드 (공식 Python 예제 구조 그대로)

```python
import json, anthropic
client = anthropic.Anthropic()
messages = [{"role": "user", "content": "이번 달 식비 얼마 썼어?"}]

response = client.messages.create(
    model="claude-sonnet-5-5", max_tokens=1024, tools=tools,
    tool_choice={"type": "auto", "disable_parallel_tool_use": True},  # 한 턴에 도구 하나만
    messages=messages,
)
tool_use = next(b for b in response.content if b.type == "tool_use")
print("모델이 부른 도구:", tool_use.name, json.dumps(tool_use.input, ensure_ascii=False))

result = get_monthly_expense(**tool_use.input)   # ③ 내 함수. 숫자는 여기서 계산된다
messages += [
    {"role": "assistant", "content": response.content},
    {"role": "user", "content": [{"type": "tool_result", "tool_use_id": tool_use.id, "content": json.dumps(result, ensure_ascii=False)}]},
]
followup = client.messages.create(model="claude-sonnet-5-5", max_tokens=1024, tools=tools, messages=messages)
print(next(b for b in followup.content if b.type == "text").text)
```

`get_monthly_expense`는 사장실 백업 JSON(2.5단계)을 읽어 3-3·3-6에서 배운 방식으로 합계를 내는 **보통 파이썬 함수**다. 모델은 숫자를 계산하지 않고 **내 함수의 결과를 읽는다**(6-1·7-3).

### 4. `tool_choice`와 병렬

- `{"type":"auto"}`(기본): 모델이 도구를 쓸지 판단. 시스템 프롬프트로 "먼저 도구로 확인하라"고 밀 수 있다.
- `{"type":"any"}`(반드시 도구 중 하나)·`{"type":"tool","name":"..."}`(특정 도구 강제)는 **지금 모델(Opus 5.5·Sonnet 5.5·Fable 5.1)에서는 400 에러**다(2026-10-23 공식 문서). 대신 `auto` + 시스템 프롬프트에 "먼저 get_monthly_expense 도구로 확인하라"처럼 이름을 적고, 인자 모양은 `strict: true`로 보장한다. JSON 만 받으려고 도구를 강제하던 경우는 10-2의 구조화된 출력으로.
- 모델은 한 번에 여러 `tool_use`를 낼 수 있다(병렬). 초보 단계에서는 `disable_parallel_tool_use: True`로 하나씩. 여러 개가 오면 **각각** `tool_result`를 돌려줘야 한다.
- 반복: ⑤에서 또 `tool_use`가 오면 ③~④를 반복한다. 이것이 **에이전트 루프**다. `while` 문 + "최대 N회" 안전장치(4-4의 멱등성처럼).

### 5. 클라이언트 도구 vs 서버 도구

| | 클라이언트 도구 | 서버 도구 |
|---|---|---|
| 실행 | 내 코드 | Anthropic 인프라 |
| 예 | 내 함수, bash·text_editor(Anthropic 정의 스키마) | `web_search`, `web_fetch`, `code_execution` |
| 비용 | 토큰만 | 토큰 + 도구별 사용료(검색 건당 등) |
| 쓰임 | 내 데이터·시스템 | 최신 정보, 샌드박스 계산 |

웹 검색 서버 도구는 `tools=[{"type":"web_search_20260209","name":"web_search"}]` 한 줄이면 6-1의 컷오프 문제를 코드에서 푼다. 공식 문서의 도구 레퍼런스에서 `type` 문자열을 확인.

### 6. 안전: 도구가 곧 권한

- 읽기 도구부터. 쓰기(주문, 파일 삭제, 메시지 전송) 도구는 **확인 단계**나 한도를 함수 안에 둔다(4-3 안전장치).
- 도구 함수는 **입력을 검증**한다. 모델이 만든 `input`은 사용자 입력과 같다(12-2).
- 도구 호출 로그(어떤 도구, 어떤 입력, 결과 길이)를 남긴다(10-5).
- `tool_result`에 에러를 돌려줄 수 있다(`is_error: true`). 예외를 숨기지 말고 돌려주면 모델이 대응한다.

## 따라하기

### 1. 가계부 조회 도구 (60분)

`tools_ledger.py`: 사장실 백업 JSON을 읽어 `get_monthly_expense(month=None, category=None)`를 만든다(3-3 JSON, 3-4 datetime). 먼저 **도구 없이** 함수만 테스트. 그다음 3절 왕복 코드에 붙여 "이번 달 식비?"·"지난달 교통비?"를 묻는다. 모델이 `input`을 어떻게 채우는지 출력해서 본다.

### 2. 루틴 조회 도구 추가 (40분)

`get_routine_streak()`(routine-checks를 읽어 연속 달성일 계산, 2단계 `routineStreak()`을 파이썬으로)를 두 번째 도구로. "요즘 루틴 잘 지키고 있어?"에 모델이 어느 도구를 고르는지 관찰. description을 바꿔 선택이 달라지는지 실험.

### 3. 에이전트 루프 (50분)

`tool_use`가 더 안 올 때까지 반복하는 `while` 루프로 바꾸고 **최대 5회** 제한을 둔다. "이번 달 지출 중 가장 큰 카테고리와 그 카테고리의 지난달 대비 증감을 알려 줘"처럼 도구를 두 번 불러야 하는 질문을 던진다.

### 4. 서버 도구 한 번 (20분)

`web_search` 서버 도구로 "오늘 코스피 마감 지수"를 묻는다. 응답에 인용(citation)이 오는지 보고, 6-1 따라하기 3(검색 없이 물었을 때)과 비교. 사용료를 콘솔에서 확인.

### 5. 쓰기 도구의 안전장치 (30분)

`send_telegram(text)`(4-4)를 도구로 추가하되, 함수 안에 "하루 10회 제한"과 "길이 500자 제한"을 넣는다. "루틴 요약을 텔레그램으로 보내 줘"를 시켜 본다. 제한을 넘기면 `is_error`로 돌려주고 모델이 어떻게 반응하는지.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| tool_result 없이 다음 요청 | 400 에러 | 모든 tool_use에 대응하는 tool_result |
| assistant 메시지 누락 | 모델이 맥락을 잃음 | ②의 content를 assistant로 그대로 추가 |
| description이 모호 | 엉뚱한 도구 선택 | "무엇 + 언제", 예시 질문 포함 |
| 무한 루프 | 과금 폭주 | 최대 반복 횟수, 상한 |
| 숫자를 모델이 계산 | 틀림 | 계산은 함수에서, 모델은 결과를 읽기만 |
| 쓰기 도구 무방비 | 의도치 않은 전송·주문 | 함수 안 한도·확인, 읽기부터 |

## 확인 퀴즈

**1. 모델은 도구를 직접 실행하나?**

<details><summary>정답과 해설</summary>
클라이언트 도구는 실행하지 않는다. 모델은 `tool_use` 블록(이름·입력)을 내고, 실행은 내 코드가 한다. 서버 도구만 Anthropic 쪽에서 실행된다.
</details>

**2. 도구 정의에서 7-2의 스킬 description과 같은 역할을 하는 것은?**

<details><summary>정답과 해설</summary>
`description`. 모델이 어떤 도구를 쓸지 판단하는 기준이라 "무엇을 + 언제"를 적는다.
</details>

**3. 네 번째 단계(④)에서 messages에 반드시 추가해야 하는 두 메시지.**

<details><summary>정답과 해설</summary>
assistant 메시지(②의 content 전체)와 user 메시지(`tool_result` 블록, `tool_use_id` 일치). 이 순서가 맞아야 한다.
</details>

**4. "이번 달 식비"를 모델이 아니라 함수가 계산하게 하는 이유.**

<details><summary>정답과 해설</summary>
모델의 암산은 틀릴 수 있다(6-1). 함수는 정확하고 검증 가능하다. 모델은 결과를 읽고 말로 풀기만 한다.
</details>

**5. 에이전트 루프에 꼭 넣을 안전장치 두 가지.**

<details><summary>정답과 해설</summary>
최대 반복 횟수와 지출 상한(콘솔). 추가로 쓰기 도구에는 함수 내부 한도·확인 단계.
</details>
