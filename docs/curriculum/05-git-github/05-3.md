## 이 단원을 마치면

- Git(내 컴퓨터의 도구)과 GitHub(인터넷의 보관소·협업 서비스)의 차이를 말할 수 있다.
- `clone`, `push`, `pull`, `fetch`가 각각 어느 방향으로 무엇을 옮기는지 그림으로 그릴 수 있다.
- Pull Request(PR)를 만들어 `claude/…` 브랜치를 `main`에 합칠 수 있고, 이슈로 할 일을 적어 둘 수 있다.
- GitHub Pages로 이 앱을 **인터넷 주소**로 배포해 휴대폰에서도 열 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

지금까지 만든 앱은 내 컴퓨터의 `index.html`을 더블클릭해야 열린다. GitHub Pages에 올리면 **휴대폰에서 주소만 치면** 열린다. 헬스장에서 루틴을 체크하고, 장 마감 후 매매 복기를 적는 건 휴대폰이 편하다. 그리고 GitHub는 13과정 포트폴리오의 기본이다. "내 코드가 여기 있다"를 보여 주는 가장 표준적인 방법이다. Claude Code 웹 세션이 이 저장소에 커밋을 올린 것도 전부 GitHub를 통해서였다.

## 핵심 개념

### 1. Git과 GitHub는 다르다

**한 줄 정의**: Git은 내 컴퓨터에서 이력을 관리하는 프로그램. GitHub는 그 이력을 인터넷에 올려 두고(원격 저장소), 다른 사람·다른 컴퓨터·AI와 함께 쓰게 해 주는 **서비스**다.

**비유**: Git은 내 장부, GitHub는 은행 금고. 장부를 금고에 복사해 두면(push) 컴퓨터가 망가져도 남고, 다른 컴퓨터에서 꺼내(clone) 이어서 쓸 수 있다.

**실제 예시**: 이 저장소는 `github.com/hyeok7809-rgb/todo-app`에 있다. 내 컴퓨터의 복사본은 `origin`이라는 이름으로 그 주소를 기억한다.

```bash
git remote -v          # origin  https://github.com/hyeok7809-rgb/todo-app.git (fetch/push)
```

### 2. 네 가지 이동

```
   GitHub (origin)
      ▲      │
   push      │ fetch / pull
      │      ▼
   내 컴퓨터 (로컬)
```

| 명령 | 방향 | 뜻 |
|---|---|---|
| `git clone 주소` | GitHub → 새 폴더 | 처음 한 번, 저장소 통째로 받기 |
| `git push` | 로컬 → GitHub | 내 커밋 올리기 |
| `git fetch` | GitHub → 로컬(보기만) | 새 커밋이 있는지 가져오되 합치지는 않음 |
| `git pull` | GitHub → 로컬(합침) | fetch + merge. 남(또는 Claude Code 웹)이 올린 것을 내 브랜치에 합침 |

**실제 예시** — 다른 컴퓨터에서 이 프로젝트를 이어 하려면:

```bash
git clone https://github.com/hyeok7809-rgb/todo-app.git
cd todo-app
git switch claude/confident-goodall-gdy93b     # 작업 중인 브랜치로
```

처음 push할 때는 `git push -u origin 브랜치이름`으로 "이 로컬 브랜치는 origin의 저 브랜치와 짝"이라고 한 번 알려 준다. 그다음부터는 `git push`만.

**왜 중요한가**: Claude Code 웹 세션과 내 컴퓨터가 **같은 브랜치를 번갈아** 고치는 일이 생긴다. 작업 시작 전 `git pull`, 끝나면 `git push`. 이 두 줄을 습관으로.

### 3. 로그인: HTTPS와 토큰

GitHub에 push하려면 "내가 나"라는 인증이 필요하다. 비밀번호로는 안 되고, **Git Credential Manager**(Windows Git 설치 시 포함, Mac은 Homebrew로)가 브라우저 로그인을 띄워 처리해 주는 것이 가장 쉽다. 처음 push 때 브라우저가 열리면 로그인·승인하면 끝. 그래도 안 되면 GitHub → Settings → Developer settings → Personal access tokens에서 토큰을 만들어 비밀번호 자리에 넣는다. **토큰은 비밀이다**(4-2). 2단계 인증(2FA)을 켜 두자.

### 4. Pull Request: "이 브랜치를 합쳐 주세요"

**한 줄 정의**: PR은 GitHub 위에서 "브랜치 A를 B에 합치고 싶다"고 제안하고, 변경 내용(diff)을 보며 검토·대화한 뒤 버튼으로 합치는 기능이다.

**비유**: 결재 서류. 혼자 쓰는 저장소라도 "내가 결재자"가 되어 diff를 한 번 더 읽는 절차가 된다. 5-2의 `merge`를 GitHub 화면에서 하는 것이고, 기록(왜 합쳤는지, 무엇이 바뀌었는지)이 남는다.

**만드는 순서**:
1. 브랜치가 push돼 있어야 한다(`git push -u origin 브랜치`).
2. GitHub 저장소 페이지 → "Pull requests" → "New pull request" → base: `main`, compare: 내 브랜치.
3. 제목·설명을 쓰고 "Create pull request". "Files changed" 탭이 diff다. **여기서 읽는다.**
4. "Merge pull request" → "Confirm merge". 끝나면 "Delete branch"로 정리해도 된다.
5. 내 컴퓨터에서 `git switch main` → `git pull` 로 합쳐진 main을 받는다.

Claude Code에게 "PR 만들어 줘"라고 하면 1~3을 해 준다. 4(합치기)는 **내가** 누른다. 그게 검토다.

### 5. 이슈(Issue): 할 일과 버그 적어 두기

저장소의 "Issues" 탭은 할 일 목록이다. "자산관리부 열기", "연속 달성일이 자정에 이상함" 같은 걸 하나씩 적는다. 번호가 붙고(#12), 커밋 메시지나 PR에 `#12`를 적으면 자동으로 연결된다. Claude Code에게 "이슈 #12 처리해 줘"라고 시킬 수도 있다. 혼자 쓰는 프로젝트에서도 **머릿속 할 일을 밖으로 꺼내는** 용도로 좋다.

### 6. README: 저장소의 첫 페이지

저장소를 열면 `README.md`가 바로 보인다. 지금 이 저장소의 README는 "무엇인지, 어떻게 실행하는지, 문서 링크"가 있다. 13과정 포트폴리오에서는 여기에 **스크린샷과 한 줄 소개**가 들어간다. 남이 10초 안에 "뭐 하는 프로젝트인지" 알 수 있으면 합격.

### 7. GitHub Pages: 정적 사이트 무료 배포

**한 줄 정의**: 저장소의 HTML/CSS/JS 파일을 그대로 `https://<아이디>.github.io/<저장소>/` 주소로 서비스해 주는 무료 기능. 서버 코드 없이 파일만 보여 주는 "정적 사이트"에 딱 맞고, 이 앱이 정확히 그렇다.

**설정** (GitHub 화면 기준. 메뉴 이름은 바뀔 수 있으니 공식 문서와 대조한다):
1. 저장소 → Settings → 왼쪽 "Pages".
2. "Build and deployment" → Source: **Deploy from a branch**.
3. Branch: `main`, 폴더: `/ (root)` → Save.
4. 몇 분 뒤 같은 화면 위에 주소가 뜬다. `https://hyeok7809-rgb.github.io/todo-app/`.

주의할 점:
- **공개 저장소**여야 무료 플랜에서 Pages가 된다. 이 앱에는 비밀값이 없고(모든 데이터는 각자 브라우저에 저장) 코드는 공개해도 된다. 단, 4과정의 `.env`·백업 JSON은 절대 저장소에 없어야 한다(4-2).
- 휴대폰 브라우저의 localStorage는 **그 휴대폰에만** 저장된다. 컴퓨터와 휴대폰 기록은 따로다. 합치려면 사장실 백업(2.5단계)으로 옮기거나, 11-4에서 설계하고 12-3에서 만드는 서버 저장이 필요하다.
- `main`에 push할 때마다 자동으로 다시 배포된다. 그래서 **main은 항상 동작하는 상태**여야 한다(5-2의 브랜치 습관).

## 따라하기

### 1. 원격 확인과 pull/push (30분)

```bash
git remote -v
git fetch
git status            # "Your branch is up to date" 또는 behind/ahead
git pull              # 웹 세션이 올린 것이 있으면 받는다
```

`docs/history.md`(5-1 숙제)를 조금 고쳐 커밋 → `git push` → GitHub 페이지에서 새로고침해 커밋이 보이는지.

### 2. 다른 폴더에 clone (20분)

`~/tmp-clone` 같은 다른 위치에 `git clone`으로 한 번 더 받아 본다. "저장소는 어디서든 똑같이 복원된다"를 확인하고, 다 봤으면 그 폴더를 지운다. 이게 "컴퓨터를 바꿔도 이어서 할 수 있다"의 증명이다.

### 3. Pull Request로 Claude 브랜치 합치기 (50분)

1. GitHub에서 New pull request: base `main`, compare `claude/confident-goodall-gdy93b`.
2. "Files changed"에서 **파일 목록을 훑고** 모르는 파일이 있으면 Claude Code에게 "이 파일 뭐야?"라고 묻는다.
3. 제목은 "Files changed"에 보이는 내용에 맞춰 쓴다(예: "4단계: 기획부 개방"). 1~2.5단계는 이미 PR #1로 합쳐져 있으니 그 뒤에 쌓인 커밋만 들어간다. Merge.
4. 내 컴퓨터: `git switch main` → `git pull` → `git log --oneline -5`에 합쳐진 커밋이 보이면 성공.
5. 앞으로 Claude Code 웹 세션은 새 브랜치에서 일하게 된다. 작업 요청 때 "main에서 새 브랜치로"라고 말하면 된다.

### 4. GitHub Pages 배포 (40분)

핵심 개념 7절대로 설정 → 주소가 뜨면 휴대폰에서 열어 본다 → 루틴 하나 체크 → 새로고침해도 남는지. 홈 화면에 추가(iPhone: 공유 → 홈 화면에 추가 / Android: 메뉴 → 홈 화면에 추가)하면 앱처럼 쓸 수 있다. README에 배포 주소를 한 줄 추가해 커밋·push.

### 5. 이슈 세 개 만들기 (20분)

Issues 탭에 지금 떠오르는 할 일·버그를 세 개 적는다. 예: "자산관리부 열기", "루틴 이름 바꾸기 UI", "모바일에서 상단 바 글자 크기". 다음 Claude Code 세션에서 "이슈 #1부터 해 줘"라고 시켜 본다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| push 거부 "rejected … fetch first" | 원격에 내가 모르는 커밋이 있음 | `git pull` 로 먼저 합치고(충돌 나면 5-2) 다시 push |
| `git pull` 이 "divergent branches" 물음 | 합치는 방식 미설정 | `git config --global pull.rebase false` (merge 방식) 한 번 설정 |
| 비밀번호 입력했는데 실패 | GitHub는 비밀번호 push 불가 | Credential Manager 브라우저 로그인 또는 토큰 |
| Pages 주소가 404 | 설정 직후, 또는 브랜치/폴더 잘못 | 몇 분 기다림, Source 가 main / root 인지 확인, `index.html` 이 루트에 있는지 |
| Pages 에서 CSS/JS 가 안 뜸 | 경로가 `/style.css` 처럼 절대경로 | 상대경로(`style.css`)로. 이 앱은 이미 상대경로 |
| 휴대폰과 PC 기록이 다름 | 정상(브라우저별 저장) | 사장실 백업으로 옮기기, 나중에 서버 저장 |
| `.env` 가 올라감 | 공개 저장소에 비밀 노출 | 즉시 키 폐기·재발급(4-2), 파일 삭제 |

## 확인 퀴즈

**1. Git과 GitHub의 차이를 한 문장으로.**

<details><summary>정답과 해설</summary>
Git은 내 컴퓨터에서 이력을 관리하는 프로그램이고, GitHub는 그 이력을 인터넷에 보관·공유·협업하게 해 주는 서비스다. GitHub 없이도 Git은 쓸 수 있다.
</details>

**2. `fetch`와 `pull`의 차이는?**

<details><summary>정답과 해설</summary>
`fetch`는 원격의 새 커밋을 가져오기만 하고 내 브랜치에 합치지 않는다(보기용). `pull`은 fetch 후 merge까지 한다. 뭐가 올라왔는지 먼저 보고 싶으면 fetch → `git log origin/main`.
</details>

**3. PR을 "혼자 쓰는 저장소"에서도 쓰는 이유는?**

<details><summary>정답과 해설</summary>
합치기 전에 diff를 한 번 더 읽는 검토 절차가 되고, 왜 무엇을 합쳤는지 기록이 남는다. AI가 만든 브랜치를 사람이 승인하는 지점이기도 하다.
</details>

**4. GitHub Pages에 올린 앱의 루틴 기록이 휴대폰과 PC에서 다르게 보인다. 버그인가?**

<details><summary>정답과 해설</summary>
아니다. localStorage는 브라우저(기기)마다 따로다. Pages는 파일만 서비스하고 데이터는 저장하지 않는다. 기기 간 공유는 백업 파일을 옮기거나 서버 저장(11-4 설계, 12-3 구현)이 필요하다.
</details>

**5. main에 push하면 바로 배포된다. 이것이 5-2의 브랜치 습관과 어떻게 연결되나?**

<details><summary>정답과 해설</summary>
main이 곧 "지금 서비스되는 것"이므로 항상 동작해야 한다. 실험은 브랜치에서 하고, 확인한 뒤 PR로 합친다. 망가진 코드를 main에 올리면 휴대폰에서 바로 깨진 앱을 보게 된다.
</details>

## 숙제

1. **배포 주소 공유** — Pages 주소를 README에 적고, 휴대폰 홈 화면에 추가해 **일주일 동안 휴대폰으로만** 루틴을 체크해 보라. 불편한 점을 이슈로 적는다.
2. **PR 한 번 더** — 5-2 숙제 1의 `routine-5th` 브랜치를 PR로 합쳐 보라(이미 merge 했다면 새 브랜치로 작은 변경을 하나 만들어서).
3. **6-1 예습** — 지금까지 Claude Code와 나눈 대화 중 "이상하게 답했다"고 느낀 순간을 두 개 적어 두라. 6과정에서 그 이유(토큰, 컨텍스트, 환각)를 배운다.
