## 이 단원을 마치면

- 브랜치(branch)가 "커밋을 가리키는 이름표"라는 것과, 왜 브랜치를 만들면 실험이 안전해지는지 설명할 수 있다.
- `git switch -c`로 브랜치를 만들고, 작업하고, `git merge`로 합칠 수 있다.
- 병합 충돌(conflict)이 **무엇이 아닌지**(고장이 아님) 알고, 충돌 표시(`<<<<<<<`)를 읽어 직접 고칠 수 있다.
- Claude Code가 이 저장소에서 `claude/…` 브랜치에 작업하는 이유를 이해하고, 그 브랜치를 `main`에 합칠 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

지금 이 저장소의 모든 작업은 `main`이 아니라 `claude/confident-goodall-gdy93b`라는 브랜치에 있다. Claude Code가 "일단 옆 줄기에서 만들고, 확인한 뒤 본 줄기에 합친다"는 방식으로 일하기 때문이다. 이 단원을 마치면 그 브랜치를 내 손으로 `main`에 합칠 수 있다. 그리고 앞으로 "자산관리부 실험", "그림 교체 실험"처럼 **잘 될지 모르는 작업**을 브랜치에서 하고, 실패하면 브랜치째 버리는 습관을 들인다. 되돌리기(5-1)가 사후 안전벨트라면 브랜치는 사전 안전벨트다.

## 핵심 개념

### 1. 브랜치는 이름표다

**한 줄 정의**: 브랜치는 특정 커밋을 가리키는 **움직이는 이름표**다. 그 브랜치에서 커밋하면 이름표가 새 커밋으로 따라 옮겨 간다.

**비유**: 매매 전략 테스트. 본 계좌(main)는 검증된 전략만. 새 전략은 **모의 계좌(브랜치)** 에서 돌려 보고, 성과가 좋으면 본 계좌에 적용(merge), 아니면 모의 계좌를 닫는다(브랜치 삭제). 본 계좌는 그동안 아무 영향이 없다.

**실제 예시**:

```
main:    A ── B ── C
                    \
feature:             D ── E      ← "자산관리부 실험" 브랜치
```

`C`까지는 공유, `D`·`E`는 feature에만 있다. main은 여전히 `C`를 가리킨다.

```bash
git branch                      # 브랜치 목록. * 가 지금 있는 곳
git switch -c assets-experiment # 만들고 바로 이동 (옛 명령: git checkout -b)
git switch main                 # 돌아가기
git branch -d assets-experiment # 삭제 (합쳐진 것만). -D 는 강제
```

**왜 중요한가**: 브랜치를 만드는 비용은 0이다(파일 복사가 아니라 이름표 하나). 그래서 "일단 브랜치 파고 시작"이 기본 습관이 된다.

### 2. 병합(merge): 줄기를 합치기

**한 줄 정의**: `git merge 브랜치`는 그 브랜치의 변경을 **지금 있는 브랜치**에 가져온다.

두 가지 모양:
- **fast-forward**: main에 새 커밋이 없으면 이름표만 앞으로 옮긴다. 병합 커밋 없음.
- **3-way merge**: 양쪽 다 커밋이 있으면 "병합 커밋"이 하나 생긴다. 부모가 둘인 커밋.

```bash
git switch main            # 합칠 곳으로 먼저 이동
git merge assets-experiment
git log --oneline --graph -10   # 줄기가 합쳐진 모양 확인
```

**왜 중요한가**: "어느 브랜치에 서서 merge를 치는가"를 헷갈리는 게 가장 흔한 실수다. **받을 쪽에 서서** 준 쪽 이름을 적는다.

### 3. 충돌(conflict)은 고장이 아니다

**한 줄 정의**: 같은 파일의 **같은 부분**을 양쪽에서 다르게 고쳤을 때, Git이 "어느 쪽이 맞는지 모르겠으니 네가 골라라"라고 멈추는 것.

**비유**: 두 사람이 같은 문서의 같은 문장을 각자 고쳐서 보냈다. 비서(Git)는 다른 문장들은 알아서 합치지만, 그 문장만은 둘 다 보여 주고 결정을 기다린다.

**실제 예시** — 충돌 난 파일 안:

```
<<<<<<< HEAD
const XP_PER_CHECK = 10;
=======
const XP_PER_CHECK = 20;
>>>>>>> assets-experiment
```

`<<<<<<< HEAD`부터 `=======`까지가 **지금 브랜치**, 그 아래 `>>>>>>>`까지가 **가져오는 브랜치**. 해결은 세 단계:
1. 파일을 열어 둘 중 하나(또는 섞은 것)를 남기고 **표시 줄 세 개를 전부 지운다.**
2. `git add 파일` (해결했다는 표시)
3. `git commit` (병합 커밋 완성)

겁나면 `git merge --abort`로 병합 전으로 돌아간다. VS Code는 충돌 부분에 "Accept Current / Incoming / Both" 버튼을 띄워 준다.

**왜 중요한가**: 충돌을 처음 보면 "망했다"고 느끼지만, Git이 **아무것도 지우지 않았다.** 양쪽 내용이 그대로 파일 안에 있다. 읽고 고르면 끝이다.

### 4. 실험을 안전하게 하는 루틴

1. `git status`로 깨끗한지 확인(커밋 안 한 변경이 있으면 먼저 커밋).
2. `git switch -c 실험이름`.
3. 작업 → 동작 확인 → 작은 커밋 여러 개.
4. 잘 됐으면 `git switch main` → `git merge 실험이름` → 브랜치 삭제.
5. 망했으면 `git switch main` → `git branch -D 실험이름`. main은 손도 안 댔다.

Claude Code에게 "브랜치 만들고 작업해 줘"라고 하면 이 루틴을 그대로 한다. 이 세션이 `claude/…` 브랜치에서 일한 것이 바로 그것이다.

### 5. 브랜치 이름 짓기

- 무엇을 하는 브랜치인지: `assets-room`, `fix-streak-bug`, `sprites-v2`.
- 소문자, 하이픈. 한글도 되지만 터미널에서 불편하다.
- Claude Code가 만든 `claude/…` 브랜치는 세션 이름이 붙은 자동 이름이다.

### 6. 아직 안 배우는 것

`rebase`(이력을 다시 쌓기), `stash`(수정을 잠시 치워 두기), `cherry-pick`(커밋 하나만 가져오기)은 편리하지만 이력을 바꾸거나 헷갈리기 쉽다. `stash`만 간단히: 브랜치를 바꿔야 하는데 커밋하기 애매한 수정이 있으면 `git stash`로 치우고, 돌아와서 `git stash pop`. 나머지는 필요해질 때 Claude Code에게 설명을 들으며 쓴다.

## 따라하기

### 1. 브랜치 만들어 실험하기 (30분)

```bash
git status                       # 깨끗한지
git switch -c color-experiment
```

`style.css`의 `--accent` 색을 바꾸고 → 브라우저 확인 → `git commit -am "강조색 실험"` (`-a`는 추적 중인 파일을 자동 add). `git switch main` → 브라우저 새로고침 → **원래 색**인 것을 확인. 브랜치를 오가면 파일 내용이 실제로 바뀐다. 다시 `git switch color-experiment` → 바뀐 색.

### 2. 합치기 (20분)

`git switch main` → `git merge color-experiment` → "Fast-forward"가 찍히는지 → `git log --oneline --graph -5` → `git branch -d color-experiment`.

### 3. 충돌 만들고 풀기 (50분)

일부러 충돌을 낸다.
1. `git switch -c xp-20` → `routine.js`의 `XP_PER_CHECK = 10`을 `20`으로 → 커밋.
2. `git switch main` → **같은 줄**을 `15`로 → 커밋.
3. `git merge xp-20` → `CONFLICT` 메시지. `git status`로 충돌 파일 확인.
4. `routine.js`를 열어 `<<<<<<<`, `=======`, `>>>>>>>` 블록을 찾는다. `15`를 남기기로 하고 표시 줄과 `20` 줄을 지운다.
5. `git add routine.js` → `git commit` (메시지 기본값 그대로 저장) → `git log --oneline --graph -5`에서 병합 커밋 확인.
6. 되돌리고 싶으면 `git revert HEAD`(5-1)… 가 아니라, 이 실습은 값이 15로 바뀐 채 남아도 상관없다. 원래 10으로 고쳐 커밋 한 번 더.

### 4. 망한 실험 버리기 (15분)

`git switch -c bad-idea` → 아무 파일이나 크게 망가뜨리고 커밋 → `git switch main` → 멀쩡한지 확인 → `git branch -D bad-idea`. 끝. 아무 흔적도 없다.

### 5. 이 저장소의 Claude 브랜치 살펴보기 (30분)

```bash
git branch -a                    # 원격 브랜치까지. origin/claude/... 가 보인다 (5-3)
git log --oneline main..claude/confident-goodall-gdy93b | head   # main 에 없고 claude 브랜치에만 있는 커밋
```

아직 main에 합치지는 않는다. 5-3에서 GitHub의 Pull Request로 합치는 방법을 배운 뒤 한다. 지금은 "main에 없는 커밋이 몇 개인가"만 센다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 커밋 안 하고 브랜치 전환 | "Your local changes would be overwritten" | 커밋하거나 `git stash` 후 전환, 돌아와서 `git stash pop` |
| 받을 쪽/줄 쪽 혼동 | 실험 브랜치에 main 이 합쳐짐 | 받을 쪽(main)에 서서 `merge 실험` |
| 충돌 표시를 안 지우고 커밋 | 코드에 `<<<<<<<` 가 남아 문법 오류 | 파일 검색으로 `<<<<<<<` 찾아 정리 |
| 충돌이 무서워 방치 | status 가 계속 merging | `git merge --abort` 로 병합 전으로, 다시 시도 |
| `-d` 로 삭제 안 됨 | "not fully merged" | 합친 적 없는 브랜치. 버릴 거면 `-D` |
| main 에서 바로 실험 | 되돌리기 번거로움 | 항상 브랜치 먼저. CLAUDE.md 규칙에도 있음 |

## 확인 퀴즈

**1. 브랜치를 만들면 파일이 복사되나?**

<details><summary>정답과 해설</summary>
아니다. 커밋을 가리키는 이름표 하나가 생길 뿐이다. 그래서 만들고 지우는 비용이 거의 0이고, 전환하면 작업 폴더의 파일 내용이 그 브랜치의 스냅샷으로 바뀐다.
</details>

**2. fast-forward 병합과 3-way 병합의 차이는? 병합 커밋이 생기는 쪽은?**

<details><summary>정답과 해설</summary>
받는 브랜치에 새 커밋이 없으면 이름표만 앞으로 옮기는 fast-forward(병합 커밋 없음). 양쪽 다 커밋이 있으면 부모가 둘인 병합 커밋이 생기는 3-way.
</details>

**3. 충돌이 났을 때 Git이 내 코드를 지웠나? 해결 3단계는?**

<details><summary>정답과 해설</summary>
지우지 않았다. 양쪽 내용이 표시와 함께 파일 안에 있다. (1) 파일을 열어 원하는 쪽을 남기고 표시 줄 삭제 (2) `git add` (3) `git commit`. 포기하려면 `git merge --abort`.
</details>

**4. "자산관리부를 만들어 보되 잘 안 되면 없던 일로" 하고 싶다. 명령 순서는?**

<details><summary>정답과 해설</summary>
`git switch -c assets-room` → 작업·커밋 → 실패 시 `git switch main` → `git branch -D assets-room`. 성공 시 `git switch main` → `git merge assets-room` → `git branch -d assets-room`.
</details>

**5. Claude Code가 main이 아니라 별도 브랜치에서 작업하는 이유는?**

<details><summary>정답과 해설</summary>
AI의 변경을 main에 바로 넣지 않고, 사람이 확인(diff, 동작)한 뒤 합치기 위해서다. 실패하면 브랜치만 버리면 되고 main은 항상 동작하는 상태로 남는다.
</details>
