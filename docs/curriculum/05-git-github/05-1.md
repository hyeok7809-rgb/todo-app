# 5-1. Git 개념: 저장소, 커밋, 이력 보기, 되돌리기(checkout/restore/revert)

| 과정 | 5. Git과 GitHub |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 4-4 |
| 경험치 | 60 |

## 이 단원을 마치면

- Git이 "파일의 **스냅샷**을 시간순으로 쌓아 두는 장부"라는 것을 그림으로 설명할 수 있다.
- 작업 폴더 → 스테이지(준비 구역) → 저장소의 세 구역과 `git add`, `git commit`의 관계를 말할 수 있다.
- `git status`, `git log`, `git diff`로 "지금 뭐가 바뀌었고, 전에 뭘 했는지"를 혼자 읽을 수 있다.
- 실수를 세 가지 수준으로 되돌릴 수 있다: 아직 저장 안 한 수정(`restore`), 스테이지에 올린 것(`restore --staged`), 이미 커밋한 것(`revert`).

## 왜 배우나 (나에게 어떤 쓸모)

지금까지 이 저장소의 모든 변경은 Git 커밋으로 남아 있다. 1단계 가계부부터 픽셀 오피스까지, `git log`를 치면 전부 보인다. 이 단원 전까지는 Claude Code가 대신 커밋했지만, 이제부터는 **내가 읽고 되돌릴 줄 알아야** 한다. 바이브 코딩의 안전벨트는 테스트가 아니라 Git이다. AI가 코드를 망쳐도 "마지막 커밋으로 돌아가"가 가능하면 두려울 게 없다. 반대로 Git을 모르면 AI가 만든 변경을 되돌리지 못해 처음부터 다시 만들게 된다.

## 핵심 개념

### 1. Git은 스냅샷 장부다

**한 줄 정의**: Git은 프로젝트 폴더 전체의 **그 순간 모습(스냅샷)** 을 메시지와 함께 저장하고, 언제든 그 순간으로 돌아갈 수 있게 해 주는 도구다.

**비유**: 매매일지. 매일 장 마감 후 "오늘 어떤 상태였고 왜 그랬는지"를 한 줄 적는다. 나중에 "그때 왜 그랬지?"를 찾아볼 수 있고, 잘못된 결정이면 그 전으로 돌아가 생각할 수 있다. Git의 커밋 하나 = 매매일지 한 줄 + 그날의 계좌 전체 사진.

**실제 예시**: 이 저장소에서 `git log --oneline`을 치면 이렇게 나온다(위가 최신).

```
a1b2c3d 2.5단계: 지출 카테고리·이번 달 요약, 사장실(회사 현황·JSON 백업), CLAUDE.md
e4f5g6h 2단계: 인사부(데일리 루틴·연속 달성일)와 교육부(커리큘럼 진도·예정일) 개방
...
973d149 Initial commit
```

앞의 7글자는 **커밋 ID(해시)** 의 앞부분이다. 전체는 40글자지만 앞 7글자로 거의 항상 구분된다.

**왜 중요한가**: "스냅샷"이라는 말을 기억하면 뒤의 모든 명령이 이해된다. 되돌리기 = 예전 스냅샷을 꺼내기. 브랜치(5-2) = 스냅샷을 다른 줄기로 쌓기.

### 2. 세 구역: 작업 폴더, 스테이지, 저장소

**한 줄 정의**: 파일은 (1) 작업 폴더에서 수정되고 (2) `git add`로 스테이지에 올려 "이번 스냅샷에 넣을 것"으로 표시되고 (3) `git commit`으로 저장소에 스냅샷이 된다.

**비유**: 택배 포장. 책상 위에서 물건을 고르고(작업 폴더), 상자에 넣고(스테이지, `add`), 테이프를 붙여 송장을 적는다(커밋, `commit`). 상자에 안 넣은 물건은 안 간다.

```
작업 폴더 ──git add──▶ 스테이지 ──git commit──▶ 저장소(.git 폴더)
   ▲                                              │
   └──────────── git restore / checkout ──────────┘
```

**실제 예시**:

```bash
git status            # 세 구역의 현재 상태. 제일 자주 치는 명령
git add app.js        # app.js 를 상자에 넣는다
git add .             # 바뀐 것 전부 (.gitignore 에 적힌 건 빼고)
git commit -m "재무부에 카테고리 추가"   # 스냅샷 + 메시지
```

`git status`가 보여 주는 세 묶음:
- `Changes not staged for commit`: 수정했지만 상자에 안 넣음
- `Changes to be committed`: 상자에 넣음, 커밋 대기
- `Untracked files`: Git이 한 번도 본 적 없는 새 파일

**왜 중요한가**: 왜 굳이 스테이지가 있나? 한 번에 여러 파일을 고쳤어도 **관련 있는 것끼리 묶어서** 따로 커밋하기 위해서다. "카테고리 기능"과 "오타 수정"을 한 커밋에 섞지 않는다. 그래야 나중에 하나만 되돌릴 수 있다.

### 3. 무엇이 바뀌었나: diff

```bash
git diff              # 작업 폴더 vs 스테이지 (아직 add 안 한 변경)
git diff --staged     # 스테이지 vs 마지막 커밋 (add 한 변경)
git diff HEAD~1       # 마지막 커밋 vs 그 전 커밋
```

출력에서 `-`로 시작하는 줄은 지워진 것, `+`는 추가된 것. Claude Code가 "이렇게 고쳤어요"라고 보여 주는 것이 바로 이 diff다. **AI의 변경을 승인하기 전에 diff를 읽는 습관**이 바이브 코딩의 핵심이다. `HEAD`는 "지금 내가 서 있는 커밋", `HEAD~1`은 "그 하나 전".

### 4. 이력 읽기: log

```bash
git log                      # 전체 (q 로 나감)
git log --oneline            # 한 줄씩
git log --oneline -10        # 최근 10개
git log -p -- app.js         # app.js 의 변경 내용까지
git log --oneline --graph    # 브랜치 모양까지 (5-2)
git show a1b2c3d             # 그 커밋 하나의 내용
```

**왜 중요한가**: "이 함수 언제 왜 생겼지?"를 `git log -p -- 파일`로 찾는다. 커밋 메시지를 성의 있게 쓰는 이유가 여기 있다. 미래의 내가 읽는다.

### 5. 되돌리기 세 수준

| 상황 | 명령 | 결과 |
|---|---|---|
| 수정했는데 마음에 안 듦 (add 안 함) | `git restore app.js` | 마지막 커밋 상태로 파일 복구. **수정 내용 사라짐** |
| add 했는데 상자에서 빼고 싶음 | `git restore --staged app.js` | 스테이지에서만 내림. 수정 내용은 유지 |
| 커밋했는데 그 커밋을 취소하고 싶음 | `git revert a1b2c3d` | "그 커밋을 반대로 적용한" **새 커밋**을 만든다. 이력은 남음 |
| 특정 커밋 시점의 파일 하나만 보고 싶음 | `git checkout a1b2c3d -- app.js` | 그 시점 파일을 작업 폴더로 가져옴 (옛 명령, restore --source 와 같음) |

예전 글에는 `git checkout`이 많이 나오는데, 최근 Git은 역할을 나눠 `restore`(파일 복구)와 `switch`(브랜치 이동, 5-2)를 쓴다. 둘 다 동작한다.

**`reset --hard`는 아직 쓰지 않는다.** 이력을 지워 버리는 명령이라 복구가 어렵다. 초보 단계에서는 `revert`(이력을 남기며 되돌림)만 쓴다. 이 저장소의 CLAUDE.md에도 "강제 푸시·이력 삭제 금지"가 적혀 있다.

### 6. 커밋 메시지 쓰는 법

- 첫 줄: **무엇을** 했는지 50자 안쪽. "가계부에 카테고리 추가". 과거형보다 현재형/명사형.
- 한 줄 띄고 본문: **왜** 했는지, 주의할 점. 선택.
- 이 저장소의 관례: 한국어, 단계 번호로 시작("2.5단계: …").
- 나쁜 예: "수정", "버그 픽스", "ㅇㅇ". 미래의 내가 못 알아본다.

### 7. 무엇을 넣고 무엇을 뺄까

넣는 것: 코드, 문서, 설정 **견본**(`.env.example`), 작은 데이터 파일.
빼는 것(`.gitignore`): 비밀(`.env`, `kis_devlp.yaml`), 로그(`logs/`), 가상환경(`.venv/`), 캐시(`__pycache__/`), 백업 JSON 같은 개인 데이터. 4-4 숙제 3의 답이다.

## 따라하기

이 저장소에서 직접 한다. 망가뜨려도 되돌릴 수 있다는 걸 몸으로 확인하는 시간이다.

### 1. 이력 읽기 (20분)

```bash
git log --oneline | head -20     # Windows PowerShell: git log --oneline -20
git show --stat HEAD             # 마지막 커밋이 어떤 파일을 건드렸나
git log -p -- routine.js | head -80   # 인사부 파일의 변경 내용
```

질문: 이 저장소의 첫 커밋 메시지는? `sprites.js`가 처음 생긴 커밋은? (`git log --oneline -- sprites.js`의 맨 아래.)

### 2. 수정 → status → diff → add → commit (30분)

1. `docs/lesson-01.md` 맨 아래에 "(5-1 실습에서 수정)" 한 줄을 추가한다.
2. `git status` → "not staged"에 보이는지. `git diff` → `+` 줄 확인.
3. `git add docs/lesson-01.md` → `git status` → "to be committed"로 옮겨졌는지. `git diff`는 이제 비어 있고 `git diff --staged`에 보인다.
4. `git commit -m "5-1 실습: lesson-01 에 메모 한 줄"` → `git log --oneline -3`에 내 커밋이 맨 위.

### 3. 세 수준 되돌리기 (40분)

1. **restore**: `app.js` 아무 데나 글자를 넣어 망가뜨린다 → 브라우저 새로고침 → 콘솔 에러 확인 → `git restore app.js` → 새로고침 → 정상. **AI가 망쳐도 이렇게 돌린다.**
2. **restore --staged**: `style.css`를 조금 고치고 `git add style.css` → `git restore --staged style.css` → `git status`에서 다시 "not staged"로. 수정은 남아 있다. 그다음 `git restore style.css`로 수정도 버린다.
3. **revert**: 따라하기 2에서 만든 커밋을 `git log --oneline`으로 찾아 `git revert <해시>` → 편집기가 열리면 그대로 저장하고 닫기(Vim이면 `:wq`, VS Code면 창 닫기) → `git log --oneline -3`에 "Revert …" 커밋이 **추가**되고 `lesson-01.md`의 메모 줄이 사라졌는지 확인. 이력은 둘 다 남는다.

### 4. 스테이지로 커밋 나누기 (30분)

`routine.js`와 `docs/ROADMAP.md`를 둘 다 조금 고친 뒤, `git add routine.js` → 커밋 "루틴 문구 수정" → `git add docs/ROADMAP.md` → 커밋 "로드맵 메모". `git log --oneline -2`로 두 커밋이 따로 생겼는지 본다. 끝나면 두 커밋을 `revert`로 되돌리거나 그냥 둬도 된다.

### 5. Claude Code와 함께 (20분)

Claude Code에서 "지금 변경 사항을 diff로 보여 주고, 커밋 메시지를 제안해 줘"라고 한다. 제안을 읽고 **내가** `git commit`을 친다. 다음부터는 "커밋해 줘"라고 시키되, 반드시 `git log --oneline -1`과 `git show --stat HEAD`로 확인한다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| `git add .` 로 `.env`까지 올림 | status에 .env 가 보임 | `git restore --staged .env` 후 `.gitignore` 추가(4-2) |
| 커밋 메시지 없이 `git commit` | 편집기(Vim)가 열려 당황 | `:q!`로 나오고 `-m "메시지"`를 붙여 다시. 또는 `git config --global core.editor "code --wait"` |
| 이름/이메일 미설정 | "Please tell me who you are" | `git config --global user.name "이름"`, `git config --global user.email "메일"` |
| `restore`로 수정을 날림 | 되돌릴 수 없음 | 커밋 안 한 수정은 Git이 모른다. 자주 커밋하는 습관 |
| `revert`가 충돌 | CONFLICT 메시지 | 5-2에서 충돌 해결을 배운 뒤 시도. 지금은 `git revert --abort` |
| 한글 파일명이 `\354\213…`로 보임 | 깨진 것처럼 보임 | `git config --global core.quotepath false` |

## 확인 퀴즈

**1. "스냅샷"이라는 말로 커밋을 설명해 보라. 커밋은 "변경 내용"을 저장하나, "그 순간의 전체 모습"을 저장하나?**

<details><summary>정답과 해설</summary>
전체 모습(스냅샷)이다. diff는 두 스냅샷을 비교해서 **계산**한 것이다. 그래서 어떤 커밋으로든 바로 돌아갈 수 있다. (내부적으로는 안 바뀐 파일을 재사용해 용량을 아끼지만 개념은 스냅샷이다.)
</details>

**2. 파일을 고치고 `git commit -m "..."`을 쳤는데 "nothing to commit"이 나왔다. 왜?**

<details><summary>정답과 해설</summary>
`git add`로 스테이지에 올리지 않았기 때문. 커밋은 스테이지에 있는 것만 스냅샷으로 만든다. `git add 파일` 후 다시 커밋.
</details>

**3. 다음 세 상황에 맞는 명령을 고르라: (a) 아직 add 안 한 수정 버리기 (b) add 한 것 내리기 (c) 이미 커밋한 것 취소하되 이력은 남기기.**

<details><summary>정답과 해설</summary>
(a) `git restore 파일` (b) `git restore --staged 파일` (c) `git revert 해시`. `reset --hard`는 이력을 지우므로 초보 단계에서는 쓰지 않는다.
</details>

**4. AI가 코드를 크게 고쳐 놨는데 앱이 안 돈다. 가장 먼저 칠 명령 두 개는?**

<details><summary>정답과 해설</summary>
`git status`(무엇이 바뀌었나)와 `git diff`(어떻게 바뀌었나). 읽고 나서 전부 버릴 거면 `git restore .`, 일부만 살릴 거면 파일 단위로. 커밋 전이라면 이것으로 충분하다.
</details>

**5. 커밋을 자주, 작게 하라는 이유 두 가지.**

<details><summary>정답과 해설</summary>
(1) 되돌릴 단위가 작아져서 좋은 변경과 나쁜 변경을 분리할 수 있다. (2) 커밋 안 한 수정은 Git이 보호하지 못한다. "동작하는 상태"마다 커밋하면 항상 돌아갈 곳이 있다.
</details>

## 숙제

1. **내 이력 요약** — `git log --oneline`을 보고 이 저장소가 지금까지 어떤 순서로 자랐는지 5줄로 요약해 `docs/history.md`에 적고 커밋하라. 커밋 메시지는 이 단원 6절 규칙대로.
2. **되돌리기 연습 3회** — 사흘 동안 하루 한 번, 일부러 파일을 망가뜨리고 `restore`로 복구하는 걸 반복하라. 손이 기억할 때까지.
3. **4과정 스크립트 정리** — 4과정에서 만든 `notify.py`, `daily_report.py` 등을 저장소의 `scripts/` 폴더에 넣고, `.env`·`logs/`·`*.json` 개인 데이터가 `.gitignore`에 있는지 확인한 뒤 커밋하라.
