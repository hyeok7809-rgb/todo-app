# 2-1. 웹은 어떻게 동작하나: 브라우저, HTML/CSS/JS의 역할 분담, URL, 클라이언트와 서버

| 과정 | 2. 웹 기초 (HTML / CSS / JavaScript) |
|---|---|
| 예상 시간 | 2시간 |
| 선수 단원 | 1-7 |
| 경험치 | 40 |

## 이 단원을 마치면

- 주소창에 주소를 치고 엔터를 누른 뒤 화면이 뜨기까지 무슨 일이 일어나는지(DNS → HTTP 요청 → 응답 → 렌더링)를 순서대로 말할 수 있다.
- 클라이언트(client)와 서버(server)를 구분하고, "지금 이 문제는 내 쪽(브라우저) 문제인지 저쪽(서버) 문제인지"를 가려서 말할 수 있다.
- URL을 스킴·도메인·포트·경로·매개변수·앵커로 쪼개 읽을 수 있다.
- `index.html`, `style.css`, `app.js` 세 파일이 브라우저 안에서 어떤 순서로 읽히고 어떻게 연결되는지 설명할 수 있다.
- 파일을 더블클릭해서 여는 것(`file://`)과 로컬 서버로 여는 것(`http://localhost`)의 차이를 알고, 로컬 서버를 직접 띄울 수 있다.
- 개발자 도구의 네트워크(Network) 탭에서 요청과 응답, 상태 코드(200, 404)를 읽을 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

지금까지는 `index.html`을 더블클릭해서 가계부를 열었다. 그래서 "웹"이라기보다 "내 컴퓨터 안의 파일"처럼 느껴졌을 것이다. 하지만 이 과정이 끝나면 2-6에서 외부 서버에 데이터를 요청하고(fetch), 4과정에서 증권사·공공데이터 API를 부르고, 12과정에서 내 앱을 인터넷에 올려 남이 쓰게 한다. 전부 **클라이언트가 서버에 요청하고 서버가 응답한다**는 하나의 그림 위에서 돌아간다.

주식으로 비유하면 이렇다. HTS나 MTS를 켜고 매수 버튼을 누르면 내 화면(클라이언트)이 증권사 서버에 "삼성전자 10주 시장가 매수"라는 **요청**을 보내고, 서버가 "체결됐다" 또는 "증거금 부족"이라는 **응답**을 돌려준다. 호가창이 깜빡이는 것도 서버가 보내 준 데이터를 내 화면이 다시 그리는 것이다. 웹 앱은 이 구조 그대로다. 다른 점은 화면을 그리는 프로그램이 HTS가 아니라 **브라우저**이고, 그 화면을 만드는 재료가 HTML/CSS/JS라는 것뿐이다.

이 그림이 머리에 있어야 클로드에게 제대로 물어볼 수 있다. "안 돼요"가 아니라 "요청은 나갔는데 응답이 404로 온다", "서버는 200을 줬는데 화면이 안 바뀐다"라고 말하면 클로드도, 검색도, 사람도 바로 답을 준다. 1-7에서 배운 "증상·위치·완료 기준" 템플릿의 "위치"를 이 단원에서 채우는 셈이다.

## 핵심 개념

### 1. 클라이언트와 서버

**한 줄 정의.** 인터넷에 연결된 컴퓨터는 요청하는 쪽인 클라이언트(client)와 저장해 두고 응답하는 쪽인 서버(server)로 나뉜다. MDN '웹의 동작 방식': "서버는 웹페이지, 사이트, 또는 앱을 저장하는 컴퓨터입니다. 클라이언트의 장비가 웹페이지에 접근하길 원할 때, 서버로부터 클라이언트의 장치로 사용자의 웹 브라우저에서 보여지기 위한 웹페이지의 사본이 다운로드 됩니다."

**비유.** 증권사 객장. 나는 창구(클라이언트)에서 주문서를 내고, 뒤쪽 전산실(서버)이 처리해서 결과를 돌려준다. 내가 창구에서 아무리 소리쳐도 전산실 장부는 내가 못 고친다. 전산실에 **요청**을 보내고 **응답**을 기다리는 것만 가능하다.

**실제 예시.** 지금 우리 앱에는 서버가 없다. `index.html`을 더블클릭하면 브라우저가 내 하드디스크에서 파일을 직접 읽는다. 그래서 주소창이 `file:///C:/Users/.../index.html`처럼 `file://`로 시작한다. 2-6에서 처음으로 "남의 서버"에 요청을 보내 보고, 11과정에서 내 서버(AI 직원이 사는 곳)를 만든다.

**왜 중요한가.** 문제가 생겼을 때 어디를 볼지가 정해진다. 화면이 깨졌다 → 내 HTML/CSS. 버튼이 안 눌린다 → 내 JS. 데이터가 안 온다 → 요청이 제대로 나갔는지(내 쪽), 서버가 뭐라고 답했는지(저쪽) 둘로 쪼개서 본다.

### 2. 주소를 치면 일어나는 일: DNS, TCP/IP, HTTP

**한 줄 정의.** 브라우저가 서버에서 페이지를 받아오는 데는 네 가지 부품이 쓰인다. 인터넷 연결(도로), TCP/IP(운송 규칙), DNS(주소록), HTTP(주문할 때 쓰는 말).

**비유.** MDN은 "웹이 도로"라고 비유한다. "도로의 한 쪽 끝은 여러분의 집 같은 클라이언트 입니다. 다른 한 쪽 끝은 여러분이 뭔가를 사길 원하는 상점같은 서버입니다." 상점 주소를 주소록(DNS)에서 찾고, 차(TCP/IP)를 타고 가서, 가게 말(HTTP)로 주문한다.

| 부품 | MDN의 설명 (한국어판) | 비유 |
|---|---|---|
| TCP/IP | "데이터가 어떻게 웹을 건너 여행해야 하는지 정의하는 통신 규약" | 차 또는 자전거 |
| DNS | "웹사이트를 위한 주소록과 같습니다" | 상점 주소 찾기 |
| HTTP | "클라이언트와 서버가 서로 통신할 수 있게 하기 위한 언어를 정의하는 어플리케이션 규약" | 주문할 때 쓰는 언어 |
| 컴포넌트 파일 | "코드 파일"(HTML, CSS, JavaScript)과 "자원"(이미지, 영상, PDF 등) | 사 오는 상품들 |

**실제로 일어나는 순서.** MDN '웹의 동작 방식'이 정리한 4단계를 그대로 옮긴다.

1. "브라우저는 DNS 서버로 가서 웹사이트가 있는 서버의 진짜 주소를 찾습니다." 진짜 주소는 `63.245.217.105` 같은 숫자 덩어리, 즉 IP 주소(IP address)다. 사람이 외우기 어려워서 `mozilla.org` 같은 도메인 이름(domain name)을 쓰고, DNS가 둘을 맞춰 준다.
2. "브라우저는 서버에게 웹사이트의 사본을 클라이언트에게 보내달라는 HTTP 요청 메세지를 서버로 전송합니다." 이 메시지는 TCP/IP 연결을 타고 간다.
3. 서버가 요청을 승인하면 "200 OK" 메시지를 보내고, 파일을 패킷(packet)이라는 작은 덩어리로 쪼개 보낸다. MDN: "'200 OK'는 '물론이죠. 당신은 웹 사이트를 볼 수 있어요! 여기 있어요' 라는 의미입니다."
4. "브라우저는 이 작은 덩어리들을 완전한 웹 사이트로 조립하고, 당신에게 보여줍니다."

**왜 중요한가.** 네 부품 중 어디가 고장 나도 "페이지가 안 떠요"라는 같은 증상이 나온다. 와이파이가 끊겼다(도로), 주소를 잘못 쳤다(DNS), 서버가 죽었다(상점 휴업), 요청 형식이 틀렸다(주문 언어). 4과정에서 API를 부를 때 이 넷을 하나씩 의심하는 습관이 큰 시간을 아껴 준다.

### 3. HTTP 요청과 응답, 그리고 상태 코드

**한 줄 정의.** HTTP(HyperText Transfer Protocol)는 클라이언트가 요청(request)을 보내고 서버가 응답(response)을 돌려주는 규칙이다. MDN 'HTTP 개요': "HTTP는 HTML 문서와 같은 리소스들을 가져올 수 있도록 해주는 프로토콜입니다. (...) 클라이언트-서버 프로토콜이란 (보통 웹브라우저인) 수신자 측에 의해 요청이 초기화되는 프로토콜을 의미합니다."

**비유.** 주문서와 영수증. 주문서(요청)에는 "뭘 할 건지(메서드)", "어떤 상품(경로)", "추가 요청 사항(헤더)"이 적히고, 영수증(응답)에는 "처리 결과(상태 코드)"와 "상품(본문)"이 담긴다.

**실제 예시.** MDN이 정리한 요청의 구성 요소는 "HTTP 메서드, 보통 클라이언트가 수행하고자 하는 동작을 정의한 GET, POST 같은 동사", "가져오려는 리소스의 경로", "HTTP 프로토콜의 버전", "선택적 헤더들", 그리고 POST 같은 경우의 "본문"이다. 응답은 "HTTP 프로토콜의 버전", "요청의 성공 여부와, 그 이유를 나타내는 상태 코드", "상태 메시지", "헤더들", "선택 사항으로 가져온 리소스가 포함되는 본문"이다.

우리 앱을 로컬 서버로 열면(따라하기 3) 브라우저는 이런 요청을 세 번 보낸다.

```
GET /index.html  → 200 OK, 본문: HTML 파일
GET /style.css   → 200 OK, 본문: CSS 파일
GET /app.js      → 200 OK, 본문: JS 파일
```

상태 코드(status code)는 세 자리 숫자다. MDN 'HTTP 상태 코드': "응답은 5개의 그룹으로 나누어집니다: 정보를 제공하는 응답, 성공적인 응답, 리다이렉트, 클라이언트 에러, 그리고 서버 에러." 지금 외울 것은 세 개면 된다.

| 코드 | 이름 | 뜻 (MDN 한국어판) | 누구 잘못? |
|---|---|---|---|
| 200 | OK | "요청이 성공적으로 되었습니다." | 잘됨 |
| 404 | Not Found | 서버에 그 경로의 리소스가 없음 | 주로 내 쪽(주소·파일 이름 오타) |
| 500 | Internal Server Error | "서버가 처리 방법을 모르는 상황이 발생했습니다." | 저쪽(서버) |

400번대는 "클라이언트 에러", 500번대는 "서버 에러"라는 것만 기억해도 반은 간다. 4-1에서 더 자세히 다룬다.

**왜 중요한가.** 상태 코드는 "누구 잘못인지"를 숫자 하나로 말해 준다. 증권사 API가 401을 주면 내 인증 문제, 503이면 증권사 점검 시간이다. 코드만 보고 다음 행동이 정해진다.

### 4. URL 해부하기

**한 줄 정의.** URL(Uniform Resource Locator)은 웹 위의 자원 하나를 가리키는 주소다. MDN 'URL이란?': "URL은 웹에서 주어진 고유 리소스 주소에 지나지 않습니다."

**비유.** 택배 송장. 배송 방법(스킴), 건물 주소(도메인), 출입구 번호(포트), 호수(경로), 추가 요청 사항(매개변수), "현관 앞에 두세요" 같은 세부 지시(앵커).

**실제 예시.** 문서용으로 예약된 가짜 도메인 `example.com`으로 만든 예다.

```
https://example.com:443/stocks/005930?period=1d&chart=candle#news
└─┬─┘   └────┬────┘└┬┘└─────┬─────┘└──────────┬──────────┘└─┬─┘
스킴       도메인     포트    경로            매개변수          앵커
```

| 조각 | 예 | MDN의 설명 |
|---|---|---|
| 스킴(scheme) | `https` | "URL의 첫 번째 부분은 브라우저가 리소스를 요청하는 데 사용해야 하는 프로토콜을 나타냅니다." `http`보다 `https`가 암호화된 버전 |
| 도메인(domain) | `example.com` | "도메인은 요청하는 웹 서버를 나타냅니다." |
| 포트(port) | `:443` | "포트는 웹 서버의 리소스에 접근하는 데 사용되는 기술적인 '게이트'를 나타냅니다." HTTP(80)·HTTPS(443) 기본 포트면 보통 생략 |
| 경로(path) | `/stocks/005930` | "웹 서버에 있는 리소스의 경로입니다." |
| 매개변수(parameters) | `?period=1d&chart=candle` | "웹 서버에 제공되는 추가 매개변수입니다." `키=값`을 `&`로 이어 붙인다 |
| 앵커(anchor) | `#news` | "리소스 자체의 어떤 부분에 대한 앵커입니다." 페이지 안의 특정 위치 |

우리 앱의 로컬 주소 `http://localhost:8000/index.html`을 같은 틀로 읽으면: 스킴 `http`, 도메인 `localhost`(내 컴퓨터 자신을 가리키는 이름), 포트 `8000`, 경로 `/index.html`.

**왜 중요한가.** 4과정의 API는 전부 URL로 부른다. 매개변수 자리에 `?code=005930&date=20261021` 같은 값을 넣어 "어떤 종목의 어느 날 시세"를 지정한다. URL을 읽을 줄 알면 API 문서가 반은 읽힌다. 또 404가 나면 경로 조각부터 의심하면 된다.

### 5. HTML, CSS, JavaScript의 역할 분담과 브라우저가 읽는 순서

**한 줄 정의.** HTML은 구조(뭐가 있는지), CSS는 모양(어떻게 보이는지), JavaScript는 동작(눌렀을 때 뭘 할지)을 맡는다. 1단계 레슨에서 "건물의 뼈대 / 인테리어 / 전기 배선"으로 비유했던 그것이다.

**비유.** 호가창 화면. 칸이 어디에 몇 개 있는지(HTML), 매수는 빨강 매도는 파랑(CSS), 숫자가 바뀌면 깜빡이고 클릭하면 주문창이 열리는 것(JS).

**실제 예시.** 브라우저가 우리 `index.html`을 받으면 무슨 일이 생기나. MDN 'How browsers load websites'(영어판)의 설명을 우리 파일에 대입했다.

1. **HTML 파싱.** "the HTML file that contains the web page content and defines its structure is received by the browser, and parsed. The browser converts it into a tree-like structure called a DOM tree (Document Object Model)." 즉 `<section id="map-screen">` 안에 `<header>`가 있고 그 안에 `<h1>`이 있는 **나무 구조**를 메모리에 만든다. 이게 2-4에서 다룰 DOM이다.
2. **추가 요청.** 파싱 중에 `<link rel="stylesheet" href="style.css">`와 `<script src="app.js">`를 만나면 그 파일들을 더 요청한다. MDN: "Certain HTML elements, when parsed, will trigger more HTTP requests: `<link>` elements referencing external CSS stylesheets. `<script>` elements referencing external JavaScript files." 그래서 네트워크 탭에 파일 세 개가 찍힌다.
3. **CSS 적용.** "The browser parses the CSS (...) and sorts the different CSS styling rules into different 'buckets' based on which HTML elements (...) they will be applied to." `.room { display: flex }` 같은 규칙을 해당 요소에 붙이고 배치(layout)한 다음 화면에 그린다(paint).
4. **JavaScript 실행.** "After the CSS has been handled, any JavaScript found on the page (...) is parsed, interpreted, compiled, and executed." `app.js`의 `load(); render();`가 이때 돌면서 저장된 내역을 DOM에 끼워 넣는다.

우리 `index.html`에서 `<script src="app.js">`가 `</body>` 바로 앞, 즉 **맨 아래**에 있는 이유가 여기 있다. 위에서 아래로 읽는 브라우저가 `<form id="entry-form">`을 먼저 만들어 둬야 `app.js`의 `document.getElementById("entry-form")`이 `null`이 아니라 진짜 요소를 받는다(1-7의 `Cannot read properties of null`이 바로 이 순서가 꼬였을 때 나는 에러다).

**왜 중요한가.** 세 언어를 한 파일에 섞어 쓰지 않고 역할별로 나누는 습관은 이 단원 이후 모든 코드의 기본이다. 클로드에게 "CSS만 고쳐 줘", "JS 로직은 건드리지 말고 HTML 구조만 바꿔 줘"라고 범위를 잘라 말할 수 있어야 결과를 검증하기 쉽다.

### 6. 정적 사이트와 동적 사이트, 그리고 `file://`의 한계

**한 줄 정의.** 정적 사이트는 요청할 때마다 같은 파일을 그대로 주고, 동적 사이트는 요청에 따라 서버가 내용을 만들어서 준다. MDN '웹 서버란 무엇일까?': "정적 웹 서버 혹은 스택은 HTTP 서버 (소프트웨어)가 있는 컴퓨터(하드웨어)로 구성되어 있습니다. 서버가 그 불려진 파일을 당신의 브라우저에게 전송하기 때문에, 저희는 그것을 '정적'이라고 부릅니다." "동적 웹 서버는 정적 웹 서버와 추가적인 소프트웨어(대부분 일반적인 애플리케이션 서버와 데이터베이스)로 구성되어 있습니다."

**비유.** 정적은 자판기(누르면 같은 캔이 나온다), 동적은 바리스타(주문을 듣고 그 자리에서 만든다).

**실제 예시.** 우리 가계부는 **정적 사이트**다. 서버가 하는 일은 파일 세 개를 건네주는 것뿐이고, 계산과 저장은 전부 브라우저 안(JS + localStorage)에서 일어난다. 그래서 12-3에서 GitHub Pages 같은 "파일만 올려두는 무료 서버"에 그대로 배포할 수 있다. 반면 11과정의 AI 직원실은 요청마다 클로드 API를 불러 답을 만들어야 하니 **동적 서버**가 필요하다.

**`file://`의 한계.** 더블클릭으로 연 페이지는 서버 없이 하드디스크에서 읽은 것이라 주소가 `file://`로 시작한다. 지금까지는 아무 문제가 없었지만, 브라우저는 `file://`로 연 문서에 보안상 제약을 두기 때문에 2-6의 `fetch` 같은 기능은 상황에 따라 막힐 수 있다(브라우저와 설정에 따라 다르다). 그래서 개발자들은 자기 컴퓨터에 **로컬 서버**를 띄우고 `http://localhost:8000`으로 연다. 따라하기 3에서 해 본다. 파이썬 공식 문서가 안내하는 한 줄짜리 서버 명령은 이것이다.

```
python -m http.server [OPTIONS] [port]
```

"The server listens to port 8000 by default."(기본 포트 8000) 그리고 `python -m http.server 9000`처럼 숫자를 붙이면 포트를 바꿀 수 있다.

**왜 중요한가.** "내 컴퓨터에서 되는데 올리면 안 돼요"의 절반은 `file://`와 `http://`의 차이에서 온다. 처음부터 로컬 서버로 여는 습관을 들이면 배포 때 놀랄 일이 줄어든다.

## 따라하기

### 따라하기 1. 네트워크 탭으로 파일 세 개가 오가는 것 보기

1. `index.html`을 브라우저로 연다(아직은 더블클릭으로 괜찮다).
2. 개발자 도구를 연다. MDN 안내 기준 단축키는 **Windows: `Ctrl`+`Shift`+`I` 또는 `F12`**, **macOS: `⌘`+`⌥`+`I`**. 크롬 메뉴로는 "More tools ➤ Developer tools"(한국어 메뉴에서는 "도구 더보기 ➤ 개발자 도구"로 보인다. 메뉴 이름은 브라우저 버전에 따라 다를 수 있으니 실제 화면을 따르자).
3. 위쪽 탭에서 **Network**(네트워크)를 고른다. 비어 있으면 `F5`로 새로고침한다.
4. 목록에 `index.html`, `style.css`, `app.js`가 찍히는지 본다. 각 줄을 클릭하면 요청(Request)과 응답(Response) 정보가 보인다. `file://`로 열었을 때는 상태 코드가 비어 있거나 다르게 보일 수 있다. 따라하기 3에서 로컬 서버로 다시 열면 `200`이 정확히 찍힌다.
5. 순서를 관찰하자. `index.html`이 먼저, 그다음에 `style.css`와 `app.js`. 핵심 개념 5에서 본 "HTML을 읽다가 `<link>`, `<script>`를 만나면 추가 요청" 그대로다.

### 따라하기 2. URL 분해 연습

| 스킴 | | | |
| 도메인 | | | |
| 포트(없으면 "생략") | | | |

### 따라하기 3. 로컬 서버로 가계부 열기

0-3에서 설치한 파이썬을 쓴다. 터미널에서 프로젝트 폴더로 이동한 뒤 서버를 켠다.

**Windows (PowerShell)**

```powershell
cd C:\Users\내이름\todo-app      # 0-2에서 배운 경로 이동. 실제 폴더 위치로 바꾼다
python -m http.server 8000
```

**Mac (터미널)**

```bash
cd ~/todo-app
python3 -m http.server 8000
```

`Serving HTTP on ...  port 8000` 비슷한 줄이 뜨면 성공이다. 이 터미널 창은 서버가 돌아가는 동안 그대로 둔다(끄려면 `Ctrl`+`C`). `python` 명령이 인식되지 않으면 0-3의 설치 확인으로 돌아가자.

브라우저에서 `http://localhost:8000` 을 연다. 주소창이 `file://`이 아니라 `http://`로 시작하는 것을 확인한다. 이제 네트워크 탭을 다시 보자.

- `index.html`(또는 `/`), `style.css`, `app.js` 세 줄 모두 **Status 200**.
- 터미널에도 `"GET /style.css HTTP/1.1" 200 -` 같은 줄이 찍힌다. 브라우저(클라이언트)가 보낸 요청을 파이썬(서버)이 받았다는 기록, 즉 **로그**다.

이제 일부러 없는 파일을 요청해 보자. 주소창에 `http://localhost:8000/없는파일.html` 을 쳐 본다. 브라우저에는 "Error response ... 404" 비슷한 페이지가, 네트워크 탭에는 **404**가, 터미널 로그에도 404가 찍힌다. 방금 "클라이언트 에러"를 직접 만든 것이다.

마지막으로 터미널에서 `Ctrl`+`C`로 서버를 끄고 브라우저를 새로고침해 보자. 페이지가 안 뜬다. 서버가 죽으면 클라이언트는 아무것도 못 받는다는 것을 몸으로 확인하는 실험이다.

## 확인 퀴즈

**1. 주소창에 `example.com`을 치고 엔터를 눌렀다. MDN이 설명한 4단계 중 가장 먼저 일어나는 일은?**

<details><summary>정답과 해설</summary>
DNS 조회다. "브라우저는 DNS 서버로 가서 웹사이트가 있는 서버의 진짜 주소를 찾습니다." 도메인 이름을 IP 주소로 바꾼 다음에야 HTTP 요청을 보낼 수 있다. 요청 → 200 OK와 패킷 전송 → 브라우저가 조립해서 표시, 순서다.
</details>

**2. `https://example.com/stocks/005930?period=1d#chart` 에서 `?period=1d`는 무엇이고, `#chart`는 무엇인가?**

<details><summary>정답과 해설</summary>
`?period=1d`는 매개변수(parameters)로 "웹 서버에 제공되는 추가 매개변수"다. 키 `period`에 값 `1d`. `#chart`는 앵커(anchor)로 "리소스 자체의 어떤 부분에 대한 앵커", 즉 페이지 안의 특정 위치를 가리킨다. 참고로 앵커는 서버로 전송되지 않고 브라우저가 처리한다.
</details>

**3. API를 불렀더니 상태 코드 404가 왔다. 먼저 의심할 것은 내 쪽인가 서버 쪽인가? 그 이유는?**

<details><summary>정답과 해설</summary>
내 쪽(클라이언트)이다. 400번대는 "클라이언트 에러" 그룹이고 404 Not Found는 그 경로에 리소스가 없다는 뜻이므로, URL의 경로·파일 이름·매개변수 오타부터 본다. 반면 500번대는 "서버 에러"로, 서버 쪽 문제다(500: "서버가 처리 방법을 모르는 상황이 발생했습니다").
</details>

**4. `index.html`에서 `<script src="app.js">`를 `<head>` 안으로 옮겼더니 콘솔에 `Cannot read properties of null (reading 'addEventListener')`가 떴다. 왜인가?**

<details><summary>정답과 해설</summary>
브라우저는 HTML을 위에서 아래로 파싱하며 DOM 트리를 만들고, `<script>`를 만나면 그 시점에 JS를 실행한다. `<head>`에서 실행되면 아직 `<form id="entry-form">`이 만들어지기 전이라 `document.getElementById("entry-form")`이 `null`을 돌려주고, `null.addEventListener`에서 에러가 난다. 그래서 스크립트를 `</body>` 직전에 둔다.
</details>

**5. 우리 가계부가 "정적 사이트"인 이유를 한 문장으로 설명하라. 어떤 기능이 추가되면 동적 서버가 필요해지는가?**

<details><summary>정답과 해설</summary>
서버는 `index.html`, `style.css`, `app.js` 파일을 요청할 때마다 그대로 건네줄 뿐이고, 계산·저장은 전부 브라우저 안에서 일어나기 때문이다("서버가 그 불려진 파일을 당신의 브라우저에게 전송하기 때문에 (...) '정적'"). 요청마다 서버가 내용을 만들어야 하는 기능, 예를 들어 AI 직원실에서 클로드 API를 호출해 답을 생성하거나 여러 기기에서 같은 가계부를 공유하려면 동적 서버(애플리케이션 서버 + 데이터베이스)가 필요하다.
</details>

## 숙제

1. **로컬 서버 습관 들이기** — 오늘부터 가계부를 열 때는 더블클릭 대신 `python -m http.server 8000`(Mac은 `python3`)으로 열자. 서버를 켜고 끄는 명령을 메모장이 아니라 손이 기억할 때까지 세 번 반복한다.
2. **404 만들고 고치기** — `index.html`의 `<link rel="stylesheet" href="style.css">`를 일부러 `styel.css`로 바꿔 저장하고 새로고침한다. (a) 화면이 어떻게 변하는지, (b) 네트워크 탭과 터미널 로그에 어떤 상태 코드가 찍히는지 적은 뒤 원래대로 되돌린다. 되돌리기는 1-7에서 배운 `git checkout index.html`로도 된다.
3. **내 하루의 요청-응답 찾기** — 오늘 사용한 앱(증권사 MTS, 배달 앱, 유튜브) 중 하나를 골라 "내가 보낸 요청"과 "서버가 돌려준 응답"을 세 쌍 적어 본다. 예: 요청 "삼성전자 호가 보여 줘" → 응답 "호가 10단계 숫자". 서버가 응답을 못 주면 화면이 어떻게 될지도 상상해서 적는다.
4. **클로드에게 검증 요청** — 숙제 3의 표를 Claude(claude.ai 또는 Claude Code)에 붙여 넣고 "이 요청-응답 구분이 맞는지, 틀린 게 있으면 왜 틀린지 설명해 줘"라고 물어 본다. 답이 MDN 설명과 다르면 그 부분을 다시 묻는다.
