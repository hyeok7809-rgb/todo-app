# 2-5. 저장: localStorage, JSON 직렬화, 데이터 구조 설계(어떤 모양으로 저장할까)

| 과정 | 2. 웹 기초 (HTML / CSS / JavaScript) |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 2-4 |
| 경험치 | 60 |

## 이 단원을 마치면

- `localStorage`가 무엇이고 어디에 얼마나 저장되며, 어떤 경우에 "사라진 것처럼" 보이는지(출처가 다름, 브라우저 데이터 삭제, 시크릿 창) 설명할 수 있다.
- `setItem`/`getItem`/`removeItem`/`clear`를 쓰고, `getItem`이 `null`을 돌려줄 때와 `setItem`이 실패할 때를 처리할 수 있다.
- `JSON.stringify`/`JSON.parse`가 왜 필요한지, JSON이 JS 객체와 어떻게 다른지(큰따옴표, `undefined` 없음 등) 알고, 깨진 JSON을 `try...catch`로 안전하게 읽을 수 있다.
- "어떤 모양으로 저장할까"를 설계할 수 있다: 객체 배열, 고유 id, 날짜·금액의 표현 방식, 버전 필드, 키 이름 규칙.
- 저장된 데이터를 JSON 파일로 내보내고(백업) 다시 불러오는(복원) 기능을 만들 수 있다.
- 2-4의 매매 복기 폼에 저장을 붙여 새로고침해도 남는 앱으로 완성한다.

## 왜 배우나 (나에게 어떤 쓸모)

저장이 없는 앱은 메모장에 적고 창을 닫는 것과 같다. 가계부가 "새로고침해도 내역이 남는" 이유가 `localStorage` 다섯 줄이고, 이 단원은 그 다섯 줄을 **제대로** 이해하는 시간이다. 특히 "데이터가 갑자기 사라졌어요"는 저장을 모르는 사람이 가장 많이 겪는 사고다. 원인(출처가 바뀜, 브라우저 정리, 잘못된 JSON)을 알면 사고를 미리 막을 수 있다.

주식 비유로는 **매매일지 양식 정하기**. 종목·매수가·매도가·수량·이유를 어떤 칸에 어떤 형식으로 적을지 정해 두면 한 달 뒤 복기할 때 합계와 승률이 바로 나오지만, 매번 다른 양식으로 적으면 쌓여도 쓸 수가 없다. 데이터 구조 설계가 그 양식이다. 로드맵 3단계(자산관리부)·5단계(루틴)·6단계(교육부, 백업)는 전부 "새 양식을 설계하고 저장한다"는 같은 일이다.

그리고 JSON은 이 과정 밖에서도 계속 나온다. 2-6의 API 응답, 3-3의 파이썬 파일 읽기, 4과정의 증권사 API, 9-6의 `settings.json`, 10과정의 Claude API 요청·응답까지 전부 JSON이다. 1-6에서 "표준 포장지"라고 배운 것을 여기서 완전히 손에 익힌다.

## 핵심 개념

### 1. `localStorage`: 출처별로 나뉜, 문자열만 담는 서랍

**한 줄 정의.** `localStorage`는 브라우저가 **출처(origin)**마다 따로 마련해 둔 키-값 저장소이고, 만료되지 않으며, 문자열만 담는다. MDN `Window.localStorage`: "`localStorage` 읽기 전용 속성을 사용하면 Document 출처의 Storage 객체에 접근할 수 있습니다. 저장한 데이터는 브라우저 세션 간에 공유됩니다." "키와 값은 **항상** (...) UTF-16 DOMString의 형태로 저장합니다."

**비유.** 증권사별 계좌. 같은 내가 써도 A증권 계좌와 B증권 계좌는 서로 못 본다. 여기서 "증권사"가 출처다. 출처는 **스킴 + 도메인 + 포트** 세 가지로 결정되므로 하나만 달라도 다른 서랍이다. MDN: "`localStorage`에 저장한 자료는 **페이지 프로토콜별로 구분**합니다. 특히 HTTP로 방문한 페이지에서 저장한 데이터는 같은 페이지의 HTTPS와는 다른 `localStorage`에 저장됩니다."

**실제 예시.** 2-1에서 더블클릭(`file://`)으로 열다가 로컬 서버(`http://localhost:8000`)로 바꿨을 때 **가계부 내역이 사라진 것처럼 보였을 것이다**. 데이터가 지워진 게 아니라 서랍이 다른 것이다. `file://`로 다시 열면 그대로 있다. 나중에 12-3에서 `https://내이름.github.io`로 배포하면 또 다른 서랍이다. MDN은 `file:` 출처에서는 접근 자체가 `SecurityError`가 날 수 있다고도 적어 두었다("출처가 `file:`이나 `data:` 스킴을 사용했을 때 발생할 수 있습니다"). 브라우저마다 다르지만, 이것이 2-1에서 "앞으로는 로컬 서버로 열자"고 한 또 하나의 이유다.

**`sessionStorage`와의 차이.** 같은 API인데 수명이 다르다. MDN: "`localStorage`의 데이터는 만료되지 않고, `sessionStorage`의 데이터는 **페이지 세션**이 끝날 때 제거되는 차이가 있습니다." 탭을 닫으면 사라지는 임시 데이터(예: 입력 중이던 폼)에는 `sessionStorage`, 남아야 하는 기록에는 `localStorage`.

**용량.** MDN 'Storage quotas and eviction criteria'(영어판): "Web Storage (...) is limited to 10 MiB of data maximum on all browsers. Browsers can store up to 5 MiB of local storage, and 5 MiB of session storage per origin." 가계부 한 건이 100자 안팎이니 수만 건은 들어간다. 다만 이미지·대용량에는 맞지 않다. 그런 용도는 IndexedDB다. MDN: "IndexedDB는 파일이나 블롭 등 많은 양의 구조화된 데이터를 클라이언트에 저장하기 위한 로우 레벨 API입니다. (...) Web Storage는 적은 양의 데이터를 저장하는데 유용하지만" 지금은 이름만 알아 두자.

**언제 사라지나.** 사용자가 브라우저 데이터(사이트 데이터)를 지울 때, 시크릿/사생활 보호 창을 닫을 때, 그리고 MDN이 언급하듯 일부 브라우저는 사생활 보호 모드에서 "an empty `localStorage` object with a quota of zero"를 줄 수도 있다. 그래서 **중요한 기록은 내보내기(백업)가 필요**하다(핵심 개념 6).

**왜 중요한가.** "내 컴퓨터, 내 브라우저, 이 주소"라는 세 조건이 모두 같을 때만 보인다는 것을 알면, 폰에서 가계부를 열었을 때 내역이 없는 것이 버그가 아님을 안다. 여러 기기에서 공유하려면 서버가 필요하다(2-1의 동적 서버, 11과정).

### 2. `Storage`의 메서드: 넣기, 꺼내기, 지우기

**한 줄 정의.** `localStorage`는 `Storage` 객체이고, MDN `Storage`: "데이터를 추가하고 수정하거나 삭제할 수 있습니다."

| 메서드 | 하는 일 | MDN 설명 (영어판/한국어판) | 주의 |
|---|---|---|---|
| `setItem(키, 값)` | 넣기(있으면 덮어쓰기) | "will add that key to the given `Storage` object, or update that key's value if it already exists." | 값이 문자열이 아니면 문자열로 바뀐다(객체는 `"[object Object]"`가 된다!) |
| `getItem(키)` | 꺼내기 | "will return that key's value, or `null` if the key does not exist" | 없으면 `null`. `JSON.parse(null)`은 `null`을 돌려주므로 반드시 검사 |
| `removeItem(키)` | 그 키만 지우기 | | |
| `clear()` | 이 출처의 전부 지우기 | "clears all keys stored in a given `Storage` object." | 다른 기능이 저장한 것까지 지운다 |
| `key(번호)`, `length` | n번째 키 이름, 키 개수 | | 디버깅·백업 때 전체 순회용 |

**실제 예시.** `app.js` 3번 구역.

```js
const STORAGE_KEY = "ledger-entries";

function save() {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(entries));
}

function load() {
  const saved = localStorage.getItem(STORAGE_KEY);   // 없으면 null
  if (saved) {                                       // null은 거짓 → 건너뜀 (1-3)
    entries = JSON.parse(saved);
  }
}
```

`setItem`이 실패할 수도 있다. MDN `setItem`은 예외로 `QuotaExceededError`를 든다. 용량이 찼거나 사생활 보호 모드일 때다. 가계부 규모에서는 거의 안 나지만, 사용자가 쓰는 앱(13과정)에서는 `try...catch`로 감싸 "저장에 실패했습니다"를 알려야 한다.

**왜 중요한가.** 네 메서드만 알면 끝이지만, `getItem`의 `null`과 `setItem`의 "문자열만"이라는 두 성질을 모르면 데이터가 조용히 깨진다. 특히 `localStorage.setItem("x", entries)`처럼 `JSON.stringify` 없이 넣으면 `"[object Object]"`가 저장되고, 꺼내서 `JSON.parse`하면 에러가 난다. 이것이 다음 개념이다.

### 3. JSON 직렬화: 객체를 글자로, 글자를 객체로

**한 줄 정의.** 직렬화(serialization)는 메모리 속 객체·배열을 **저장·전송 가능한 문자열**로 바꾸는 것이고, 그 표준 형식이 JSON이다. `JSON.stringify()`는 "JavaScript 값이나 객체를 JSON 문자열로 변환합니다", `JSON.parse()`는 "JSON 문자열의 구문을 분석하고, 그 결과에서 JavaScript 값이나 객체를 생성합니다."(MDN)

**비유.** 1-6의 택배 포장. 서랍(`localStorage`)에는 "글자로 쓴 종이"만 들어가니 물건(배열)을 종이에 받아 적고(`stringify`), 꺼낼 때 종이를 읽어 물건을 다시 만든다(`parse`).

**실제 예시.** 콘솔에서.

```js
const entry = { id: 1761000000000, type: "expense", title: "점심", amount: 9000, date: "2026-10-21" };
const text = JSON.stringify(entry);
text;             // '{"id":1761000000000,"type":"expense","title":"점심","amount":9000,"date":"2026-10-21"}'
typeof text;      // "string"

const back = JSON.parse(text);
back.amount + 1;  // 9001 (숫자로 돌아옴)
back === entry;   // false (내용은 같지만 새로 만든 객체)

JSON.stringify(entry, null, 2);   // 들여쓰기 2칸으로 예쁘게 (백업 파일·디버깅용)
```

**JSON은 JS가 아니다.** MDN `JSON`: "JSON은 객체, 배열, 숫자, 문자열, 불리언과 `null`을 직렬화하기 위한 구문으로, JavaScript 구문에 기반을 두고 있지만 분명한 차이점을 가지고 있습니다. 즉, 어떤 JavaScript는 JSON이 아닙니다."

| JS에서는 되는데 JSON에서는 | MDN 설명 | 결과 |
|---|---|---|
| 키에 따옴표 없음 `{title: "점심"}` | "속성의 이름은 반드시 큰따옴표로 표시된 문자열이어야 합니다." | `parse` 시 `SyntaxError` |
| 작은따옴표 `'점심'` | "문자열의 작은따옴표 금지" | `SyntaxError` |
| 끝에 쉼표 `[1, 2, ]` | "후행 쉼표는 허용하지 않습니다." | `SyntaxError` |
| 주석 `// 메모` | "주석 (...) 미지원" | `SyntaxError` |
| `undefined`, 함수 | `stringify` 시 "생략되거나(객체 안에 있을 경우) `null`로 변환된다(배열 안에 있을 경우)" | 조용히 사라짐 |
| `Date` 객체 | 문자열로 바뀜(`"2006-01-02T15:04:05.000Z"`), `parse` 후에도 문자열 | 날짜는 처음부터 문자열로 저장하는 편이 안전 |
| `NaN`, `Infinity` | "지원하지 않습니다" | `null`이 됨 |

`app.js`가 `date`를 `Date` 객체가 아니라 `"2026-10-21"` 문자열로 저장하는 이유가 바로 이 표다. 숫자 `id`는 그대로 숫자로 돌아오고, `amount`도 숫자로 돌아온다.

**깨진 JSON 읽기.** MDN `JSON.parse`: "변환할 문자열이 유효한 JSON이 아닐 경우 `SyntaxError`." 사용자가 개발자 도구에서 값을 잘못 고쳤거나 옛 버전 앱이 다른 형식으로 저장했으면 `load()`에서 앱이 통째로 멈춘다. 1-7의 `try...catch`로 감싼다(따라하기 3).

**왜 중요한가.** "저장했는데 꺼내면 이상해요"의 원인은 셋 중 하나다. `stringify`를 안 했거나, `parse`를 안 했거나, JSON이 될 수 없는 값(`Date`, `undefined`)을 넣었거나. 이 표를 보면 전부 설명된다.

### 4. 데이터 구조 설계: 어떤 모양으로 저장할까

**한 줄 정의.** 저장할 데이터의 **모양(스키마, schema)**을 먼저 정한다. 각 기록은 어떤 키를 갖고, 각 값은 어떤 자료형이며, 전체는 어떻게 묶이는가.

**비유.** 엑셀 시트의 열 제목과 서식을 먼저 정하는 것. "날짜 열은 YYYY-MM-DD, 금액 열은 숫자(원), 구분 열은 '매수/매도' 둘 중 하나". 이걸 안 정하고 적기 시작하면 한 달 뒤 합계가 안 맞는다.

**실제 예시.** 가계부의 설계와 그 이유.

```js
// 전체: 객체들의 배열 (1-6). 순서가 있고 filter/map/find가 바로 된다.
[
  {
    id: 1761000000000,        // 숫자. 고유. Date.now()로 생성 → 삭제 시 이걸로 찾는다
    type: "expense",          // 정해진 값 중 하나("expense" | "income"). 한글 "지출"이 아님
    title: "점심",            // 문자열. 사용자 입력 그대로
    amount: 9000,             // 숫자. 단위는 원, 정수. "9,000원"처럼 꾸민 문자열 절대 금지
    date: "2026-10-21",       // 문자열, ISO 형식. 비교·정렬이 글자 순서로 됨
  },
]
```

설계 원칙 일곱 가지.

1. **한 건 = 객체 하나, 전체 = 배열.** 표 모양. 나중에 `filter`로 "이번 달 지출만", `reduce`로 합계가 한 줄이다.
2. **고유 `id`를 꼭 둔다.** 제목이 같은 "점심"이 두 건 있어도 구분해야 삭제·수정이 안전하다. `Date.now()`는 같은 밀리초에 두 건을 넣지 않는 한 충분하다.
3. **값은 가장 날것으로.** 금액은 `9000`(숫자), 화면의 "9,000원"은 `formatMoney()`가 **그릴 때** 만든다. 날짜도 `"2026-10-21"`로 저장하고 "10월 21일"은 그릴 때. 저장 형식과 표시 형식을 섞으면 계산이 깨진다.
4. **정해진 값은 영문 코드로.** `type: "expense"`처럼. 화면 글자("지출")를 바꾸고 싶을 때 데이터를 안 건드려도 된다. 1-6에서 `<option value="expense">지출</option>`로 나눈 것과 같은 이유다.
5. **키 이름은 짧고 일관되게.** `amount`로 정했으면 다른 기록에서 `price`·`money`로 바꾸지 않는다. 소문자 camelCase(`tradeDate`)를 쓰는 것이 JS 관례다.
6. **저장 키 이름은 앱 이름을 붙여** 다른 기능과 충돌을 막는다. `"ledger-entries"`, `"trade-log"`, `"routine-checks"`처럼. `STORAGE_KEY` 상수로 한 곳에 둔다.
7. **버전을 남긴다.** 나중에 키를 바꾸면(예: `title` → `memo`) 옛 데이터를 읽을 때 변환이 필요하다. `{ version: 1, entries: [...] }`처럼 감싸 두면 `load()`에서 버전을 보고 변환할 수 있다. 지금 가계부는 배열만 저장하는 1단계라 괜찮지만, 로드맵 3단계(여러 데이터)부터는 감싸는 편이 좋다.

**매매 복기의 설계.** 2-4의 `trades` 배열은 이미 원칙 1~5를 따른다. 여기에 나중에 필요한 것들을 미리 생각해 보자. "수익률"은 저장하지 않는다(매수·매도 기록에서 계산). "전략"은 `strategy: "breakout"`처럼 코드로. "복기 메모"는 `memo` 문자열. 여러 번 나눠 산 것은 한 건씩 따로(평단가는 계산). 이렇게 **계산할 수 있는 값은 저장하지 않는다**는 원칙을 더하면 데이터가 어긋날 일이 없다. 2-4의 "진실의 원본"과 같은 생각이다.

**왜 중요한가.** 클로드에게 기능을 시킬 때 "데이터는 이런 모양이야"라고 먼저 주면 결과가 훨씬 정확하다. 모양을 안 주면 클로드가 자기 식으로 설계해 버리고, 그 설계가 기존 데이터와 안 맞아 "저장된 게 다 사라졌어요"가 된다. 데이터 모양을 **내가** 쥐고 있어야 한다.

### 5. 안전한 `load()`: 없을 때, 깨졌을 때, 모양이 다를 때

**한 줄 정의.** 저장소에서 읽은 값은 **믿지 않는다**. 없을 수 있고(`null`), 깨졌을 수 있고(`SyntaxError`), 모양이 다를 수 있다(옛 버전). 세 경우 모두 기본값으로 안전하게 시작한다.

**실제 예시.** `app.js`의 `load()`를 이렇게 보강할 수 있다.

```js
function load() {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (saved === null) {           // 1. 없음 → 빈 배열로 시작
    entries = [];
    return;
  }
  try {
    const parsed = JSON.parse(saved);          // 2. 깨졌으면 여기서 SyntaxError
    if (Array.isArray(parsed)) {               // 3. 모양 검사: 배열인가? (MDN: "전달된 값이 Array인지 판단")
      entries = parsed;
    } else {
      console.error("저장된 데이터가 배열이 아닙니다. 빈 상태로 시작합니다.", parsed);
      entries = [];
    }
  } catch (error) {
    console.error("저장된 데이터를 읽을 수 없습니다. 빈 상태로 시작합니다.", error);
    entries = [];
  }
}
```

1-7에서 배운 대로 `catch`를 비워 두지 않는다. 최소한 `console.error`로 흔적을 남긴다. 실제 서비스라면 깨진 원본을 다른 키(`"ledger-entries-broken"`)에 옮겨 두고 사용자에게 알리는 것까지 한다.

**왜 중요한가.** 저장 기능의 버그는 **앱 시작 시** 터져서 아무것도 못 하게 만든다. 안전한 `load()` 하나가 "앱이 안 열려요"를 막는다.

### 6. 백업: 내보내기와 가져오기

**한 줄 정의.** `localStorage`는 브라우저 안에만 있으므로, 중요한 기록은 JSON **파일**로 내보내 두고 필요하면 다시 가져온다.

**실제 예시.** 내보내기는 "문자열 → 파일 → 다운로드 링크" 세 단계다. MDN: `Blob` 객체는 "파일류의 불변하는 미가공 데이터를 나타냅니다." `URL.createObjectURL()`은 "주어진 객체를 가리키는 URL을 (...) 반환합니다." `<a>`의 `download` 속성을 쓰면 링크를 열지 않고 내려받는다.

```js
function exportEntries() {
  const text = JSON.stringify(entries, null, 2);                   // 사람이 읽기 좋게
  const blob = new Blob([text], { type: "application/json" });      // 파일 모양으로
  const url = URL.createObjectURL(blob);                            // 그 파일을 가리키는 임시 URL
  const a = document.createElement("a");
  a.href = url;
  a.download = "ledger-" + new Date().toISOString().slice(0, 10) + ".json";
  a.click();                                                        // 다운로드
  URL.revokeObjectURL(url);                                         // 임시 URL 해제 (MDN 권고)
}
```

가져오기는 `<input type="file">`로 파일을 받아 읽은 뒤 `JSON.parse` → 모양 검사 → `entries`에 넣고 `save(); render();`다. 파일 읽기 API는 로드맵 6단계(교육부)에서 다루므로, 지금은 "내보내기"까지만 따라하기 4에서 만든다.

**왜 중요한가.** 브라우저 데이터 삭제 한 번에 몇 달치 가계부가 사라질 수 있다. 백업은 기능이 아니라 보험이다. 그리고 내보낸 JSON 파일은 3과정에서 파이썬 pandas로 바로 읽어 분석할 수 있다.

### 따라하기 2. JSON 깨뜨리고 고치기 (20분)

콘솔에서 순서대로 친다.

```js
JSON.parse('{"a": 1}');            // {a: 1}
JSON.parse("{'a': 1}");            // SyntaxError — 작은따옴표
JSON.parse('{a: 1}');              // SyntaxError — 키에 따옴표 없음
JSON.parse('[1, 2, ]');            // SyntaxError — 후행 쉼표
JSON.parse(null);                  // null (에러는 아니지만 배열도 아니다!)
JSON.stringify({ a: undefined, b: function () {}, c: new Date(0) });
// '{"c":"1970-01-01T00:00:00.000Z"}'  — a, b는 사라지고 c는 문자열
```

이제 Application 탭에서 `ledger-entries` 값의 맨 끝 `]`를 지워 저장(값을 더블클릭해 편집)하고 새로고침한다. 지금 `app.js`의 `load()`는 `try...catch`가 없으므로 콘솔에 빨간 `SyntaxError`가 뜨고 폼이 동작하지 않는다(에러로 아래 코드가 실행되지 않음). 핵심 개념 5의 안전한 `load()`로 바꿔 저장한 뒤 다시 새로고침하면, 콘솔에 `console.error` 메시지가 뜨고 앱은 빈 상태로 **살아서** 열린다. 이것이 방어 코드의 효과다.

## 흔한 실수와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 로컬 서버로 바꿨더니(또는 배포했더니) 내역이 사라짐 | 출처(스킴·도메인·포트)가 달라 서랍이 다름 | 데이터는 안 지워졌다. 같은 출처로 열거나, 내보내기 → 가져오기로 옮긴다 |
| 꺼낸 값이 `"[object Object]"` | `JSON.stringify` 없이 객체를 `setItem` | 저장은 항상 `JSON.stringify(값)`, 읽기는 `JSON.parse` |
| `JSON.parse`에서 `SyntaxError` | 깨진 문자열, 손으로 고친 값, 옛 형식 | `try...catch`로 감싸고 기본값. 원인은 Application 탭에서 값 확인 |
| 앱이 열리자마자 멈춤 | `load()`의 에러가 아래 코드 실행을 막음 | 안전한 `load()`(핵심 개념 5) |
| 삭제했는데 새로고침하면 되살아남 | 삭제 함수에 `save()` 누락 | 데이터를 바꾸는 모든 함수 끝에 `save(); render();` |
| 날짜 비교가 이상함 | `Date` 객체를 저장해 문자열로 돌아옴, 또는 형식이 제각각 | 처음부터 `"YYYY-MM-DD"` 문자열로 통일 |
| 금액 합계가 글자로 이어 붙음 | 금액을 `"9000"` 문자열로 저장 | 저장 전에 `Number()`. 저장된 값의 `typeof` 확인 |
| 다른 기능 데이터까지 지워짐 | `localStorage.clear()` 사용 | 내 키만 `removeItem(키)` |
| 시크릿 창에서 저장이 안 됨 | 브라우저가 용량 0 또는 예외 | `setItem`을 `try...catch`. 사용자에게 안내 |
| 여러 기기에서 같은 데이터가 안 보임 | `localStorage`는 기기·브라우저·출처별 | 정상. 공유하려면 서버(11과정) 또는 내보내기/가져오기 |

## 확인 퀴즈

**1. 가계부를 `http://localhost:8000`에서 쓰다가 `http://localhost:8001`로 서버를 켜서 열었다. 내역이 보일까?**

<details><summary>정답과 해설</summary>
보이지 않는다. 출처는 스킴·도메인·포트로 정해지는데 포트가 다르므로 다른 `localStorage`다. MDN은 프로토콜(http/https)만 달라도 다른 저장소라고 설명한다. 데이터는 8000 출처에 그대로 남아 있다.
</details>

**2. `localStorage.setItem("x", {a: 1})` 뒤에 `JSON.parse(localStorage.getItem("x"))`를 하면 무슨 일이 생기나?**

<details><summary>정답과 해설</summary>
`setItem`은 문자열만 저장하므로 객체가 `"[object Object]"`로 변환되어 저장된다. 이를 `JSON.parse`하면 유효한 JSON이 아니라 `SyntaxError`가 난다. 올바른 순서는 `setItem("x", JSON.stringify({a: 1}))` → `JSON.parse(getItem("x"))`.
</details>

**3. 다음 중 유효한 JSON은? (a) `{'name': '삼성'}` (b) `{"name": "삼성", }` (c) `{"name": "삼성", "qty": 10}` (d) `{"memo": undefined}`**

<details><summary>정답과 해설</summary>
(c)만 유효하다. (a)는 작은따옴표, (b)는 후행 쉼표, (d)는 `undefined`가 JSON에 없다. MDN: "속성의 이름은 반드시 큰따옴표로 표시된 문자열", "후행 쉼표는 허용하지 않습니다", "`undefined` 미지원".
</details>

**4. 매매 복기에 "수익률" 필드를 저장하자는 제안을 받았다. 받아들일까? 근거는?**

<details><summary>정답과 해설</summary>
받아들이지 않는 편이 좋다. 수익률은 매수가·매도가·수량에서 계산할 수 있는 값이므로 저장하면 원본(가격)을 수정했을 때 수익률과 어긋날 위험이 생긴다. "계산할 수 있는 값은 저장하지 않고 그릴 때 계산한다"는 원칙(2-4의 진실의 원본)을 따른다. 단, 계산 비용이 매우 크거나 과거 시점의 값을 고정해야 하는 특별한 경우에는 예외가 있을 수 있다.
</details>

**5. `load()`에서 `try...catch`를 쓰는 것과 `catch`를 비워 두는 것의 차이는?**

<details><summary>정답과 해설</summary>
둘 다 앱이 멈추지는 않지만, 비워 두면 왜 데이터가 비었는지 아무 흔적이 없어 디버깅이 불가능하다(1-7 "에러가 숨음"). 최소한 `console.error`로 에러와 원본을 남기고, 가능하면 깨진 원본을 다른 키에 보관한 뒤 사용자에게 알린다. MDN `JSON.parse`가 `SyntaxError`를 던진다고 명시하므로 그 예외를 **처리**하는 것이지 **무시**하는 것이 아니다.
</details>

## 숙제

1. **가계부에도 안전한 `load()`** — 핵심 개념 5의 코드를 `app.js`에 적용하고, 따라하기 2처럼 일부러 값을 깨뜨려 앱이 살아서 열리는지 확인한다. `console.error` 메시지가 뜨는 것까지 확인.
2. **버전 감싸기** — `app.js`의 저장 형식을 `{ version: 1, entries: [...] }`로 바꾼다. 단, **옛 형식(배열만)으로 저장된 데이터도 읽을 수 있어야 한다**: `load()`에서 `Array.isArray(parsed)`이면 옛 형식으로 보고 그대로 쓰고, 객체이고 `parsed.version === 1`이면 `parsed.entries`를 쓴다. 바꾸기 전 데이터로 테스트해 사라지지 않는지 본다.
3. **가계부 내보내기** — 따라하기 4(a)의 버튼을 가계부 재무부 화면에도 단다. 내려받은 파일을 다시 VS Code로 열어 `type`이 전부 `"expense"` 또는 `"income"`인지 눈으로 검사한다.
4. **두 탭 실험** — 가계부를 두 탭에 열고 한쪽에서 내역을 추가한 뒤 다른 쪽을 보라. 바뀌지 않는다. 왜인지 적고(각 탭의 `entries` 배열은 메모리에 따로 있다), MDN의 `storage` 이벤트 설명을 읽고 "다른 탭에서 바뀌면 다시 `load(); render();`"를 하는 코드를 시도해 본다. 이벤트는 "the event is not fired on the window that made the change"라는 점에 유의.
