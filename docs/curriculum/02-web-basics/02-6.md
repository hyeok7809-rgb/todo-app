|---|---|
| 예상 시간 | 4시간 |

## 이 단원을 마치면

- "비동기"가 왜 필요한지(기다리는 동안 화면이 멈추면 안 되니까)를 설명하고, 코드가 적힌 순서와 실행되는 순서가 다른 경우를 읽을 수 있다.
- Promise의 세 상태(대기·이행·거부)를 알고, `.then`/`.catch`와 `async`/`await` + `try...catch` 두 가지 표기를 서로 바꿔 쓸 수 있다.
- `fetch()`로 JSON을 받아 화면에 그리고, `response.ok`를 확인하며, 네트워크 오류와 HTTP 오류를 구분해 처리할 수 있다.
- CORS가 무엇인지, `file://`로 열면 왜 막히는지, "내가 고칠 수 있는 것과 없는 것"을 구분할 수 있다.
- 키 없이 쓸 수 있는 공개 API(GitHub REST API)를 브라우저에서 직접 호출해 데이터를 받아 본다.
- 로딩 중·성공·실패 세 상태를 화면에 표시하는 패턴을 만들 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

지금까지 가계부는 내 브라우저 안에서만 살았다. 이 단원부터 **바깥 세상**과 연결된다. 2-1에서 그린 "클라이언트가 요청하고 서버가 응답한다"를 JS 코드로 직접 하는 것이 `fetch`이고, 4과정의 공공데이터·증권사 API, 10과정의 Claude API, 11과정의 AI 직원실이 전부 `fetch`(또는 파이썬의 `requests`) 위에 있다.

주식 비유로는 **시세 조회**다. MTS에서 종목을 검색하면 화면이 잠깐 "불러오는 중"이 됐다가 호가가 뜬다. 그 사이 앱은 멈추지 않고 다른 버튼이 눌린다. 이것이 비동기다. 그리고 가끔 "일시적인 오류입니다"가 뜬다. 이것이 오류 처리다. 요청을 보내고, 기다리는 동안 다른 일을 하고, 응답이 오면 그리고, 실패하면 알린다. 이 네 박자가 이 단원의 전부다.

비동기는 초보자가 가장 많이 헤매는 주제다. 콘솔에 찍히는 순서가 코드 순서와 달라서다. 하지만 클로드가 써 주는 네트워크 코드는 거의 전부 `async`/`await`라서, 이걸 못 읽으면 API 연동 코드를 검증할 수 없다. 이 단원에서 "왜 순서가 다른지"를 실험으로 몸에 익히자.

## 핵심 개념

### 1. 비동기: 기다리는 동안 멈추지 않기

**한 줄 정의.** 동기(synchronous) 코드는 한 줄이 끝나야 다음 줄로 가고, 비동기(asynchronous) 코드는 오래 걸리는 일을 **시작만 해 두고** 다음 줄로 간다. MDN '비동기 JavaScript 소개': "비동기 프로그래밍은 작업이 완료될 때까지 기다리지 않고 잠재적으로 오래 실행되는 작업을 시작하여 해당 작업이 실행되는 동안에도 다른 이벤트에 응답할 수 있게 하는 기술입니다."

**비유.** 음식점 주문. 동기는 주문한 뒤 카운터 앞에 서서 음식이 나올 때까지 아무것도 안 하는 것. 비동기는 진동벨을 받아 자리에 앉아 있다가 울리면 가지러 가는 것. 네트워크 요청은 수백 밀리초에서 수 초가 걸리므로, 동기로 기다리면 그동안 화면이 얼어붙는다. MDN의 소수 계산 예제 설명처럼 "프로그램이 완전히 응답하지 않는 것을 확인할 수 있을 겁니다. 아무것도 입력할 수 없고 클릭도 안될 것"이 된다.

**실제 예시.** 1-7에서 본 `setTimeout`이 가장 작은 비동기다. 우리 `showXpPop()`:

```js
document.body.appendChild(pop);          // 1
setTimeout(function () {                 // 2: "1초 뒤에 이걸 실행해 줘"라고 예약만 하고
  pop.remove();                          // 4: 1초 뒤에 실행
}, 1000);
console.log("예약 끝");                   // 3: 즉시 실행
```

콘솔에는 "예약 끝"이 먼저 찍히고 1초 뒤 팝업이 사라진다. 코드는 위에서 아래지만, 실행은 1 → 2(예약) → 3 → 4다. `fetch`도 똑같다. "요청을 보내 줘"라고 시작만 하고 다음 줄로 간다. 응답이 오면 그때 **미리 맡겨 둔 함수**가 실행된다.

**왜 중요한가.** "`fetch` 다음 줄에서 데이터를 썼는데 `undefined`예요"가 비동기를 모를 때 나는 1번 질문이다. 다음 줄이 실행될 때 응답은 아직 안 왔다. 응답이 온 **뒤에** 실행될 자리에 코드를 둬야 하고, 그 자리를 만드는 도구가 Promise다.

### 2. Promise: "나중에 결과를 줄게"라는 약속 객체

**한 줄 정의.** MDN `Promise`: "`Promise` 객체는 비동기 작업이 맞이할 미래의 완료 또는 실패와 그 결과 값을 나타냅니다." 상태는 셋이다. "대기(pending): 이행하지도, 거부하지도 않은 초기 상태", 이행(fulfilled): 성공해서 값이 있음, 거부(rejected): 실패해서 이유가 있음.

**비유.** 진동벨. 받는 순간은 대기 상태. 음식이 나오면 울린다(이행, 결과는 음식). 재료가 떨어졌으면 직원이 와서 말한다(거부, 이유는 "품절"). 벨에 "울리면 이렇게 해"(`.then`), "문제 생기면 이렇게 해"(`.catch`)를 미리 적어 둔다.

**실제 예시.** `.then` 표기.

```js
fetch("https://api.github.com/repos/mdn/content")   // Promise<Response> (대기 상태)
  .then(function (response) {                        // 이행되면: 응답 객체를 받는다
    return response.json();                          // 본문 파싱도 Promise → 다음 then으로
  })
  .then(function (data) {
    console.log(data.stargazers_count);              // 파싱된 객체
  })
  .catch(function (error) {                          // 어느 단계든 거부되면 여기로
    console.error("실패:", error);
  });
```

MDN '프로미스 사용하기': "`then()` 함수는 새로운 promise를 반환합니다. 처음에 만들었던 promise와는 다른 새로운 promise입니다." 그래서 `.then`을 사슬처럼 이을 수 있고, 예전 방식의 "지옥의 콜백 피라미드"(콜백 안의 콜백 안의 콜백)를 평평하게 편다. `.catch(실패콜백)`은 "`then(null, failureCallback)`의 축약"이며, "promise chain은 예외가 발생하면 멈추고 chain의 아래에서 catch를 찾습니다." 중간 어디서 터져도 마지막 `catch` 하나가 받는다.

**왜 중요한가.** `.then` 표기는 오래된 코드와 라이브러리 문서에 많다. 직접 쓰는 일은 줄겠지만 읽을 줄은 알아야 한다. 그리고 다음의 `async`/`await`가 결국 이 Promise를 예쁘게 쓰는 문법일 뿐이라는 것을 알면 둘을 자유롭게 오갈 수 있다.

### 3. `async`/`await`: Promise를 동기 코드처럼 쓰기

**한 줄 정의.** `async` 함수 안에서 `await 프로미스`라고 쓰면, 그 Promise가 끝날 때까지 **그 함수만** 멈췄다가 결과 값을 돌려준다. MDN `await`: "`await` 연산자는 Promise가 이행될 때까지 이행된 값을 반환받는 데 사용됩니다. 이 연산자는 비동기 함수 내부나 모듈 최상단 부분에서만 사용할 수 있습니다." MDN `async function`: "`async` 함수는 항상 promise를 반환합니다."

**비유.** 진동벨을 들고 "울릴 때까지 **이 심부름만** 잠깐 멈출게"라고 하는 것. 가게 전체(다른 이벤트, 애니메이션)는 계속 돌아간다.

**실제 예시.** 위 코드를 다시 쓰면.

```js
async function loadStars() {
  try {
    const response = await fetch("https://api.github.com/repos/mdn/content"); // 응답 올 때까지 이 함수만 대기
    if (!response.ok) {                                                       // HTTP 오류 검사 (핵심 개념 4)
      throw new Error("HTTP 오류: " + response.status);
    }
    const data = await response.json();                                       // 파싱 끝날 때까지 대기
    console.log(data.stargazers_count);
  } catch (error) {                                                           // 네트워크 오류 + 위의 throw
    console.error("실패:", error);
  }
}

loadStars();                 // 호출은 즉시 돌아온다(Promise). 안의 코드는 나중에 진행
console.log("다음 줄");       // 이게 먼저 찍힌다
```

규칙 세 개. (1) `await`는 `async` 함수 안에서만. (2) `async` 함수는 호출하면 **즉시** Promise를 돌려주고 안은 나중에 진행된다. 그래서 `loadStars()`의 결과를 바깥에서 바로 쓸 수 없다. (3) 실패는 `try...catch`로 받는다. MDN이 "비동기 코드를 사용한 이러한 대칭성"이라 부르는, 1-7에서 배운 `try...catch`와 같은 모양이다.

MDN이 꼽는 가장 흔한 실수: "이러한 문법의 가장 흔한 실수는 `await` 키워드를 빼먹는 것입니다." `const data = response.json();`처럼 `await`를 빼면 `data`는 객체가 아니라 **Promise**이고, `data.stargazers_count`는 `undefined`다.

**왜 중요한가.** 클로드가 써 주는 API 코드의 표준 형태다. "`async function`, `await fetch`, `if (!response.ok) throw`, `await response.json()`, `try...catch`" 다섯 줄 뼈대를 외워 두면 어떤 API 코드든 읽힌다.

### 4. `fetch()`와 `Response`: 요청 보내고 응답 읽기

**한 줄 정의.** MDN `fetch()`: "전역 `fetch()` 메서드는 네트워크에서 리소스를 취득하는 절차를 시작하고, 응답이 사용 가능해지면 이행하는 프로미스를 반환합니다. 프로미스는 요청에 대한 응답을 나타내는 Response 객체로 이행합니다."

**비유.** 2-1의 주문서와 영수증. `fetch(URL, 옵션)`이 주문서, `Response`가 영수증(상태 코드 + 본문).

**실제 예시.** `Response`에서 자주 보는 세 가지.

| 속성/메서드 | MDN 설명 | 쓰임 |
|---|---|---|
| `response.ok` | "응답이 성공했는지 여부(200-299 범위의 상태)를 나타내는 불리언" | 성공 검사. 2-1의 상태 코드 그룹 |
| `response.status` | "the HTTP status code of the response. For example, `200` for success or `404`"(영어판) | 오류 메시지에 숫자 포함 |
| `response.json()` | "본문 텍스트를 JSON으로 파싱한 결과와 함께 이행하는 프로미스를 반환합니다." | JSON 본문 → 객체. **Promise라서 `await` 필요** |

`response.json()` 문서의 주의: "메서드 이름은 `json()`임에도 불구하고, 결과는 JSON이 아니라 JSON을 입력으로 받아 파싱하여 JavaScript 객체를 생성한 결과". 즉 2-5의 `JSON.parse`를 대신해 주는 것이다. 본문이 JSON이 아니면(HTML 오류 페이지 등) 여기서 거부된다.

**가장 중요한 함정: `fetch`는 404에 실패하지 않는다.** MDN `fetch()`: "`fetch()` 프로미스는 네트워크 오류(보통 권한 문제 등)가 있을 때만 거부되며, `404` 등의 HTTP 오류 시에는 **거부되지 않습니다**. 그러므로 `then()` 처리기는 반드시 `Response.ok` 또는 `Response.status` 속성을 확인해야 합니다." 'Fetch API 사용하기': "`fetch()` 프로미스는 네트워크에 오류가 있었거나, 서버의 CORS 설정이 잘못된 경우 `TypeError`로 거부됩니다. (...) 404와 같은 응답은 네트워크 오류가 아니므로 거부하지 않습니다."

| 상황 | Promise 상태 | `response.ok` | 잡는 곳 |
|---|---|---|---|
| 와이파이 끊김, 주소의 도메인이 없음, CORS 차단 | 거부 (`TypeError`) | — | `catch` |
| 서버가 404/500을 돌려줌 | **이행** | `false` | `if (!response.ok) throw` |
| 서버가 200을 돌려줌 | 이행 | `true` | 정상 흐름 |

그래서 MDN '네트워크 요청' 튜토리얼의 예제도 이 모양이다.

```js
if (!response.ok) {
  throw new Error(`HTTP error: ${response.status}`);
}
```

**데이터 보내기(POST).** 'Fetch API 사용하기'의 예를 그대로 옮긴다. 가계부 내역을 (가상의) 서버에 보낸다고 치자.

```js
const response = await fetch("https://example.com/api/entries", {   // example.com은 문서용 가짜 도메인
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(entry),                                         // 2-5의 직렬화
});
```

MDN: 본문의 데이터 형식은 "반드시 'Content-Type' 헤더와 일치해야 함". 4-1에서 메서드·헤더를 본격적으로 다룬다.

**왜 중요한가.** "응답이 왔는데 화면이 안 바뀌어요"의 절반은 `response.ok`를 안 보고 404 본문(HTML)을 `json()`하다 터진 것이고, 나머지 절반은 `await`를 빼먹은 것이다. 이 표 하나로 둘 다 잡는다.

### 5. CORS와 같은 출처 정책: 브라우저가 막는 이유

**한 줄 정의.** 브라우저는 보안상 **스크립트가 다른 출처로 보내는 요청**을 기본적으로 제한하고, 서버가 "허락한다"는 헤더를 보내야 통과시킨다. MDN 'CORS': "교차 출처 리소스 공유(CORS)는 브라우저가 자신의 출처가 아닌 다른 어떤 출처(도메인, 스킴 혹은 포트)로부터 자원을 로딩하는 것을 허용하도록 서버가 허가 해주는 HTTP 헤더 기반 메커니즘입니다." "보안상의 이유로 브라우저는 스크립트에서 시작한 교차 출처 HTTP 요청을 제한합니다. 예를 들어, `fetch()`와 `XMLHttpRequest`는 동일 출처 정책을 따릅니다."

**비유.** 다른 증권사 계좌 조회. 내가 A증권 앱에서 B증권 잔고를 바로 볼 수 없다. B증권이 "A앱에 공개해도 된다"고 허락(헤더)해야 한다. 출처의 정의는 2-5의 `localStorage`와 같다(스킴 + 도메인 + 포트).

**실제 예시.** 세 경우.

1. `http://localhost:8000`의 페이지가 `http://localhost:8000/data/watchlist.json`을 부른다 → **같은 출처**, 항상 된다.
2. `http://localhost:8000`의 페이지가 `https://api.github.com/...`을 부른다 → **다른 출처**. GitHub가 허락 헤더(`Access-Control-Allow-Origin: *`)를 보내므로 된다. GitHub 문서: "The REST API supports cross-origin resource sharing (CORS) for AJAX requests from any origin."
3. 어떤 사이트의 HTML을 `fetch`로 긁어온다 → 그 사이트가 허락하지 않으면 콘솔에 CORS 오류가 뜨고 Promise가 `TypeError`로 거부된다. **내 코드로는 못 고친다.** 서버 쪽 설정이기 때문이다.

그리고 `file://`로 연 페이지는 출처 자체가 특수해서(2-5의 "유효하지 않은 튜플") `fetch`가 같은 폴더의 JSON조차 막히는 경우가 많다. 2-1부터 로컬 서버를 쓰라고 한 가장 실질적인 이유가 이것이다.

**왜 중요한가.** CORS 오류를 보고 "내 코드가 틀렸나" 하며 몇 시간을 쓰는 일이 흔하다. 결론은 둘 중 하나다. (a) 그 API가 브라우저 직접 호출을 허락하는가 확인하고, (b) 허락하지 않으면 **내 서버**(파이썬, 11과정)에서 대신 호출한다. 증권사 API 대부분이 (b)이고, 그래서 4과정은 파이썬으로 간다.

### 6. 화면 패턴: 로딩 중 · 성공 · 실패

**한 줄 정의.** 네트워크 요청이 있는 화면은 항상 세 상태를 가진다. 요청 전/중(로딩), 성공(데이터 표시), 실패(오류 메시지 + 재시도). 2-4의 "데이터가 바뀌면 다시 그린다"에 **상태**를 하나 더한 것이다.

**실제 예시.** 데이터 하나와 상태 하나를 두고 `render`가 상태를 본다.

```js
let stars = null;          // 데이터
let status = "idle";       // "idle" | "loading" | "success" | "error"
let errorMessage = "";

async function loadStars() {
  status = "loading"; render();
  try {
    const response = await fetch("https://api.github.com/repos/mdn/content");
    if (!response.ok) throw new Error("HTTP " + response.status);
    const data = await response.json();
    stars = data.stargazers_count;
    status = "success";
  } catch (error) {
    errorMessage = error.message;
    status = "error";
  }
  render();                 // 성공이든 실패든 마지막에 한 번
}

function render() {
  const box = document.getElementById("stars-box");
  if (status === "loading") { box.textContent = "불러오는 중..."; return; }
  if (status === "error")   { box.textContent = "실패: " + errorMessage + " (다시 시도)"; return; }
  if (status === "success") { box.textContent = "⭐ " + stars.toLocaleString("ko-KR"); return; }
  box.textContent = "";
}
```

**왜 중요한가.** 사용자(와 나)는 "지금 기다리는 중인지, 실패한 건지"를 알아야 한다. 로딩 표시가 없으면 버튼을 다섯 번 누르고(요청 5번), 실패 표시가 없으면 빈 화면을 버그로 오해한다. 13과정에서 앱을 팔 때 이 세 상태를 빠뜨리면 바로 환불 요청이 온다.

### 따라하기 1. 콘솔에서 실행 순서 체험하기 (30분)

콘솔에 한 덩어리씩 붙여 넣고 찍히는 **순서**를 예측한 뒤 확인한다.

```js
// (a) setTimeout: 0ms여도 나중
console.log("A");
setTimeout(() => console.log("B (0ms 타이머)"), 0);
console.log("C");
// 예측: A, C, B
```

```js

bell.then((msg) => console.log("then:", msg));
console.log("자리에 앉아 기다리는 중");
// 2초 뒤 then이 찍힌다
```

```js
// (c) async/await: 콘솔에서도 async 함수를 정의해 쓸 수 있다
async function wait(ms) {
  await new Promise((resolve) => setTimeout(resolve, ms));
  return ms + "ms 지남";
}
async function run() {
  console.log("시작");
  const r = await wait(1000);
  console.log(r);
  console.log("끝");
}
run();
console.log("run() 호출 직후");   // "시작" 다음, "1000ms 지남" 전에 찍힌다
```

```js
// (d) await 빼먹기 실험
async function bad() {
  const r = wait(500);        // await 없음
  console.log(r);             // Promise {<pending>} — 값이 아니다!
}
bad();
```

(d)에서 `Promise {<pending>}`이 보이면 성공이다. 앞으로 콘솔에 이게 보이면 "어딘가 `await`를 빼먹었다"고 바로 알아차리게 된다.

  { "code": "000660", "name": "SK하이닉스", "sector": "반도체", "note": "거래량 급증 시 체크" },

async function loadWatchlist() {
  const ul = document.getElementById("watch-list");
  ul.textContent = "불러오는 중...";
  try {
    const response = await fetch("data/watchlist.json");       // 같은 출처: 상대 경로

### 따라하기 3. 공개 API 호출: GitHub REST API (40분)

키 없이 브라우저에서 바로 부를 수 있는 API로 GitHub REST API를 쓴다. 공식 문서 기준: 기본 주소는 `https://api.github.com`, 저장소 하나를 조회하는 엔드포인트는 `GET /repos/{owner}/{repo}`("Get a repository"), 응답에 `stargazers_count`(별 개수) 필드가 있다. 인증 없는 요청의 기본 한도는 "60 requests per hour"(IP 기준)이고, CORS를 허용한다.

const r = await fetch("https://api.github.com/repos/mdn/content");   // 콘솔은 최상위 await 허용
r.status;            // 200
r.ok;                // true
const data = await r.json();

### 따라하기 4. 클로드에게 API 연동을 시키고 다섯 줄 뼈대로 검증 (30분)

Claude Code에 요청한다.

```
@trade.js 의 loadWatchlist 를 개선해 줘.
(1) "새로고침" 버튼을 누르면 다시 불러오고, 불러오는 동안 버튼을 disabled로
(2) 실패하면 오류 메시지와 "다시 시도" 버튼을 보여 줄 것
(3) fetch 결과는 반드시 response.ok 를 확인하고, 실패는 try...catch 로 받을 것
(4) await 를 빼먹은 곳이 없는지 스스로 점검한 결과를 답에 포함할 것
```

결과를 받으면 핵심 개념 3의 다섯 줄 뼈대(`async function` / `await fetch` / `if (!response.ok) throw` / `await response.json()` / `try...catch`)가 전부 있는지 체크한다. 하나라도 빠졌으면 어떤 상황에서 문제가 되는지(핵심 개념 4의 표) 말하며 되돌려 보낸다. 그리고 따라하기 2의 실험 (2)·(3)을 다시 돌려 두 오류가 모두 화면에 표시되는지 확인한다.

## 흔한 실수와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `fetch` 다음 줄에서 데이터가 `undefined` | 응답이 오기 전에 다음 줄이 실행됨 | 데이터를 쓰는 코드를 `await` 뒤 또는 `.then` 안으로 |
| 콘솔에 `Promise {<pending>}` | `await` 누락 | MDN이 꼽은 가장 흔한 실수. `await` 추가 |
| `await is only valid in async functions` | `async`가 아닌 함수 안에서 `await` | 함수 앞에 `async` |
| 404인데 `catch`로 안 들어옴 | `fetch`는 HTTP 오류에 거부되지 않음 | `if (!response.ok) throw new Error(...)` |
| `Unexpected token '<'` in JSON | 404/500 페이지(HTML)를 `json()`함 | 먼저 `response.ok` 검사. 네트워크 탭에서 응답 본문 확인 |
| 콘솔에 CORS 오류, `TypeError: Failed to fetch` | 다른 출처 서버가 허락 헤더를 안 보냄, 또는 `file://`로 염 | 로컬 서버로 열기. 서버가 CORS 미허용이면 내 서버(파이썬)에서 대신 호출 |
| 버튼을 여러 번 누르면 요청이 여러 번 나감 | 로딩 상태를 안 둠 | `status === "loading"`이면 무시하거나 버튼 `disabled` |
| 403과 함께 "rate limit" 메시지 | 한도 초과(GitHub 비인증 60/시간) | 반복문에서 호출 금지. 결과를 변수에 저장해 재사용 |
| 성공했는데 화면이 그대로 | 데이터만 바꾸고 `render()`를 안 부름 | 2-4 패턴: `try`/`catch` 끝에서 `render()` |
| `async` 함수의 반환값을 받았는데 Promise | `async` 함수는 항상 Promise 반환 | 호출하는 쪽도 `await` (그러려면 그쪽도 `async`) |

## 확인 퀴즈

**1. 다음 코드의 콘솔 출력 순서는?**

```js
console.log(1);
setTimeout(() => console.log(2), 0);
fetch("data/watchlist.json").then(() => console.log(3));
console.log(4);
```

<details><summary>정답과 해설</summary>
1, 4가 먼저 찍히고, 그 뒤 2와 3이 찍힌다(2와 3의 순서는 타이머와 네트워크 응답 시점에 따라 달라질 수 있으며 보통 2가 먼저다). `setTimeout`과 `fetch`는 시작만 해 두고 다음 줄로 넘어가는 비동기 작업이기 때문이다.
</details>

**2. `fetch`가 거부(reject)되는 경우와 이행(fulfill)되지만 `response.ok`가 `false`인 경우를 각각 하나씩 들라.**

<details><summary>정답과 해설</summary>
거부: 네트워크 오류(오프라인, 존재하지 않는 도메인), 서버의 CORS 미허용. MDN: "네트워크 오류(보통 권한 문제 등)가 있을 때만 거부". 이행+`ok: false`: 서버가 404나 500을 돌려준 경우. "`404` 등의 HTTP 오류 시에는 거부되지 않습니다." 그래서 반드시 `response.ok`를 확인한다.
</details>

**3. `const data = response.json();`에서 빠진 것은 무엇이고, 이대로 두면 `data.name`은 무엇이 되나?**

<details><summary>정답과 해설</summary>
`await`가 빠졌다. `response.json()`은 "JSON으로 파싱한 결과와 함께 이행하는 프로미스를 반환"하므로 `data`는 Promise 객체이고 `data.name`은 `undefined`다. `const data = await response.json();`으로 고친다.
</details>

**4. `http://localhost:8000`의 페이지에서 어떤 증권사 사이트의 시세 페이지를 `fetch`했더니 CORS 오류가 났다. 내 코드를 고쳐서 해결할 수 있나?**

<details><summary>정답과 해설</summary>
없다. CORS는 "서버가 허가 해주는 HTTP 헤더 기반 메커니즘"이라 허락 여부를 서버가 정한다. 해결은 (a) 그 서비스가 제공하는 공식 API(허락 헤더가 있거나 서버 간 호출용)를 쓰거나, (b) 내 서버(파이썬 스크립트 등)에서 대신 요청해 내 페이지에 전달하는 것이다. 4과정의 KIS API가 (b)의 길이다.
</details>

**5. 로딩·성공·실패 세 상태를 두지 않으면 생기는 문제를 두 가지 말하라.**

<details><summary>정답과 해설</summary>
(1) 기다리는 동안 아무 표시가 없어 사용자가 버튼을 반복해 눌러 요청이 여러 번 나간다(한도 소진, 중복 데이터). (2) 실패했을 때 빈 화면만 남아 버그인지 네트워크 문제인지 알 수 없고 재시도 길도 없다. 그래서 `status` 변수를 두고 `render()`가 상태에 따라 그린다.
</details>

## 숙제

1. **`.then`으로 바꿔 쓰기** — 따라하기 2의 `loadWatchlist`를 `async`/`await` 없이 `.then`/`.catch` 사슬로 다시 쓰고, 둘 중 어느 쪽이 읽기 쉬운지 이유와 함께 적는다. 동작은 같아야 한다.
2. **중복 요청 막기** — 따라하기 3의 위젯에 "새로고침" 버튼을 달되, 로딩 중에는 다시 눌러도 요청이 나가지 않게 한다. 네트워크 탭에서 연타해도 요청이 한 번만 나가는 것을 확인한다.
3. **JSONPlaceholder로 POST 연습** — JSONPlaceholder 공식 사이트에서 글(post)을 만드는 경로를 확인한 뒤, 핵심 개념 4의 POST 예제 형태로 매매 복기 한 건을 보내 보고 응답의 상태 코드와 본문을 콘솔에 찍는다. 실제로 저장되지 않는 연습용 서버라는 점을 확인한다.
4. **4과정 예고 조사** — 공공데이터포털과 한국투자증권 Open API 포털에 접속해 "API 키를 어떻게 발급받는지", "브라우저에서 직접 호출할 수 있는지(CORS)"를 공식 안내에서 찾아 세 줄로 메모한다. 못 찾으면 "못 찾음"이라고 적는다. 4-2에서 키 보관법, 4-3에서 실제 호출을 다룬다.
