# 9-6. 설정 파일과 권한 관리: settings.json, 허용 목록, 안전하게 쓰기

| 과정 | 9. Claude Code 심화 |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 9-5 |
| 경험치 | 60 |

## 이 단원을 마치면

- 설정 파일 네 종류(사용자, 프로젝트 공유, 프로젝트 로컬, 관리형)의 위치와 **우선순위**를 말할 수 있고, "이 설정은 어디에 넣나"를 판단한다.
- `permissions.allow / ask / deny` 규칙을 JSON으로 직접 쓰고, `.env` 읽기 금지 같은 보호를 **파일로** 고정할 수 있다.
- 설정이 안 먹을 때 `/status`로 어느 파일이 읽혔는지 확인하고 원인을 찾는다.
- 지금까지 배운 안전장치(권한 모드·규칙·훅·샌드박스·신뢰)를 한 표로 정리해 **내 기본 설정**을 완성한다.

## 왜 배우나 (나에게 어떤 쓸모)

8·9과정에서 "설정에 넣으면 된다"가 여러 번 나왔다(권한 규칙, 훅, 기본 모드, MCP). 이 단원은 그 설정 파일들을 한 번에 정리하고, **저장소에 커밋해서 어디서 열어도 같은 안전장치**가 따라오게 만든다. 9과정의 마무리이자, 10과정에서 API 키를 만들기 전에 "키를 읽지 못하게 하는 설정"을 먼저 깔아 두는 단계다.

## 핵심 개념

(공식 settings 문서, 확인일 2026-10-21.)

### 1. 네 개의 파일

| 범위 | 파일 | 누구에게 | 용도 |
|---|---|---|---|
| 사용자 | `~/.claude/settings.json` | 이 컴퓨터의 나, 모든 프로젝트 | 테마, 기본 모델, 내 권한 규칙 |
| 프로젝트 공유 | `.claude/settings.json` | 이 폴더에서 일하는 모두. **커밋** | 팀 권한, 훅, 플러그인, 필요한 환경변수 |
| 프로젝트 로컬 | `.claude/settings.local.json` | 나, 이 프로젝트만. git 제외 | 개인 예외, 시험용 |
| 관리형 | `managed-settings.json` 등 | 조직이 배포 | 보안 정책(개인은 해당 없음) |

Windows에서 `~/.claude`는 `%USERPROFILE%\.claude`. 설치해도 파일이 자동으로 생기지 않는다. `/config`에서 테마 등을 바꾸면 사용자 파일이, 권한 프롬프트에서 "Yes, and don't ask again"을 고르면 **로컬 파일**에 allow 규칙이 생긴다(Claude Code가 global git excludes에 자동 추가).

`~/.claude.json`은 Claude Code가 스스로 쓰는 다섯 번째 파일(로그인, MCP 서버, 프로젝트별 신뢰 상태). 직접 편집하지 않는다.

### 2. 우선순위

높은 것이 이긴다: **관리형 > 명령줄 `--settings` > 프로젝트 로컬 > 프로젝트 공유 > 사용자**. 단 **리스트 키(`permissions.allow` 등)는 덮어쓰지 않고 합쳐진다.** 환경변수는 이 사다리 밖에서 키별로 정해진다(`ANTHROPIC_MODEL`은 파일의 `model`보다 우선). 보안 관련 몇 키는 **더 엄격한 값**이 낮은 범위에서도 이긴다.

한 세션만 시험: `claude --settings '{"model": "claude-opus-5-5"}'`. 저장되지 않는다.

### 3. 권한 규칙 쓰기

공식 예시:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

- 형식: `도구(패턴)`. `Bash(git commit *)`, `Read(./.env)`, `Edit(docs/**)`처럼.
- `deny`와 `ask`는 즉시 적용, 프로젝트 파일의 `allow`는 **폴더를 신뢰한 뒤** 적용(남이 커밋한 허용이 바로 먹지 않게).
- `permissions.defaultMode`로 시작 모드(8-4). 단 `auto`·`bypassPermissions`는 프로젝트 파일에서 안 먹고 사용자·관리형에서만.
- `$schema` 줄을 넣으면 VS Code가 자동완성·검증을 해 준다. JSON은 **주석·끝 쉼표 금지**.
- 저장하면 실행 중인 세션에도 대부분 바로 적용된다(`permissions`, `hooks` 포함). `model`은 `/model`로.

### 4. 안 먹을 때

1. `/status` → "Setting sources"에 그 파일이 있나?
2. 더 높은 범위가 같은 키를 덮나?
3. 그 키가 그 파일에서 허용되는 키인가?(위 `auto` 예)
4. JSON이 깨졌나? → 시작 시 "Settings Error" 대화상자, `claude doctor`.
5. `allow`가 신뢰 대기 중인가?

### 5. 안전장치 한 표

| 장치 | 성격 | 어디에 | 배운 곳 |
|---|---|---|---|
| 권한 모드 | 얼마나 묻나 | `defaultMode`, Shift+Tab | 8-4 |
| 권한 규칙 | 무엇을 허용/질문/거부 | `permissions` | 9-6 |
| 훅 | 결정적 차단·검사 | `hooks` | 9-3 |
| 샌드박스 | OS 수준 격리 | `/sandbox` | 8-4 |
| 폴더 신뢰 | 남의 설정 즉시 적용 방지 | 첫 실행 대화상자 | 0-4 |
| CLAUDE.md | 권고 | 저장소 | 8-3 |
| MCP 범위·도구 deny | 외부 도구 제한 | `.mcp.json`, `permissions` | 9-4 |
| 클라우드 환경 | 네트워크·변수 제한 | 환경 설정 | 9-5 |

**우리 프로젝트의 기본 설정**(이 단원 따라하기에서 완성): deny에 `.env` 읽기, `git push --force`, `rm -rf`; allow에 `node -e *`, `git status`, `git diff *`, `git log *`; hooks에 9-3의 세 훅; `defaultMode`는 공부 중엔 `plan` 또는 `default`.

## 따라하기

### 1. 지금 상태 보기 (15분)

`/status`로 읽힌 설정 파일 목록. 각 파일을 열어 무엇이 들어 있는지 읽는다(9-5 숙제 3). "Yes, and don't ask again"으로 쌓인 allow 규칙이 로컬 파일에 있는지 확인.

### 2. 프로젝트 공유 설정 만들기 (50분)

`.claude/settings.json`을 만들어 5절의 "기본 설정"을 적는다. `$schema` 포함. 저장 후 `/status`에 "Project settings"가 보이는지, "`.env` 보여 줘"가 거부되는지, `node -e "1+1"`이 묻지 않고 되는지 확인. **커밋**한다. 이로써 웹·데스크톱·다른 컴퓨터에서도 같은 보호가 적용된다(폴더 신뢰 후).

### 3. 로컬 예외 (15분)

`.claude/settings.local.json`에 나만의 예외 하나(예: `"model": "claude-sonnet-5-5"`)를 넣고, 공유 파일보다 우선하는지 확인. `.gitignore`에 들어 있는지(자동 추가됐는지) 확인.

### 4. 깨뜨리고 고치기 (20분)

공유 파일에 일부러 끝 쉼표를 넣고 `claude`를 다시 열어 Settings Error 대화상자를 본다. 고친 뒤 `claude doctor`로 깨끗한지.

### 5. 안전장치 표 완성 (20분)

5절의 표를 내 설정 기준으로 채워 `docs/safety.md`에 저장. 8-4 숙제 2의 금지 명령 5개가 **규칙과 훅 둘 다**에 있는지 대조.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| JSON에 주석·끝 쉼표 | Settings Error | 제거, `$schema`로 검증 |
| 프로젝트 파일에 `auto` 모드 | 무시됨 | 사용자 파일 또는 플래그 |
| allow가 안 먹음 | 계속 물어봄 | 폴더 신뢰, 상위 범위의 ask 규칙 확인 |
| 로컬 파일 커밋 | 개인 설정 공유 | `.gitignore` |
| 비밀 경로를 deny 안 함 | AI가 .env 읽음 | `Read(./.env*)` deny + 훅 |
| 환경변수와 파일이 충돌 | 엉뚱한 모델 | 변수 제거 또는 키별 우선순위 확인 |

## 확인 퀴즈

**1. 네 설정 파일의 우선순위를 높은 순으로.**

<details><summary>정답과 해설</summary>
관리형 > 명령줄 `--settings` > 프로젝트 로컬 > 프로젝트 공유 > 사용자. 리스트 키는 합쳐진다.
</details>

**2. "이 저장소를 여는 누구든 `.env`를 못 읽게" 하려면 어느 파일에 무엇을?**

<details><summary>정답과 해설</summary>
`.claude/settings.json`(커밋)의 `permissions.deny`에 `Read(./.env)`, `Read(./.env.*)`. deny는 신뢰 전에도 즉시 적용.
</details>

**3. 프로젝트 파일의 `allow` 규칙이 바로 적용되지 않는 이유.**

<details><summary>정답과 해설</summary>
폴더 신뢰 전에는 남이 커밋한 허용이 내 컴퓨터에서 바로 먹지 않게 보호한다. 신뢰 후 적용.
</details>

**4. 설정이 안 먹을 때 첫 명령.**

<details><summary>정답과 해설</summary>
`/status`. Setting sources에 파일이 읽혔는지 본다. 없으면 경로·JSON 오류, 있으면 우선순위·허용 키 확인.
</details>

**5. `permissions.allow`를 사용자 파일과 프로젝트 파일에 둘 다 적으면?**

<details><summary>정답과 해설</summary>
합쳐진다(리스트 키는 덮어쓰지 않음). 단 다른 파일의 ask 규칙이 allow보다 우선할 수 있다.
</details>
