# 12-4. 유지보수: 에러 모니터링, 백업, 버전 관리, 업데이트 습관

| 과정 | 12. 바이브 코딩 실전과 배포 |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 12-3 |
| 경험치 | 60 |

## 이 단원을 마치면

- "만들기"와 "굴리기"가 다른 일이라는 것을 알고, 굴리는 데 필요한 네 가지(모니터링, 백업, 버전, 업데이트)를 **주기표**로 만든다.
- 앱(브라우저)과 서버의 에러를 **내가 모르는 사이에** 놓치지 않는 장치(전역 에러 핸들러 → 서버 → 텔레그램)를 만든다.
- 버전 번호와 변경 기록(CHANGELOG)을 붙여 "언제 무엇이 바뀌었나"를 사용자(미래의 나, 13과정의 고객)가 알 수 있게 한다.
- GitHub Actions로 push마다 테스트(12-1)가 자동으로 돌게 해, 깨진 코드가 main에 들어가지 못하게 한다.

## 왜 배우나 (나에게 어떤 쓸모)

12-3 숙제 3에서 "모르는 사이 깨진 것"을 찾았을 것이다. 배포 다음 날부터 소프트웨어는 **낡기 시작**한다: 브라우저가 바뀌고, 패키지가 바뀌고, API가 바뀌고(4-3의 "샘플은 예고 없이 바뀐다"), 데이터가 쌓인다. 13과정에서 남이 쓰는 순간 유지보수는 의무가 된다. 트레이더의 "매일 복기·주간 점검"을 소프트웨어에 적용하는 단원이다. 11-3의 운영 수칙(runbook)을 앱까지 확장한다.

## 핵심 개념

### 1. 주기표

| 주기 | 할 일 | 도구 |
|---|---|---|
| 매일(자동) | 직원 요약 알림, 에러 알림, 비용 알림 | 11-3 |
| 매주 | 로그 훑기, pending 결재, 테스트 초록 확인, 성과 지표 | 7-3, 11-1 |
| 매월 | 의존성 감사·업데이트(12-2), 백업 복구 연습(11-3), 콘솔 비용 대조(10-5), CLAUDE.md 가지치기(8-3) | |
| 분기 | 메모리 점검(7-1, 8-3), 보안 체크리스트 재점검(12-2), 모델 ID·가격 재확인(6-4) | |

**비유**: 차량 점검표. 매일 계기판, 매주 세차, 매월 오일, 분기 타이어. 점검표 없이 "고장 나면 고친다"는 가장 비싼 방식이다.

### 2. 에러 모니터링

**앱(브라우저)**: 전역 핸들러로 잡아 서버로 보낸다.
```js
// app.js 맨 앞에 (설명 주석과 함께). 에러가 나면 사용자가 모르게 넘어가지 않고 서버에 알린다
window.addEventListener("error", function (event) {
  reportError(event.message + " @ " + event.filename + ":" + event.lineno);
});
function reportError(text) {
  // 12-3의 API 서버 POST /error (토큰 포함). 실패해도 앱은 계속 동작해야 하므로 catch 로 삼킨다 — 단 콘솔에는 남긴다
  fetch(API + "/error", { method: "POST", headers: {...}, body: JSON.stringify({ text: text, when: new Date().toISOString() }) })
    .catch(function (e) { console.error("에러 보고 실패", e); });
}
```
**서버**: `/error`를 받아 로그 + 하루 N건 넘으면 텔레그램. 서버 자체 에러는 11-3의 로그·알림 그대로. 전문 에러 추적 서비스(무료 티어가 있는 것들)를 붙일 수도 있지만, 1인 회사는 **텔레그램 한 줄**이면 충분하다.

원칙: 사용자에게 보이는 메시지는 친절하게(1-7 "에러 메시지 읽기"의 반대 방향), 개발자에게 가는 로그는 상세하게, 둘 다 **비밀 없이**(11-3).

### 3. 버전과 변경 기록

- `version.js`(또는 사장실 화면 구석)에 `v1.3.0` 표시. 숫자 규칙(semantic versioning): **큰 변경.기능 추가.버그 수정**. 데이터 모양이 바뀌면(2.5단계 카테고리처럼) 최소 가운데 숫자.
- `CHANGELOG.md`: 버전마다 "추가/변경/수정" 세 줄. 커밋 메시지(5-1)를 모아 Claude Code에게 "최근 커밋으로 CHANGELOG 초안"을 시키고 읽는다.
- Git 태그: `git tag v1.3.0` → `git push --tags`. 롤백 지점이 된다(12-3).
- **데이터 마이그레이션**: 저장 형식이 바뀔 때 옛 데이터를 읽는 코드(2.5단계의 `entry.category || "etc"`, 3단계의 `latestBalance`)와 `version` 필드를 백업 JSON에 두고(`version: 1`이 이미 있다) 가져오기에서 변환.

### 4. 자동 검사(CI): GitHub Actions

push·PR마다 GitHub가 테스트를 돌린다. 저장소에 `.github/workflows/test.yml`:
```yaml
name: test
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt pytest
      - run: pytest
      - uses: actions/setup-node@v4
        with: { node-version: "22" }
      - run: for f in *.js; do node -e "new Function(require('fs').readFileSync('$f','utf8'))"; done
```
(액션 버전은 공식 마켓플레이스에서 확인.) PR 화면에 초록/빨강이 뜨고, 빨강이면 병합하지 않는다(5-3). Claude Code의 클라우드 세션은 PR의 CI 실패를 감지해 고치는 Auto-fix(9-5)와 연결된다. 비밀(API 키)이 필요한 테스트는 CI에서 **mock**(12-1)으로 돌리고, 꼭 필요하면 GitHub Secrets에.

### 5. 업데이트 습관

- 월 1회: `pip-audit`(12-2) → 업데이트 → 테스트(12-1) → 배포(12-3). 하나씩, 깨지면 `revert`.
- 모델·API: 6-4의 은퇴 예정일을 분기마다 확인, `.env`의 `CLAUDE_MODEL`만 바꾼다(코드 무변경이 설계 목표였다).
- 외부 API(증권사, 공공데이터): 변경 공지 구독, 응답 스키마 검증 테스트(4-1의 상태 코드 + 필드 존재).
- 브라우저: Pages 앱을 가끔 다른 브라우저·폰에서 열어 본다.

### 6. 문서도 유지보수

- `docs/company/runbook.md`(11-3)에 "고장 → 조치"를 사례마다 추가. 같은 고장 두 번째부터는 runbook을 보고 10분 안에.
- CLAUDE.md는 코드처럼 가지치기(8-3). 커리큘럼 lesson 문서는 코드가 바뀌면 같이(이 저장소의 규칙).
- 미래의 나는 남이다. 6개월 뒤 열어도 README만 보고 돌릴 수 있게.

## 따라하기

### 1. 주기표 만들기 (20분)

1절 표를 내 회사 기준으로 `docs/maintenance.md`에. 각 항목에 "어떻게 확인하나(명령·화면)"를 붙인다.

### 2. 앱 에러 보고 (50분)

2절 전역 핸들러와 서버 `/error`를 붙이고, 일부러 `undefined.foo`를 실행시켜 텔레그램에 오는지. 보고 실패 시 앱이 멈추지 않는지.

### 3. 버전·CHANGELOG·태그 (30분)

현재 상태를 `v1.0.0`으로 태그. `CHANGELOG.md`에 1단계부터 지금까지를 Claude Code로 초안 → 읽고 고침. 사장실에 버전 표시.

### 4. GitHub Actions (50분)

4절 워크플로를 추가해 push → Actions 탭에서 초록 확인. 일부러 테스트를 깨뜨린 PR을 만들어 빨강이 뜨는지, 그 PR을 병합하지 않고 닫는다.

### 5. 모의 고장 (30분)

증권사 API 응답에 필드가 사라졌다고 가정(가짜 응답)해 스키마 검증 테스트가 잡는지. runbook에 "외부 API 변경 시" 항목 추가.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 에러를 사용자만 봄 | 개발자는 모름 | 전역 핸들러 → 서버 → 알림 |
| 버전 없이 배포 | 어떤 코드가 돌고 있는지 모름 | 버전 표시, 태그 |
| 데이터 형식 변경 시 옛 데이터 깨짐 | 가져오기 실패 | version 필드, 변환 코드 |
| CI 없이 병합 | 깨진 main | Actions 필수, 빨강이면 병합 금지 |
| 한꺼번에 업데이트 | 원인 불명 고장 | 하나씩, 테스트, revert |
| runbook 미갱신 | 같은 고장 반복 | 고장마다 추가 |

## 확인 퀴즈

**1. "만들기"와 "굴리기"의 차이를 주기표로 설명하라.**

<details><summary>정답과 해설</summary>
만들기는 한 번이지만 굴리기는 매일(알림)·매주(로그·테스트)·매월(의존성·백업·비용)·분기(보안·모델) 반복되는 점검이다.
</details>

**2. 앱의 전역 에러 핸들러에서 보고 실패를 `catch`로 삼키는 이유.**

<details><summary>정답과 해설</summary>
에러 보고 자체가 실패해도 앱이 멈추면 안 되기 때문. 단 콘솔에는 남긴다(완전히 삼키지 않음, 12-2).
</details>

**3. 저장 형식이 바뀔 때 해야 할 두 가지.**

<details><summary>정답과 해설</summary>
버전 번호(가운데 숫자) 올리기와 옛 데이터를 읽는 변환 코드(version 필드 기준). 2.5·3단계에서 이미 했다.
</details>

**4. GitHub Actions가 빨강인 PR을 어떻게 하나?**

<details><summary>정답과 해설</summary>
병합하지 않는다. 고쳐서 초록이 된 뒤 병합. Auto-fix(9-5)로 Claude가 고치게 할 수도 있다.
</details>

**5. 모델 ID 변경에 코드 수정이 없어야 하는 이유와 방법.**

<details><summary>정답과 해설</summary>
모델은 은퇴·교체된다. `.env`의 `CLAUDE_MODEL`로 빼 두면 설정만 바꾼다(6-4·10-1).
</details>

## 숙제

1. **한 달 운영** — 주기표대로 한 달을 돌리고, 각 항목을 실제로 한 날짜를 표에 적어라. 안 한 항목은 왜 못 했는지.
2. **복구 리허설** — 서버·앱 데이터를 백업에서 복구하는 전체 절차를 runbook대로 30분 안에 해 보라(11-3 기준 재확인).
3. **13-1 예습** — 지금까지 만든 것 중 "남에게 보여 주고 싶은 것" 3개를 고르고 스크린샷을 찍어 두라.
