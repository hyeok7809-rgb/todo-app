# 12-1. 요구사항→작은 단위→검증 사이클, 테스트 기초(자동 테스트란)

| 과정 | 12. 바이브 코딩 실전과 배포 |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 11-4 |
| 경험치 | 80 |

## 이 단원을 마치면

- 바이브 코딩의 기본 루프 "요구사항 한 줄 → 작은 변경 → 검증 → 커밋"을 **테스트 코드**까지 포함해 돌릴 수 있다.
- 자동 테스트가 무엇인지(함수를 부르고 기대값과 비교하는 코드), 왜 AI 시대에 더 중요한지(AI가 고친 코드가 다른 것을 깨뜨렸는지 즉시 아는 유일한 방법) 설명할 수 있다.
- 파이썬 `pytest`로 11과정 직원 코드의 순수 함수(검증기, 집계)를 테스트하고, 자바스크립트 앱은 Playwright 스크립트(이미 CLAUDE.md에 있는 방식)로 끝에서 끝까지 검증한다.
- Claude Code에게 "테스트를 먼저 쓰고 통과시켜라"고 시키는 흐름(공식 best practices의 "검증 기준 제공")을 쓴다.

## 왜 배우나 (나에게 어떤 쓸모)

8-6에서 "검증 없이 배포 없다"고 했다. 지금까지 검증은 **내가 눈으로** 하거나 Playwright 스크립트였다. 직원 코드가 10개 파일이 되면 눈으로는 못 한다. 테스트는 "내가 안 봐도 Claude가 스스로 확인하는 장치"(8-6의 루프)이고, 13과정에서 남에게 팔 때 "동작 보장"의 근거다. 트레이더에게 테스트는 **백테스트**와 같다. 전략(코드)을 과거 데이터(테스트 케이스)에 돌려 보지 않고 실전에 넣지 않는다.

## 핵심 개념

### 1. 루프 한 바퀴

```
요구사항 한 줄 (8-6 여섯 칸)
 → 테스트 먼저: "이 입력이면 이 출력" 을 코드로 (실패하는 상태)
 → 구현 (Claude Code 또는 나)
 → 테스트 통과 확인 (Claude 가 스스로 돌림)
 → 리뷰 (diff 읽기, 9-1 리뷰어)
 → 커밋 (5-1)
```

**비유**: 매매 규칙을 먼저 적고(테스트), 그 규칙으로 과거 차트를 돌려 보고(실행), 통과해야 실전(커밋). 규칙 없이 "느낌"으로 매매하는 것이 테스트 없는 바이브 코딩이다.

### 2. 자동 테스트란

**한 줄 정의**: 함수를 **정해진 입력**으로 부르고 **기대한 출력**과 같은지 확인하는 코드. 사람이 아니라 프로그램이 검사한다.

```python
# tests/test_validate.py   (11-1 검증기)
from agents.review_analyst.validate import validate_review

def test_valid_review_passes():
    ok = {"good": ["a"], "fix": ["b"], "rule_tomorrow": "c", "violations": ["none"]}
    assert validate_review(ok) == []

def test_too_many_items_fails():
    bad = {"good": ["a", "b", "c"], "fix": [], "rule_tomorrow": "", "violations": []}
    assert "항목 수 초과" in validate_review(bad)

def test_forbidden_word_fails():
    bad = {"good": ["이 종목 추천"], "fix": [], "rule_tomorrow": "", "violations": []}
    assert any("금지어" in p for p in validate_review(bad))
```

`pip install pytest` → `pytest`를 치면 `tests/` 아래 `test_*.py`의 `test_*` 함수를 전부 돌려 통과/실패를 보여 준다. `assert`는 "이게 참이어야 한다"다(1-3 조건문).

### 3. 무엇을 테스트하나

| 우선순위 | 대상 | 이유 |
|---|---|---|
| 1 | **순수 함수**(입력→출력만, 외부 영향 없음): 검증기, 집계, 날짜 계산, 순자산 | 쉽고 빠르고 가장 자주 깨진다 |
| 2 | 경계값: 빈 목록, 0, 월 바뀜, 자정, 깨진 JSON | 버그의 서식지 |
| 3 | 끝에서 끝(E2E): 앱 열기 → 기록 → 새로고침 | Playwright, 느리지만 "진짜 동작" |
| 안 함 | 모델의 답 내용 자체 | 비결정적. 대신 **검증기**(11-1)와 스키마(10-2)로 |

AI 호출이 있는 함수는 **호출 부분을 가짜(mock)로** 바꿔 테스트한다: "모델이 이 JSON을 돌려줬다 치면 우리 코드가 제대로 저장하나". 모델을 실제로 부르는 테스트는 비용이 들고 결과가 매번 달라 테스트로 부적합.

### 4. 앱(JS) 쪽

이 앱은 순수 HTML/JS(빌드 없음)라 테스트 도구를 넣지 않는다(CLAUDE.md). 대신 두 층:
- **문법 검사**: `node -e "new Function(...)"`(9-3 훅).
- **E2E**: Playwright 스크립트(`scratch/verify-*.mjs` 같은 것을 `tests/e2e/`에 정식으로). "기록 추가 → 새로고침 유지 → 잠긴 방 dialog → 390px 가로 스크롤 없음"이 이미 CLAUDE.md의 검증 목록이다. 이것을 파일로 고정하고 `/precommit` 스킬(9-2)이 돌리게 한다.
- 순수 함수(`routineStreak`, `netWorthAt`)는 나중에 `tests/unit/*.mjs`로 Node에서 직접 불러 `assert`로 검사할 수도 있다(파일을 `import`하려면 구조 변경이 필요하니 지금은 E2E로 충분).

### 5. Claude Code에게 시키는 법

공식 best practices의 표를 우리말로: "`validateEmail` 함수를 써. 테스트 케이스: … 구현 후 테스트를 돌려." → 우리: "`netWorthAt(date)`가 그 날짜 **이전** 스냅샷만 쓰는지 확인하는 Playwright 케이스를 추가하고, 통과할 때까지 고쳐. 결과 출력을 보여 줘." 테스트가 있으면 Claude가 **실패를 읽고 다시 고친다**. 테스트 파일도 diff로 읽는다(테스트를 약하게 고쳐 통과시키는 꼼수를 잡는다 — 공식 "에러를 숨기지 말고 원인을 고쳐").

### 6. 테스트도 코드다

- 테스트 이름은 "무엇이 어떻게 돼야 하는지"(`test_empty_list_returns_zero`).
- 한 테스트 = 한 사실. 실패하면 이름만 봐도 안다.
- 커밋마다 돌린다(9-3 Stop 훅 또는 `/precommit`). 13과정에서 GitHub Actions(CI)로 push마다 자동.
- 테스트가 느려지면 E2E는 줄이고 단위 테스트를 늘린다.

## 따라하기

### 1. pytest 첫 실행 (30분)

`pip install pytest` → `tests/test_validate.py`에 2절 세 테스트 → `pytest -v`. 일부러 검증기를 망가뜨려(한 줄 주석) 실패를 본 뒤 되돌린다.

### 2. 경계값 추가 (40분)

11-2의 집계 함수(위반 횟수 표)에 "JSON 0개", "7개 중 하나가 깨진 파일", "월이 바뀌는 주"를 테스트로 추가. 깨진 파일을 건너뛰는지, 0개면 빈 표를 내는지.

### 3. 모델 호출 가짜로 (40분)

복기 분석가 `run.py`의 모델 호출을 함수 하나(`call_model(prompt)`)로 뽑고, 테스트에서 그 함수를 가짜(고정 JSON 반환)로 바꿔 "저장·알림 로직"만 검사한다(`unittest.mock.patch` 또는 함수 인자로 주입).

### 4. 앱 E2E 정식화 (40분)

지금까지 썼던 Playwright 검증을 `tests/e2e/app.mjs`로 정리(CLAUDE.md 검증 목록 전부). `/precommit` 스킬이 이것을 돌리게 고친다.

### 5. 테스트 먼저 시키기 (40분)

Claude Code에 "자산관리부 `netWorthAt`가 미래 날짜 스냅샷을 섞지 않는지 E2E 케이스를 **먼저** 추가하고(실패 확인), 필요하면 고쳐서 통과시켜. 테스트 파일 diff와 실행 출력을 보여 줘." 테스트를 약화시키지 않았는지 diff를 읽는다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 모델 답을 테스트 | 매번 다른 결과 | 검증기·스키마 테스트, 모델은 mock |
| 테스트 없이 리팩터링 | 조용히 깨짐 | 순수 함수부터 테스트 |
| AI가 테스트를 약화 | 통과하지만 무의미 | 테스트 diff 읽기 |
| E2E만 | 느리고 원인 불명 | 단위 테스트 추가 |
| 테스트 안 돌리고 커밋 | 이력에 깨진 코드 | precommit 스킬·훅 |

## 확인 퀴즈

**1. 자동 테스트를 한 문장으로.**

<details><summary>정답과 해설</summary>
정해진 입력으로 함수를 부르고 기대 출력과 같은지 프로그램이 확인하는 코드.
</details>

**2. AI 호출이 있는 함수를 테스트하는 방법.**

<details><summary>정답과 해설</summary>
호출 부분을 가짜(mock)로 바꿔 고정 결과를 돌려주게 하고, 우리 코드의 저장·검증·알림 로직만 검사한다. 모델 답 자체는 테스트하지 않는다.
</details>

**3. 가장 먼저 테스트할 대상과 이유.**

<details><summary>정답과 해설</summary>
순수 함수(검증기, 집계, 날짜 계산). 쉽고 빠르며 가장 자주 깨진다.
</details>

**4. Claude에게 "테스트 먼저"를 시킬 때 내가 꼭 읽어야 할 것.**

<details><summary>정답과 해설</summary>
테스트 파일의 diff. 테스트를 약하게 고쳐 통과시키지 않았는지 확인한다.
</details>

**5. 이 앱(순수 JS)에서 테스트 도구를 추가하지 않는 이유와 대안.**

<details><summary>정답과 해설</summary>
빌드 도구·패키지 없음이 프로젝트 규칙(CLAUDE.md). 대안은 node 문법 검사와 Playwright E2E.
</details>
