# 13-1. 포트폴리오: 자동화 사례 정리, GitHub 공개, 데모 만들기

| 과정 | 13. 수익화 |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 12-4 |
| 경험치 | 80 |

## 이 단원을 마치면

- "포트폴리오 = 내가 **무엇을 자동화해서 어떤 결과**를 냈는지의 증거 모음"이라는 기준으로, 이 저장소를 남이 10초 안에 이해하는 형태로 정리한다.
- README를 **사례 중심**(문제 → 해결 → 결과 숫자 → 스크린샷)으로 다시 쓰고, 공개해도 되는 것과 안 되는 것(6-2, 12-2)을 가른다.
- 2분짜리 데모(GIF 또는 짧은 영상)와 "라이브 데모 주소"(12-3)를 만든다.
- 세 가지 수익화 길(자동화 판매, 앱 판매, 외주) 각각이 포트폴리오에서 무엇을 보고 싶어 하는지 안다.

## 왜 배우나 (나에게 어떤 쓸모)

수익화의 첫 질문은 "당신이 할 수 있다는 걸 어떻게 아나요?"다. 학위도 경력도 없는 비전공자에게 그 답은 **보여 줄 수 있는 결과물**뿐이다. 이 저장소는 이미 포트폴리오다: 픽셀 앱, AI 직원, 운영 로그, 66단원을 공부한 기록. 다만 지금은 "나를 위한" 정리라 남이 읽기 어렵다. 이 단원은 **읽는 사람을 바꾸는** 작업이다.

## 핵심 개념

### 1. 포트폴리오는 증거다

| 읽는 사람 | 보고 싶은 것 | 증거 |
|---|---|---|
| 외주 의뢰인(13-3) | 비슷한 문제를 풀어 봤나, 소통이 되나 | 사례 글, README, 이슈·PR 대화(5-3) |
| 앱 고객(13-2) | 내 문제가 해결되나, 믿을 만한가 | 라이브 데모, 스크린샷, 변경 기록(12-4) |
| 자동화 고객 | 시간·돈이 얼마나 절약되나 | 전후 숫자, 운영 기간, 비용(10-5) |

**비유**: 트레이더의 수익 인증. 말이 아니라 계좌 캡처다. 다만 여기서는 "수익률"이 아니라 "자동화로 아낀 시간 / 지킨 규칙 / 운영한 일수"다.

### 2. 사례 글의 틀 (한 사례 = 반 페이지)

```
## 매매 복기 자동화
문제: 장 마감 후 복기를 미루다 안 하게 됨. 규칙 위반이 반복.
해결: 매일 15:40 AI 직원이 기록을 읽어 위반·규칙을 150자로 정리, 텔레그램 발송. 주간 리포트 자동 생성.
결과: 8주 운영, 복기 실행률 32% → 94%, 손절 규칙 위반 주 5회 → 1회. 월 AI 비용 약 $0.4.
기술: Python, Claude API(구조화 출력·캐싱), cron, Telegram Bot, 테스트 24개, VPS.
[스크린샷] [코드 링크] [리포트 샘플(가명)]
```
숫자는 **인사부 데이터와 비용 로그**에서 나온다. 그래서 2단계부터 기록을 남겼다. 사례 3개면 충분하다: 복기 자동화, 자기관리 앱(픽셀 오피스), AI 직원 조직(11과정).

### 3. 공개 범위

- **공개**: 코드, 구조, 문서, 가명 처리한 샘플 데이터, 비용·운영 숫자.
- **비공개**: 실제 매매 기록·계좌·금액(6-2), 키(4-2), 서버 주소·토큰(12-2), 백업 JSON.
- 저장소가 공개면 **이력(5-1)** 까지 공개다. 과거 커밋에 비밀이 있었다면 재발급(4-2)하고, 필요하면 새 저장소로 "깨끗한 복사본"을 만든다.
- 커리큘럼 문서 66단원은 그 자체로 "독학 기록"이라는 포트폴리오다. 공개하면 13-4의 콘텐츠 길도 열린다.

### 4. README 구조 (5-3 보강)

1. 한 줄: 무엇을 하는 프로젝트인가 + 라이브 데모 링크 + 스크린샷 1장.
2. 사례 3개(2절 틀).
3. 구조 그림(11-2 조직도): 앱 ↔ 서버 ↔ AI 직원.
4. 기술과 배운 것(커리큘럼 링크).
5. 실행 방법(기존 README 내용).
6. 변경 기록·버전(12-4), 라이선스(아래).

**라이선스**: 공개 저장소에는 라이선스 파일을 둔다. 13-2에서 판매할 거면 "코드 공개 + 상업 이용 제한" 같은 선택이 필요하니, 공식 안내 사이트에서 비교하고 **확실치 않으면 전문가에게**(6-2).

### 5. 데모

- **라이브**: 12-3의 Pages/Vercel 주소. 체험용 데이터가 미리 들어가게 "샘플 데이터 넣기" 버튼(사장실)을 추가하면 첫인상이 좋다.
- **GIF 2분**: 지도 → 재무부 기록 → 인사부 체크 → 교육부 진도 → 사장실 AI 직원 상태. 화면 녹화 도구로 찍고 GIF로 변환해 README 맨 위에.
- **리포트 샘플**: 주간 리포트 md를 가명 처리해 `docs/samples/`에.

### 6. 글쓰기는 Claude에게, 숫자와 판단은 나에게

"README 초안을 사례 틀로 써 줘"는 Claude Code가 잘한다(저장소를 읽으니까). 하지만 **숫자**(실행률, 위반 횟수, 비용)는 내 로그에서 내가 뽑고, **무엇을 공개할지**는 내가 정한다. 6-2의 검증 습관이 여기서는 "내 포트폴리오에 환각이 없게"다.

## 따라하기

### 1. 숫자 뽑기 (40분)

인사부 14일 표·복기 JSON·비용 로그에서 사례 3개의 전후 숫자를 뽑아 `docs/portfolio/numbers.md`에. 출처(어느 파일, 어느 기간)를 옆에.

### 2. 사례 3개 (60분)

2절 틀로 세 사례를 쓴다. Claude Code에 초안을 시키되 숫자는 내가 넣는다. 각 사례에 스크린샷 1장.

### 3. 공개 점검 (30분)

`git log -p | grep -i "key\|secret\|token"` 등으로 이력에 비밀이 없는지 확인(있으면 재발급 + 새 저장소). 샘플 데이터 가명화. 12-2 체크리스트 재확인.

### 4. README 재작성 + 데모 (60분)

4절 구조로 README를 고치고, GIF를 찍어 맨 위에, 라이브 데모 링크, 라이선스 파일 추가. 다른 사람(또는 Claude에게 "처음 보는 개발자 입장에서 10초 안에 이해되나?")에게 읽혀 본다.

### 5. 공개 (20분)

저장소를 공개로 전환(이미 Pages로 공개라면 확인만). 프로필 README(GitHub 계정 소개)에 이 프로젝트를 고정(pin).

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 기능 나열 | "그래서 뭐가 좋은데?" | 문제→해결→결과 숫자 |
| 숫자 없음 | 신뢰 부족 | 로그에서 뽑기(그래서 기록했다) |
| 실제 데이터 공개 | 개인정보·계좌 노출 | 가명, 비공개 목록 |
| 이력 속 비밀 | 공개와 동시에 유출 | 재발급, 깨끗한 저장소 |
| 라이선스 없음 | 쓸 수 있는지 불명 | 라이선스 파일, 전문가 확인 |
| 데모 없음 | 읽기만으로 못 믿음 | 라이브 주소 + GIF |

## 확인 퀴즈

**1. 포트폴리오에서 "증거"가 되는 것 세 가지.**

<details><summary>정답과 해설</summary>
전후 숫자(실행률·위반·비용), 운영 기간, 라이브 데모·스크린샷. 기능 목록은 증거가 아니다.
</details>

**2. 공개 저장소로 전환하기 전에 확인할 것.**

<details><summary>정답과 해설</summary>
커밋 이력 전체에 비밀이 없는지, 샘플 데이터가 가명인지, 라이선스가 있는지. 이력에 비밀이 있었다면 재발급.
</details>

**3. 사례 글에서 Claude에게 맡길 것과 맡기지 않을 것.**

<details><summary>정답과 해설</summary>
문장 초안은 맡기고, 숫자와 공개 범위는 내가 정한다. 포트폴리오에 환각이 들어가면 안 된다.
</details>

**4. 커리큘럼 66단원 문서가 포트폴리오인 이유.**

<details><summary>정답과 해설</summary>
비전공자가 기초부터 독학한 기록 자체가 학습 능력과 꾸준함의 증거이고, 13-4의 콘텐츠 상품의 원천이 된다.
</details>

**5. 외주 의뢰인이 특히 보는 것.**

<details><summary>정답과 해설</summary>
비슷한 문제를 풀어 본 사례와 소통 능력(이슈·PR·문서). 기술 목록보다 사례 글.
</details>
