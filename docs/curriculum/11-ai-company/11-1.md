# 11-1. 에이전트 설계: 역할·입력·출력·검증 정의, 에이전트 하나부터 제대로

| 과정 | 11. AI 에이전트 조직 만들기 (최종 목표) |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 10-5 |
| 경험치 | 80 |

## 이 단원을 마치면

- "AI 직원 한 명"을 **직무 기술서** 한 장(역할·입력·출력·도구·검증·실패 시·비용)으로 정의할 수 있다.
- 10과정의 재료(시스템 프롬프트, 구조화 출력, 도구, Agent SDK, 로그)를 조립해 **첫 직원**(매매 복기 분석가)을 실제로 돌린다.
- 직원의 출력을 **검증하는 코드**(스키마, 범위, 금지어, 샘플 사람 검토)를 먼저 쓰고 나서 직원을 쓴다.
- 7-3의 주간 평가처럼 직원의 성과를 숫자로 재는 방법을 정한다.

## 왜 배우나 (나에게 어떤 쓸모)

이 커리큘럼의 최종 목표가 "24시간 돌아가는 AI 회사"다. 회사는 직원 한 명에서 시작한다. 첫 직원을 **제대로** 뽑는 법을 배우면 둘째, 셋째는 같은 틀의 반복이다. 반대로 첫 직원을 대충 뽑으면(지시가 모호, 검증 없음, 비용 추적 없음) 직원이 늘수록 혼란만 는다. 이 단원은 픽셀 오피스의 "채용 예정" 책상에 첫 사람을 앉히는 날이다.

## 핵심 개념

### 1. 직무 기술서 한 장

| 항목 | 내용 | 배운 곳 |
|---|---|---|
| 이름·부서 | 복기 분석가 · 인사부 | — |
| 역할(시스템 프롬프트) | SKILL.md 본문 | 7-2, 10-2 |
| 입력 | 오늘 매매 기록(식별 정보 제거) | 6-2, 7-3 |
| 출력 | JSON: good[2], fix[2], rule_tomorrow, violations[] | 10-2 |
| 도구 | 없음(읽기만) / 또는 get_routine_streak | 10-3 |
| 검증 | 스키마 통과, violations가 enum, 150자 이내, 금지어 없음 | 11-1 |
| 실패 시 | 재시도 1회 → 실패면 알림 + 사람 검토 큐 | 4-4 |
| 주기·트리거 | 평일 15:40(장 마감 후) | 4-4, 9-5 |
| 모델·비용 | Sonnet, 캐싱, 월 ≈ $0.3 | 6-4, 10-5 |
| 성과 지표 | 사람 검토에서 "유용" 비율, 규칙 위반 감소 추세 | 7-3 |

**비유**: 사람을 뽑을 때도 "뭘 하는 자리인지, 무엇을 받고 무엇을 내는지, 잘했는지 어떻게 아는지"가 없으면 평가도 못 한다. AI 직원은 이 표가 **곧 코드**가 된다.

### 2. 역할은 좁게, 출력은 고정으로

- 한 직원 = 한 작업(7-2의 "스킬 하나 = 작업 하나"). "복기도 하고 뉴스도 보고"는 두 직원.
- 출력은 **구조화된 JSON**(10-2). 사람이 읽는 문장은 그 JSON에서 코드가 만든다. 그래야 다음 직원(주간 리포트)이 입력으로 받는다(11-2).
- 입력도 고정 형식(CSV/JSON). 7-3에서 정한 저장처가 그대로 직원 간 **인터페이스**가 된다.

### 3. 검증을 먼저 쓴다

8-6의 "검증 없이 배포 없다"를 코드로:

```python
def validate_review(obj):
    problems = []
    if len(obj["good"]) > 2 or len(obj["fix"]) > 2: problems.append("항목 수 초과")
    if len(json.dumps(obj, ensure_ascii=False)) > 600: problems.append("길이 초과")
    for v in obj["violations"]:
        if v not in {"stoploss", "chase", "average_down", "none"}: problems.append("알 수 없는 위반 코드 " + v)
    for word in ["추천", "매수하세요", "전망"]:           # 6-2·4-3: 종목 추천·시장 전망 금지
        if word in json.dumps(obj, ensure_ascii=False): problems.append("금지어 " + word)
    return problems
```

검증 실패 → 같은 입력으로 **1회 재시도**(프롬프트에 실패 이유 추가) → 또 실패면 `review/pending/`에 저장하고 텔레그램 알림(4-4). 사람이 본다. 이 "사람 검토 큐"가 있어야 자동화가 **조용히 틀리지 않는다.**

### 4. 모델·비용·캐싱

6-4 규칙대로 Sonnet부터. 시스템 프롬프트를 캐시(10-5). 호출마다 `log_usage(message, "review-analyst")`. 월 비용 추정을 직무 기술서에 적고, 콘솔 상한과 비교.

### 5. 성과를 잰다

- **품질**: 주 1회 샘플 5건을 내가 읽고 "유용/보통/쓸모없음"으로 표시 → 유용 비율.
- **효과**: 인사부 데이터에서 규칙 위반 횟수의 4주 추세(복기 분석가가 있는 이유).
- **비용**: 로그 합계 / 유용 건수 = 유용한 복기 1건당 비용.
세 숫자가 7-3의 주간 평가에 들어간다. 품질이 낮으면 **지시서를 고친다**(6-3의 "모델 탓은 마지막").

### 6. Client SDK로 충분하다

첫 직원은 파일을 수정하지 않으니 Client SDK + 구조화 출력(10-2)이면 된다. Agent SDK(10-4)는 저장소를 만지는 직원(11-2의 리포트 작성자)부터.

## 따라하기

### 1. 직무 기술서 (30분)

`agents/review-analyst/JOB.md`에 1절 표를 내 상황으로 채운다. 성과 지표까지.

### 2. 검증기 먼저 (40분)

`agents/review-analyst/validate.py`에 3절 함수를 쓰고, **가짜 출력 5개**(정상 2, 항목 초과, 금지어, 잘못된 코드)로 테스트한다. 직원 코드는 아직 없다.

### 3. 직원 코드 (60분)

`agents/review-analyst/run.py`: `.env` 로드 → 오늘 기록 읽기(`docs/review/input/YYYY-MM-DD.txt`) → 시스템 프롬프트(SKILL.md, 캐싱) → 구조화 출력 호출 → `validate` → 통과 시 `docs/review/YYYY-MM-DD.json` 저장 + 사람용 요약 텍스트 생성 → 실패 시 재시도/알림. 모든 단계에 `logging`(4-4)과 `log_usage`(10-5).

### 4. 스케줄 (20분)

4-4의 cron/작업 스케줄러에 평일 15:40 등록(또는 9-5 예약 작업). 다음 날 실제로 도는지, 텔레그램 요약이 오는지.

### 5. 첫 평가 (일주일 뒤, 30분)

5건 샘플 검토 → 유용 비율, 비용/건, 위반 추세를 `docs/agents-review.md`에 기록. 지시서를 한 번 고친다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 역할이 넓음 | 출력 품질 들쭉 | 한 직원 한 작업 |
| 출력이 자유 문장 | 다음 단계가 못 씀 | 구조화 JSON |
| 검증 없음 | 틀린 결과가 쌓임 | 검증기 먼저, 사람 검토 큐 |
| 실패를 삼킴 | 고장을 모름 | 재시도 1회 후 알림 |
| 비용 미추적 | 월말 청구 놀람 | log_usage + 상한 |
| 성과 지표 없음 | 개선 방향 모름 | 품질·효과·비용 세 숫자 |

## 확인 퀴즈

**1. 직무 기술서에서 "검증" 항목이 빠지면 생기는 일.**

<details><summary>정답과 해설</summary>
틀린 출력이 그대로 저장·전달되고, 다음 직원의 입력을 오염시킨다. 조용한 고장. 검증기와 사람 검토 큐가 필요하다.
</details>

**2. 출력을 JSON으로 고정하는 두 가지 이유.**

<details><summary>정답과 해설</summary>
코드가 검증·집계할 수 있고, 다음 직원(주간 리포트)의 입력 형식이 된다(직원 간 인터페이스).
</details>

**3. 검증 실패 시 흐름.**

<details><summary>정답과 해설</summary>
실패 이유를 붙여 1회 재시도 → 또 실패면 pending 큐에 저장하고 알림 → 사람이 검토.
</details>

**4. 첫 직원에 Agent SDK가 아니라 Client SDK를 쓰는 이유.**

<details><summary>정답과 해설</summary>
파일 수정·명령 실행이 필요 없는 텍스트→JSON 작업이라 Client SDK가 더 싸고 단순하다.
</details>

**5. 품질이 낮을 때 첫 번째로 고치는 것.**

<details><summary>정답과 해설</summary>
지시서(시스템 프롬프트·예시·형식). 모델 교체는 마지막(6-3).
</details>
