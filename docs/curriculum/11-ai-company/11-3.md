# 11-3. 24시간 운영: 스케줄러, 서버(VPS/클라우드), 로그, 실패 알림, 비용 관리

| 과정 | 11. AI 에이전트 조직 만들기 (최종 목표) |
|---|---|
| 예상 시간 | 5시간 |
| 선수 단원 | 11-2 |
| 경험치 | 100 |

## 이 단원을 마치면

- "24시간"을 실현하는 세 가지 길(내 컴퓨터 상시 가동, 클라우드 예약 작업, 작은 서버)의 비용·난이도·맞는 일을 비교해 **내 회사의 조합**을 정한다.
- 작은 리눅스 서버(VPS)를 빌려 파이썬 팀장을 cron으로 돌리고, `.env`·로그·백업을 서버에서 안전하게 다루는 최소 운영을 할 수 있다.
- 로그를 **세 층**(직원 로그, 팀장 로그, 비용 로그)으로 나누고, 실패·비용 이상을 텔레그램으로 받는다.
- 4-3의 안전장치(주문 한도, 실전 전환 확인)를 운영 코드로 옮기고, "멈추는 스위치"(kill switch)를 만든다.

## 왜 배우나 (나에게 어떤 쓸모)

11-2의 팀장은 내 컴퓨터가 켜져 있을 때만 돈다(4-4의 교훈). "24시간 돌아가는 회사"는 결국 **어디서 돌릴 것인가**와 **고장을 어떻게 알 것인가**의 문제다. 트레이더에게 비유하면 이 단원은 **리스크 관리**다. 수익 전략(직원)이 아무리 좋아도 리스크 관리(운영) 없이는 한 번의 사고로 끝난다.

## 핵심 개념

### 1. 세 가지 길

| 길 | 어떻게 | 비용 | 난이도 | 맞는 일 |
|---|---|---|---|---|
| 내 컴퓨터 상시 가동 | 4-4 cron/작업 스케줄러, 절전 끄기 | 전기 | 낮음 | 시작 단계, 증권사 API처럼 **내 PC 인증**이 필요한 것 |
| 클라우드 예약 작업 | 9-5 `/schedule` | 구독 사용량 | 낮음 | 저장소를 읽고 쓰는 판단형 작업(리포트, 정리) |
| 작은 서버(VPS) | 리눅스 서버 빌려 cron + 파이썬 | 월 수천~1만 원대 | 중간 | 수집·분류·알림 같은 **항상 도는 스크립트**, 큐 보관 |

현실적 조합: **VPS**에 팀장·수집·분류·알림(싸고 항상 켜짐) + **클라우드 예약 작업**에 저장소 리포트·정리(Claude Code가 필요한 일) + **내 PC**에 증권사 연동(인증·보안상 PC가 유리한 경우). 셋은 **저장소(Git)와 큐 폴더**로 연결된다.

### 2. VPS 최소 운영

(서비스 이름·요금은 바뀌니 각 공식 페이지에서 확인. 국내외 저가 VPS는 월 1만 원 안팎부터.)

1. 우분투 서버 하나 생성 → SSH 키로 접속(비밀번호 로그인 끄기).
2. `git clone` 내 저장소 → 가상환경 → `pip install`.
3. `.env`는 **서버에서 직접** 만든다(저장소에 없다, 4-2). 권한 `chmod 600 .env`.
4. `crontab -e`로 팀장 등록(4-4와 동일, 절대경로). 시간대 `timedatectl set-timezone Asia/Seoul`.
5. 로그 폴더 권한, 디스크 용량 확인(`df -h`), 로그 회전.
6. 서버도 업데이트(`apt update && apt upgrade`)를 월 1회.
Claude Code(SSH로 접속한 터미널에서 `claude`)에게 "이 서버에 cron 등록 상태 점검"을 시킬 수 있다 — 단 서버의 `.env`를 읽지 못하게 9-6 deny 규칙을 **서버 저장소에도** 둔다(커밋돼 있으니 자동).

### 3. 로그 세 층

| 층 | 내용 | 어디에 | 누가 읽나 |
|---|---|---|---|
| 직원 로그 | 입력 요약, 검증 결과, 재시도 | `logs/<직원>.log` | 고장 조사 때 |
| 팀장 로그 | 어떤 직원이 언제 성공/실패/건너뜀 | `logs/manager.log` | 매일 요약 알림의 원천 |
| 비용 로그 | 호출별 토큰·비용 | `logs/api-usage.csv` | 일일 비용 알림, 월말 대조 |

원칙: **로그에 비밀·개인정보 없음**(4-2, 6-2), 날짜별 회전(`RotatingFileHandler` 또는 `logrotate`), 보관 30일.

### 4. 알림 설계

- **매일 1통**: "오늘 직원 3/3 성공, 비용 $0.31, 큐 대기 0, pending 1건". 안 오면 그 자체가 고장 신호(4-4).
- **즉시**: 직원 실패(재시도 후), 비용이 일 평균 3배 초과, 큐가 N건 이상 쌓임, 디스크 90%.
- **주간**: 7-3·11-1의 성과 지표.
알림 채널은 4-4의 텔레그램 봇 하나로 통일. 알림이 너무 많으면 무시하게 되니 **즉시 알림은 세 종류만.**

### 5. 멈추는 스위치

- `STOP` 파일: 저장소(또는 서버)에 `company/STOP` 파일이 있으면 팀장이 **아무것도 하지 않고** 종료. 휴대폰에서 GitHub 앱으로 파일 하나 만들면 전사 정지.
- 비용 상한: 콘솔 월 상한(10-1) + 코드 상한(일 $X 넘으면 STOP 파일 생성 + 알림).
- 주문 관련(4-3): 실전 모드는 `KIS_MODE=prod` **그리고** 별도 확인 파일 둘 다 있어야. 하루 주문 금액·횟수 상한은 코드 상수. 이 단원에서도 **주문 자동화는 켜지 않는다.** 조회·알림까지.

### 6. 백업과 복구

- 큐·로그·리포트는 서버에만 두지 말고 **저장소에 커밋**(리포트)하거나 **일일 압축 백업**을 다른 곳(클라우드 스토리지)으로.
- 앱 데이터(사장실 백업 JSON)도 같은 백업 흐름에.
- 복구 연습: 서버를 지웠다 치고 새 서버에 2절을 다시 해 본다. 30분 안에 되면 합격.

## 따라하기

### 1. 길 정하기 (30분)

1절 표를 내 직원 3명에 적용해 `docs/company/ops.md`에 "누가 어디서 도나"를 적는다.

### 2. VPS 세팅 (90분)

2절 순서대로. SSH 키 접속까지 되면 `claude`를 서버 터미널에서 열어 "cron 목록과 로그 폴더 상태를 점검해"를 시켜 본다. `.env` 읽기가 거부되는지 확인(9-6).

### 3. 팀장 서버 이전 (40분)

11-2 팀장을 서버 cron에 등록. 내 PC의 cron은 끈다(중복 방지). 다음 날 텔레그램 일일 요약이 **서버에서** 오는지.

### 4. 알림·스위치 (50분)

4절의 일일 요약과 즉시 알림 세 종류를 팀장에 붙인다. `STOP` 파일을 만들어 팀장이 멈추는지, 지우면 다시 도는지 확인. 비용 상한 초과를 흉내(로그에 큰 값 삽입)내 STOP이 생기는지.

### 5. 복구 연습 (40분)

로그·큐·백업 JSON을 압축해 다른 저장소(클라우드 스토리지)로 올리는 스크립트를 만들고 cron에. 그 다음 새 서버(또는 로컬 새 폴더)에서 복구를 시연.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| `.env`를 서버에 git으로 | 비밀 커밋 | 서버에서 직접 생성, chmod 600 |
| 시간대 미설정 | 새벽에 실행 | Asia/Seoul |
| PC·서버 cron 둘 다 | 중복 실행 | 한 곳만, 멱등 |
| 알림 과다 | 무시하게 됨 | 일일 1통 + 즉시 3종 |
| 멈출 방법 없음 | 사고 시 손 못 씀 | STOP 파일, 상한 |
| 백업 없음 | 서버 사고 시 전부 손실 | 일일 백업, 복구 연습 |

## 확인 퀴즈

**1. 증권사 연동을 서버가 아니라 내 PC에 두는 게 유리할 수 있는 이유.**

<details><summary>정답과 해설</summary>
인증·보안 정책상 특정 기기가 필요한 경우가 있고, 주문 관련 사고 시 물리적으로 바로 멈출 수 있다. 조회만이면 서버도 가능하되 4-3 주의를 따른다.
</details>

**2. "매일 1통" 요약 알림이 안 오면 무엇을 뜻하나?**

<details><summary>정답과 해설</summary>
팀장 자체가 안 돌았다는 신호. 알림의 부재도 신호가 되도록 설계한 것.
</details>

**3. STOP 파일 방식의 장점.**

<details><summary>정답과 해설</summary>
서버 접속 없이 휴대폰 GitHub 앱으로 파일 하나 만들어 전사 정지가 가능하고, 팀장 코드가 단순해진다.
</details>

**4. 로그에 넣으면 안 되는 것.**

<details><summary>정답과 해설</summary>
API 키·토큰·계좌 등 비밀과 개인정보. 로그는 백업·공유될 수 있다.
</details>

**5. 복구 연습의 합격 기준과 이유.**

<details><summary>정답과 해설</summary>
새 서버에서 30분 안에 복구. 백업은 복구해 본 적 없으면 백업이 아니다.
</details>

1. **운영 수칙** — `docs/company/runbook.md`에 "매일 확인할 것, 주간 확인할 것, 고장 시 순서, 정지 방법, 복구 방법"을 적어라. 12-4에서 다듬는다.
