# 11-4. 나의 회사 설계: 재무·루틴·학습·매매 부서에 AI 직원 배치 (이 프로젝트와 연결)

| 과정 | 11. AI 에이전트 조직 만들기 (최종 목표) |
|---|---|
| 예상 시간 | 5시간 |
| 선수 단원 | 11-3 |
| 경험치 | 100 |

## 이 단원을 마치면

- 픽셀 오피스의 부서(재무·자산·인사·교육·기획·AI 직원실)마다 **어떤 AI 직원이 무엇을 하는지** 배치표를 완성한다.
- 앱(브라우저)과 회사(서버)를 잇는 방법 세 가지(백업 파일 동기화, 작은 API 서버, 정적 JSON 발행)를 비교해 하나를 고른다.
- 서버의 큐·로그를 읽어 지도의 "직원 상태"(근무 중/완료/문제)를 **진짜 데이터**로 바꾸는 첫 연결을 만든다.
- 졸업 프로젝트(2월 말)의 범위와 완료 기준을 적는다.

## 왜 배우나 (나에게 어떤 쓸모)

1단계 가계부에서 시작한 "나의 1인 회사"가 여기서 처음 **사람 하나 + AI 직원 여럿**이 된다. 지금까지 지도의 직원 책상은 비어 있었다(`buildDeskGrid()`의 빈 의자). 이 단원 끝에 그 책상에 실제로 도는 직원이 앉는다. 그리고 커리큘럼의 모든 조각(앱, 파이썬, API, Git, Claude Code, 운영)이 한 그림으로 모인다.

## 핵심 개념

### 1. 부서별 배치표

| 부서(방) | 사람(나)의 일 | AI 직원 | 입력 → 출력 | 주기 | 실행 위치 |
|---|---|---|---|---|---|
| 재무부 | 가계부 기록 | 지출 분석가 | 백업 JSON → 월간 지출 해석·이상 지출 알림 | 주 1회 | VPS |
| 자산관리부 | 잔고 기록 | 자산 리포터 | 스냅샷 → 순자산 추세 해석 | 월 1회 | VPS |
| 인사부 | 루틴 체크, 복기 | 복기 분석가(11-1), 루틴 코치 | 복기 기록 → JSON / 14일 표 → 격려·경고 1줄 | 매일 | VPS |
| 교육부 | 단원 공부 | 학습 코치(7-2 퀴즈 스킬의 자동화) | 완료 단원 → 복습 퀴즈·다음 단원 예습 메모 | 매일 | 클라우드 예약 작업 |
| 기획부 | 리포트 읽기 | 주간 리포터(11-2) | 모든 직원 결과 → 주간 리포트 md | 주 1회 | 클라우드 예약 작업 |
| AI 직원실 | 감독 | 팀장(코드), 뉴스 분류가(배치) | 큐 → 큐 | 매일 | VPS |
| 사장실 | 결재 | pending 검토 큐 | 검증 실패 건 → 사람 판단 | 수시 | 앱 |

원칙(11-1): 사람은 **입력과 결재**, AI는 **분석과 정리**, 코드는 **집계와 배선**. 주문·결제 같은 돈이 움직이는 행동은 이 표에 없다. 4-3의 안전 기준을 통과한 뒤 별도 설계.

### 2. 앱과 회사를 잇는 세 길

지금 앱 데이터는 브라우저 `localStorage`에만 있고(1단계부터 그렇게 저장했다), 회사는 서버에 있다. 잇는 방법:

| 길 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 백업 파일 동기화 | 사장실 백업 JSON을 서버 폴더에 올리고(수동/클라우드 드라이브), 직원 결과 JSON을 앱이 "가져오기" | 코드 변경 최소, 지금 당장 가능 | 수동, 실시간 아님 |
| B. 정적 JSON 발행 | 서버가 `status.json`(직원 상태·오늘 결과)을 GitHub Pages 저장소에 커밋 → 앱이 fetch | 서버 없이 읽기 가능, 저장소가 곧 API | 쓰기(앱→서버)는 여전히 A 필요, 공개 저장소면 내용 공개 |
| C. 작은 API 서버 | 서버에 HTTP API(4-1 역할 분담) → 앱이 fetch로 읽고 쓰기 | 실시간 양방향, 휴대폰·PC 데이터 통합(5-3의 한계 해결) | 인증·보안·배포(12과정) 필요 |

권장 순서: **A로 시작 → B로 상태 표시 → C는 12과정 뒤에.** 12-3 배포와 12-2 보안을 배우기 전에 C를 열면 내 데이터가 인터넷에 노출된다.

### 3. 첫 연결: 직원 상태를 지도에 (길 B)

서버 팀장이 매일 끝에 `company/status.json`을 만든다:
```json
{ "updated": "2026-12-20T15:45:00",
  "agents": { "review-analyst": {"status": "done", "last": "15:41", "pending": 0},
              "news-classifier": {"status": "working", "last": "15:30", "queue": 12},
              "weekly-reporter": {"status": "rest", "last": "12-14"} } }
```
이 파일을 저장소(또는 Pages 저장소)에 커밋·push(9-5의 `claude/` 브랜치 규칙 또는 별도 `status` 브랜치). 앱은 `fetch("status.json")`(2-6)로 읽어 `ROOMS`의 직원 책상(`buildDeskGrid`)에 **실제 직원 이름과 상태 알약**을 붙인다. `file://`로 열면 fetch가 막히니 Pages 주소(5-3)에서 동작. 실패하면 "오프라인" 표시로 **조용히 실패하지 않게**(4-4). 이 변경은 "AI 직원실" 방을 여는 로드맵 8단계이며, 지금까지의 모든 방처럼 `agents.js` 파일 하나로 만든다(CLAUDE.md 규칙).

### 4. 사장실 결재 큐

11-1의 pending(검증 실패 건)을 앱 사장실에 띄운다: 길 A/B로 `pending.json`을 읽어 "승인/반려" 버튼 → 결과는 길 A(백업 내보내기에 포함) 또는 C가 생길 때까지는 **텔레그램 명령**(봇에 `/approve 123`)으로. 사람의 판단이 들어가는 지점을 UI로 만드는 것이 "1인 회사의 사장"의 핵심 화면이다.

### 5. 졸업 프로젝트 정의 (2월 16일~28일)

**완료 기준**(8-6의 검증 칸):
1. 직원 3명 이상이 VPS/예약 작업에서 **2주 연속** 무인 운영, 일일 요약 알림 14통.
2. 지도의 직원 상태가 `status.json`으로 실제 갱신.
3. 사장실에서 pending 1건 이상을 실제로 결재.
4. 월 AI 비용이 설계치(10-5) 이내, 로그와 콘솔 대조 완료.
5. `docs/company/` 아래 조직도·큐·운영 수칙·비용표가 최신.
6. README에 스크린샷과 "무엇을 자동화했나" 한 문단(13-1 포트폴리오).

**범위 밖**: 주문 자동화, 실시간 API 서버(C), 다른 사람 사용.

### 6. 그다음

12과정에서 C(API 서버)·보안·배포를 배우면 앱이 서버와 양방향이 되고, 휴대폰·PC 데이터가 합쳐진다. 13과정에서 이 회사를 **포트폴리오**로 만들고, 같은 구조를 다른 1인 투자자에게 제공할 수 있는지(시세 데이터 제외, 4-3) 검토한다.

## 따라하기

### 1. 배치표 완성 (40분)

1절 표를 내 상황으로 채워 `docs/company/org.md`(11-2 숙제)에 합친다. 직원마다 11-1 직무 기술서 링크.

### 2. 길 A 가동 (40분)

사장실 백업 JSON을 서버 `company/input/app-backup.json`으로 올리는 절차를 정하고(클라우드 드라이브 동기화 폴더 등), 지출 분석가(새 직원, Client SDK)가 그것을 읽어 "이번 달 이상 지출 3건"을 텔레그램으로 보내게 한다.

### 3. 길 B: status.json (60분)

팀장이 `company/status.json`을 만들어 커밋·push하게 한다. 앱에 `agents.js`를 추가해(CLAUDE.md의 "새 부서 여는 법") AI 직원실 방을 열고, Pages 주소에서 `fetch`로 읽어 직원 이름·상태를 책상에 표시. 오프라인이면 "연결 없음" 표시. Playwright로 검증(fetch는 `page.route`로 흉내).

### 4. 결재 큐 UI (50분)

사장실에 pending 목록을 보여 주고 승인/반려를 localStorage에 기록, 백업 JSON에 포함. 서버 쪽은 텔레그램 `/approve` 명령을 받는 작은 폴링 스크립트(4-4 봇 API `getUpdates`).

### 5. 졸업 프로젝트 계획서 (30분)

5절 완료 기준을 `docs/company/capstone.md`에 복사하고 날짜·담당(나)·확인 방법을 붙인다. SCHEDULE.md 2월 16~28일 칸에 링크.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 길 C부터 시작 | 보안 없는 API 노출 | A→B→C, 12과정 후 |
| 공개 저장소에 status.json | 개인 데이터 공개 | 민감 정보 제외, 비공개 저장소·토큰 |
| fetch 실패를 무시 | 지도가 옛 상태로 | 오프라인 표시, updated 시각 표시 |
| 직원 결과를 모델이 지도에 직접 | 복잡·비용 | 팀장이 status.json 생성, 앱은 읽기만 |
| 주문 자동화 포함 | 사고 위험 | 범위 밖. 4-3 기준 통과 후 별도 |
| 졸업 기준 없음 | 끝이 없음 | 완료 기준 6개 |

## 확인 퀴즈

**1. 사람·AI·코드의 역할 분담 원칙.**

<details><summary>정답과 해설</summary>
사람은 입력과 결재, AI는 분석과 정리, 코드는 집계와 배선. 돈이 움직이는 행동은 별도 설계.
</details>

**2. 앱과 서버를 잇는 길 A·B·C의 순서와 이유.**

<details><summary>정답과 해설</summary>
A(백업 파일) → B(정적 status.json 발행) → C(API 서버). C는 인증·보안·배포(12과정)가 필요해 그 전에 열면 데이터가 노출된다.
</details>

**3. status.json 방식에서 "저장소가 곧 API"라는 말의 뜻.**

<details><summary>정답과 해설</summary>
서버가 결과를 저장소에 커밋하고 앱이 Pages 주소에서 fetch로 읽으니, 별도 API 서버 없이 Git 저장소가 데이터 전달 통로가 된다.
</details>

**4. 사장실 결재 큐가 필요한 이유.**

<details><summary>정답과 해설</summary>
검증 실패 건은 사람이 판단해야 하고(11-1), 그 판단 지점을 UI로 만들어야 자동화가 조용히 틀리지 않는다.
</details>

**5. 졸업 프로젝트 범위 밖 세 가지와 이유.**

<details><summary>정답과 해설</summary>
주문 자동화(4-3 안전 기준), 실시간 API 서버(12과정 보안·배포 후), 타인 사용(13과정 검토 후). 범위를 정해야 끝이 있다.
</details>
