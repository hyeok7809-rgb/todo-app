# 11-2. 멀티 에이전트: 팀장-팀원 구조, 작업 큐, 결과 합치기, 실패 처리

|---|---|
| 예상 시간 | 5시간 |
| 선수 단원 | 11-1 |
| 경험치 | 100 |

## 이 단원을 마치면

- 직원이 둘 이상일 때 **파일·큐로 느슨하게 연결**하는 구조(생산자 → 큐 → 소비자)를 설계하고, 왜 "직원이 직원을 직접 부르는" 구조보다 안전한지 설명할 수 있다.
- 팀장(오케스트레이터)이 하는 일 네 가지(작업 나누기, 순서 정하기, 결과 합치기, 실패 처리)를 **보통 파이썬 코드**로 쓴다. 팀장은 모델이 아니어도 된다.
- 멱등성·재시도·사람 검토 큐로 "한 직원이 실패해도 회사가 멈추지 않게" 만든다.
- 9-1의 서브에이전트·Claude Code 워크플로우와 이 구조의 관계를 안다(이 커리큘럼이 그렇게 만들어졌다).

## 왜 배우나 (나에게 어떤 쓸모)

11-1의 복기 분석가가 매일 JSON을 만든다. 주간 리포트 작성자는 그 7개를 읽어야 하고, 뉴스 분류가는 50건을 처리해 요약가에게 넘겨야 한다. 직원이 셋만 돼도 "누가 누구 결과를 언제 받나"가 문제다. 이 단원은 그 **배선**이다. 재미있는 사실: 이 커리큘럼과 픽셀 오피스가 바로 이 구조(집필자 → 비평가 → 수정자, 세 후보 → 심사위원 → 승자)로 만들어졌다. 그 경험에서 배운 "비싸고 복잡해지는 지점"도 같이 적는다.

## 핵심 개념

### 1. 직원은 서로를 모른다: 큐로 연결

```
[복기 분석가] ──JSON──▶ docs/review/        ──▶ [주간 리포트 작성자] ──md──▶ docs/weekly/
[뉴스 수집(cron)] ──txt──▶ queue/news/in/  ──▶ [뉴스 분류가(배치)] ──JSON──▶ queue/news/out/ ──▶ [요약가]
```

**한 줄 정의**: 생산자는 결과를 **정해진 곳**(폴더·파일·DB)에 넣고, 소비자는 거기서 **가져간다**. 둘은 서로를 직접 부르지 않는다.

**비유**: 공장의 컨베이어. 앞 공정이 다음 공정 사람을 부르지 않고 벨트에 올려 둔다. 다음 사람이 없어도 벨트에 쌓이고, 나중에 처리된다.

**왜**: (1) 한 직원이 죽어도 다른 직원은 돈다 (2) 각 직원을 따로 테스트·교체할 수 있다 (3) 큐에 쌓인 양이 **상태 표시**가 된다(픽셀 오피스의 "근무 중/문제"). 7-3의 저장처가 이 큐다. 작게는 폴더 하나면 되고, 커지면 SQLite 한 파일(12과정 전 수준에서 충분).

### 2. 팀장은 파이썬 함수다

```python
# company/run_daily.py — 팀장. 순서와 실패 처리만 담당. 판단은 직원(모델)이, 조립은 코드가.
def run_daily():
    collect_news()                       # cron 이 이미 했을 수도. 멱등이라 두 번 돌아도 안전
    analyst_result = run_review_analyst()            # 11-1
    if analyst_result.failed: notify("복기 분석 실패 → pending 확인"); # 다음 단계는 계속
    classify_news_batch()                # 10-5 배치. 결과는 queue/news/out/
    if is_sunday(): run_weekly_reporter()            # 7개 JSON 을 읽어 md 작성
    notify(summary_of_today())
```

팀장이 하는 네 가지: **나누기**(어떤 입력을 누구에게), **순서**(의존 관계), **합치기**(결과 모아 리포트), **실패 처리**(건너뛰기·재시도·알림). 이 넷은 **결정적**이어야 하니 모델이 아니라 코드다. 모델을 팀장으로 두는 것(Claude Code의 서브에이전트처럼)은 "무엇을 할지 모를 때" 유용하지만 비용·예측 가능성에서 불리하다. 우리 회사의 일은 매일 같으니 코드 팀장.

### 3. 멱등성과 재시도

- **멱등**(4-4): 같은 날 두 번 돌아도 결과가 같다. 출력 파일이 이미 있으면 건너뛴다. 큐 항목에 `done` 표시.
- **재시도**: API 오류(429, 5xx)는 잠시 기다렸다 재시도(지수 백오프: 2초, 4초, 8초). 검증 실패는 1회 재시도 후 pending(11-1).
- **타임아웃**: 한 직원이 영원히 돌지 않게 시간 제한.
- **락**: 팀장이 동시에 두 번 돌지 않게 lock 파일(4-4).

### 4. 결과 합치기

주간 리포트 작성자는 7개 JSON을 **코드가** 먼저 집계(위반 횟수, 추세)하고, 모델은 **해석 문장**만 쓴다(7-3의 "계산은 코드가"). 모델에게 7개를 통째로 주고 "합쳐 줘"라고 하면 토큰도 많고 숫자도 틀린다. 집계표를 주고 "이 표를 3줄로 해석"이 맞다.

### 5. 병렬은 필요할 때만

뉴스 50건은 병렬이 아니라 **배치**(10-5)가 맞다(급하지 않다). 병렬 서브에이전트(9-1)는 "지금 당장 여러 관점이 필요"할 때. 이 커리큘럼 제작에서 세 후보 병렬은 품질을 올렸지만 크레딧을 크게 썼다. 매일 도는 회사에 그 방식을 쓰면 월 비용이 수십 배가 된다. **일상은 큐+배치, 특별한 결정만 병렬.**

### 6. Claude Code 워크플로우와의 관계

Claude Code에는 서브에이전트를 코드로 조율하는 워크플로우 기능이 있다(공식 best practices의 "dynamic workflows", `/batch`). 그것이 "모델 팀장 + 서브에이전트 팀원"의 Claude Code 버전이다. 우리 회사는 파이썬 팀장으로 시작하고, "탐색·심사"처럼 판단이 필요한 일에만 Claude Code 워크플로우를 빌려 쓴다.

## 따라하기

### 1. 큐 폴더 설계 (30분)

`queue/` 아래 직원별 `in/`, `out/`, `pending/`, `done/` 구조를 만들고 `docs/company/queues.md`에 "누가 어디에 쓰고 누가 어디서 읽나"를 그린다.

### 2. 주간 리포트 작성자 (60분)

`agents/weekly-reporter/run.py`: `docs/review/*.json` 7일치를 코드로 집계(위반 횟수 표) → Agent SDK(10-4, Read+Write) 또는 Client SDK로 "표 해석 3줄 + 다음 주 규칙 1개"를 받아 `docs/weekly/YYYY-MM-DD.md` 저장. 멱등(파일 있으면 건너뜀). `log_usage`.

### 3. 팀장 (50분)

2절 `run_daily()`를 만들어 복기 분석가 → (일요일) 주간 리포트 순으로 돌린다. 일부러 복기 분석가를 실패시켜(입력 파일 삭제) 팀장이 알림을 보내고 **다음 단계를 계속** 하는지 확인.

### 4. 재시도와 락 (40분)

API 호출을 감싸는 `call_with_retry(fn, tries=3)`를 만들어 429를 흉내(예외 발생)내 백오프가 도는지 확인. lock 파일로 팀장 이중 실행을 막는다.

### 5. 뉴스 분류가 (60분)

11-1 숙제 1의 기술서대로 Haiku + 배치(10-5)로 `queue/news/in/*.txt`를 분류해 `out/`에 JSON. 팀장에 연결. 비용 로그로 Sonnet 대비 절감을 확인.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 직원이 직원을 직접 호출 | 하나 죽으면 연쇄 중단 | 큐로 분리 |
| 모델에게 합산 시킴 | 숫자 틀림, 토큰 낭비 | 코드 집계 → 모델 해석 |
| 멱등 없음 | 중복 리포트·중복 알림 | 출력 존재 확인, done 표시 |
| 재시도 없음 | 일시 오류로 하루 결손 | 백오프 재시도 |
| 모든 일을 병렬 에이전트로 | 비용 폭증 | 큐+배치, 병렬은 결정에만 |
| 팀장을 모델로 | 예측 불가, 비용 | 코드 팀장 |

## 확인 퀴즈

**1. 생산자-큐-소비자 구조의 세 가지 이점.**

<details><summary>정답과 해설</summary>
한 직원 실패가 다른 직원을 막지 않음, 직원별 테스트·교체 가능, 큐 길이가 상태 표시가 됨.
</details>

**2. 팀장을 모델이 아니라 코드로 두는 이유.**

<details><summary>정답과 해설</summary>
나누기·순서·합치기·실패 처리는 결정적이어야 하고 매일 같다. 코드가 예측 가능하고 싸다. 판단이 필요한 일만 모델.
</details>

**3. 7일치 JSON을 리포트로 만들 때 모델에게 주는 것은?**

<details><summary>정답과 해설</summary>
코드가 집계한 표. 원본 7개를 통째로 주지 않는다. 모델은 해석 문장만 쓴다.
</details>

**4. 멱등성이 깨지면 생기는 구체적 문제.**

<details><summary>정답과 해설</summary>
같은 날 두 번 돌면 리포트·알림·과금이 중복된다. 출력 존재 확인과 done 표시로 막는다.
</details>

**5. 병렬 서브에이전트를 매일 업무에 쓰지 않는 이유.**

<details><summary>정답과 해설</summary>
비용이 에이전트 수에 비례해 는다. 급하지 않은 대량 작업은 배치, 병렬은 당장 여러 관점이 필요한 결정에만.
</details>
