# 6-3. 프롬프트 작성법: 역할·맥락·형식·예시 주기, 단계별로 시키기, 반복 개선

| 과정 | 6. AI 기초: LLM 이해하기 |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 6-2 |
| 경험치 | 60 |

## 이 단원을 마치면

- 좋은 요청의 네 요소 **역할·맥락·형식·예시**를 알고, 아무 질문이나 이 틀로 다시 쓸 수 있다.
- "한 번에 다 해 줘" 대신 **단계별로 시키는** 이유와 방법을 안다.
- 결과가 마음에 안 들 때 모델을 바꾸기 전에 **요청을 고치는** 순서(무엇이 빠졌나)를 안다.
- 자주 쓰는 요청을 **템플릿**으로 만들어 7과정에서 스킬로 옮길 준비를 한다.

## 왜 배우나 (나에게 어떤 쓸모)

같은 모델, 같은 비용으로 결과 품질이 몇 배 달라지는 지점이 요청문이다. 코드를 못 짜도 **요청을 잘 쓰면** 바이브 코딩이 된다. 반대로 요청이 엉성하면 아무리 좋은 모델도 엉뚱한 걸 만든다. 8-6(좋은 요청 쓰는 법)과 11과정(AI 직원에게 업무 지시서 쓰기)이 전부 이 단원 위에 선다. 트레이더에게 비유하면, 요청문은 **주문서**다. 종목·수량·가격·조건이 빠진 주문은 체결되지 않거나 엉뚱하게 체결된다.

## 핵심 개념

### 1. 네 요소: 역할, 맥락, 형식, 예시

**한 줄 정의**: 좋은 요청 = 누구로서(역할) + 어떤 상황에서(맥락) + 어떤 모양으로(형식) + 이런 식으로(예시).

**비유**: 디자이너에게 "로고 만들어 줘"보다 "카페 로고, 손님은 30대, 따뜻한 느낌, 정사각형 PNG, 이 세 가지 참고" 가 낫다. AI도 같다.

**실제 예시** — 나쁜 요청과 고친 요청:

> 나쁨: "매매 복기 정리해 줘."

> 고침:
> **역할** 너는 10년 차 단타 트레이더의 코치다.
> **맥락** 아래는 오늘 내 매매 기록(종목·진입·청산·손익·메모)이다. 나는 손절 기준을 자주 어긴다.
> **형식** (1) 잘한 점 2개 (2) 고칠 점 2개 (3) 내일 지킬 규칙 1줄. 각 항목 한 문장, 총 150자 이내.
> **예시** 고칠 점은 "~했을 때 ~했다 → ~해야 했다" 꼴로.
> [기록 붙여 넣기]

**왜 중요한가**: 모델은 빠진 것을 **추측으로 채운다**(6-1). 역할이 없으면 평범한 어조, 형식이 없으면 긴 줄글, 예시가 없으면 내 취향과 다른 표현이 나온다. 네 요소는 추측할 여지를 줄이는 것이다.

### 2. 맥락은 "모델이 모르는 것" 위주로

맥락에는 **모델이 알 수 없는 내 상황**을 넣는다: 내 수준(비전공 초보), 내 목표(자동화 → 판매), 지금까지 한 것(이 저장소 구조), 제약(빌드 도구 없음, 한국어 주석). 이 저장소의 `CLAUDE.md`가 바로 "매번 자동으로 붙는 맥락"이다(8-3). 반대로 모델이 이미 아는 일반 지식("파이썬이란…")은 넣을 필요 없다. 토큰 낭비다.

### 3. 형식을 정하면 검증이 쉬워진다

"표로", "JSON으로", "번호 목록 3개", "코드만, 설명 없이", "150자 이내". 형식을 정하면 (1) 읽기 쉽고 (2) 다음 단계(코드로 처리, 다른 요청에 입력)에 바로 쓸 수 있고 (3) 빠진 항목이 바로 보인다. 10-2에서 "구조화된 출력"으로 이걸 강제한다.

### 4. 단계별로 시킨다

**한 줄 정의**: 큰 일을 한 번에 시키지 말고, **먼저 계획을 받고**, 승인한 뒤, 한 단계씩 실행시킨다.

**실제 예시**:
> 1단계: "AI 직원실 방을 어떻게 열지 **계획만** 5줄로. 파일 어디를 고칠지 포함. 아직 코드는 쓰지 마."
> 2단계: (계획을 읽고 고친 뒤) "1번 항목만 구현해. 끝나면 어떻게 확인하는지 알려 줘."
> 3단계: 확인 → 다음 항목.

Claude Code의 **플랜 모드**(8-4)가 이걸 기능으로 만든 것이다.

**왜 중요한가**: (1) 계획 단계에서 오해를 잡는다(싸다). (2) 한 단계가 작으면 검증이 쉽다(6-2). (3) 컨텍스트가 덜 찬다(6-1).

### 5. 생각할 시간을 준다

"바로 답하지 말고, 먼저 가능한 원인을 3개 나열한 뒤 가장 유력한 것부터 확인해." 모델에게 **중간 단계를 쓰게** 하면 복잡한 문제의 정확도가 오른다. 현재 Claude 모델은 스스로 생각(thinking)하는 기능이 있지만(6-1), 요청에서 단계를 명시하면 **내가 그 과정을 읽고 고칠 수 있다**는 장점이 따로 있다.

### 6. 결과가 나쁠 때 고치는 순서

1. **빠진 요소**가 있나? (역할·맥락·형식·예시 중 무엇이 없었나)
2. **자료**가 부족했나? (에러 전문, 코드, 문서를 안 붙였나 — 6-2)
3. **너무 컸나**? (쪼개서 단계별로)
4. **모호한 단어**가 있나? ("깔끔하게", "적당히" → 구체적 기준으로)
5. 그래도 안 되면 **모델을 바꾼다**(6-4). 모델 탓은 마지막이다.

### 7. 템플릿으로 만든다

자주 하는 요청은 빈칸이 있는 틀로 저장한다.

```
[매매 복기 코치]
역할: 10년 차 단타 트레이더 코치
맥락: 나는 {손절/추격매수/물타기} 습관이 문제. 오늘 기록은 아래.
형식: 잘한 점 2, 고칠 점 2, 내일 규칙 1. 총 150자.
예시: 고칠 점은 "~했을 때 ~했다 → ~해야 했다".
기록: {붙여 넣기}
```

7-2에서 이 틀을 claude.ai 스킬·프로젝트 지침으로, 9-2에서 Claude Code 스킬(`/복기`)로 옮긴다.

## 따라하기

### 1. 요청 고쳐 쓰기 (30분)

6-2 숙제 3의 "짧은 요청"을 꺼내 네 요소 틀로 다시 쓴다. 두 답을 나란히 놓고 무엇이 달라졌는지 세 가지 적는다.

### 2. 매매 복기 코치 템플릿 (40분)

7절의 템플릿을 내 습관에 맞게 고치고, 실제 오늘(또는 최근) 기록으로 돌려 본다. **계좌·이름은 뺀다**(6-2). 답의 형식이 요청대로 나왔는지 체크. 안 나왔으면 형식 문장을 더 구체적으로.

### 3. 단계별 시키기 (40분)

Claude Code에서 "AI 직원실 방을 열고 싶다. 계획만 5줄로, 코드는 쓰지 마"라고 요청 → 계획을 읽고 마음에 안 드는 항목을 고쳐 다시 요청 → "1번만 구현" → 확인. 실제로 구현까지 가도 되고(브랜치에서! 5-2), 계획까지만 하고 멈춰도 된다. 핵심은 **계획을 읽고 고치는 경험**.

### 4. 모호어 사냥 (20분)

내가 최근에 쓴 요청 5개에서 "깔끔하게", "적당히", "잘", "예쁘게", "간단하게" 같은 모호한 단어를 찾아 구체 기준으로 바꿔 본다. 예: "예쁘게" → "픽셀 테마 유지, 색은 style.css의 변수만, 글자 크기 14px 이상".

### 5. 템플릿 모음 시작 (20분)

`docs/prompts.md`를 만들어 템플릿 3개를 적는다: 매매 복기 코치, 코드 설명 요청("이 함수를 초보자에게 비유로 설명, 5줄"), 에러 해결 요청("에러 전문과 코드를 붙이고, 원인 후보 3개 → 확인 방법 → 수정안"). 7-2에서 스킬로 옮긴다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 한 줄 요청 | 평범하고 긴 답 | 네 요소 틀 |
| 한 번에 전부 | 큰 코드가 와서 검증 불가 | 계획 → 한 단계씩 |
| 모호한 형용사 | 내 취향과 다른 결과 | 측정 가능한 기준 |
| 에러를 말로 설명 | 추측 수정 | 에러 전문·코드 붙이기 |
| 답이 나쁘면 바로 모델 교체 | 같은 문제 반복 | 요청 점검 순서(6절)부터 |
| 템플릿 없이 매번 새로 씀 | 품질 들쭉날쭉 | 템플릿 파일 → 스킬 |

## 확인 퀴즈

**1. "이 코드 고쳐 줘"를 네 요소로 다시 써 보라(코드는 app.js의 renderMonth라고 가정).**

<details><summary>정답과 해설</summary>
예: 역할 "초보자 학습용 코드를 유지하는 시니어", 맥락 "app.js renderMonth()의 카테고리 막대 옆에 전체 지출 대비 비율(%)도 보이게 하고 싶다. 빌드 도구 없음, 한국어 주석", 형식 "변경 diff만, 설명 3줄", 예시 "주석은 '// 왜:' 로 시작". 정답은 하나가 아니고, 네 요소가 다 있는지가 기준.
</details>

**2. 단계별로 시키는 세 가지 이점.**

<details><summary>정답과 해설</summary>
오해를 계획 단계에서 싸게 잡음, 작은 단계라 검증이 쉬움, 컨텍스트 소모가 적음.
</details>

**3. 결과가 나쁠 때 모델을 바꾸는 것이 마지막인 이유는?**

<details><summary>정답과 해설</summary>
대부분의 실패 원인은 요청(빠진 요소, 자료 부족, 크기, 모호어)에 있어서 모델을 바꿔도 반복된다. 요청을 고치는 것이 더 싸고 재현 가능하다.
</details>

**4. 맥락에 넣지 말아야 할 것은?**

<details><summary>정답과 해설</summary>
모델이 이미 아는 일반 지식(토큰 낭비)과 비밀·개인정보(6-2). 넣을 것은 모델이 모르는 내 상황·제약·목표.
</details>

**5. 템플릿을 만들면 좋은 점과, 그것을 7·9과정에서 무엇으로 바꾸나?**

<details><summary>정답과 해설</summary>
품질이 일정해지고 매번 네 요소를 다시 생각하지 않아도 된다. claude.ai에서는 프로젝트 지침·스킬(7-2), Claude Code에서는 스킬 명령(9-2)으로 바꾼다.
</details>

## 숙제

1. **템플릿 5개** — `docs/prompts.md`에 템플릿을 5개로 늘려라. 하나는 "이 단원 퀴즈를 나에게 다시 내 줘" 같은 공부용.
2. **일주일 실험** — 매일 요청 하나를 네 요소로 고쳐 쓰고, 전·후 답을 비교한 메모를 남겨라. 7일 뒤 가장 효과 큰 요소가 무엇이었는지 한 줄.
3. **6-4 예습** — claude.ai에서 모델 선택 메뉴를 열어 어떤 모델이 있는지 적어 두라. ChatGPT·Gemini도 같은 메뉴를 확인.
