## 이 단원을 마치면

- 환각(hallucination)이 "버그"가 아니라 다음 토큰 예측의 **자연스러운 부작용**이라는 것을 설명할 수 있다.
- 환각이 특히 잘 나오는 질문 유형 5가지를 알고, 질문을 던지기 전에 알아챌 수 있다.
- AI 답변을 검증하는 세 가지 방법(실행해 보기, 출처 대조, 다른 모델에 반대 질문)을 상황에 맞게 고를 수 있다.
- 개인정보·비밀·저작권에서 "AI에게 주면 안 되는 것"과 "AI가 준 것을 그대로 쓰면 안 되는 것"을 구분할 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

바이브 코딩의 위험은 코드가 틀리는 게 아니라 **틀린 코드가 그럴듯하게 보이는 것**이다. 존재하지 않는 함수, 없는 명령 옵션, 틀린 API 경로를 AI는 자신 있게 쓴다. 매매로 치면 "확신에 찬 잘못된 추천"이다. 트레이더는 이미 "확신은 근거가 아니다"를 안다. 그 감각을 AI에 그대로 적용하는 단원이다. 그리고 내 계좌번호·매매 기록·키를 AI에 어디까지 줄지, 받은 코드를 상업적으로 써도 되는지는 공부 초반에 정해 두는 게 안전하다.

## 핵심 개념

### 1. 환각은 기능의 그림자다

**한 줄 정의**: 환각은 모델이 **모르는 것을 모른다고 하지 않고** 그럴듯한 내용을 만들어 내는 현상이다.

**비유**: 시험에서 모르는 문제를 빈칸으로 두지 않고 그럴듯하게 채우는 학생. 글씨가 또렷하다고 정답은 아니다.

**실제 예시** — 코딩에서 자주 보는 환각:
- 없는 함수: `requests.get_json()` (실제는 `response.json()`)
- 없는 옵션: `git commit --undo`
- 틀린 경로: 증권사 API의 엔드포인트나 `tr_id`를 비슷하게 지어냄
- 옛 정보: 바뀐 라이브러리 사용법을 컷오프 시점 기준으로 설명(6-1)
- 인용 조작: 존재하지 않는 문서 URL, 논문 제목

**왜 중요한가**: 환각은 모델이 "나쁜 날"이라 나오는 게 아니다. 질문이 **모델이 모르는 영역**(최신, 희귀, 세부 수치, 내 개인 상황)으로 들어갈수록 확률이 오른다. 그러니 "환각이 나올 질문인가"를 먼저 판단한다.

### 2. 환각이 잘 나오는 질문 5유형

| 유형 | 예 | 대처 |
|---|---|---|
| 최신·날짜 의존 | "지금 Claude Code 최신 명령어는?" | 공식 문서 붙이기, 검색 켜기 |
| 정확한 수치·인용 | "이 함수의 기본 타임아웃 값은?" | 문서 원문 확인 |
| 희귀한 조합 | "한국투자증권 API + 특정 라이브러리 조합" | 공식 샘플을 먼저 읽히기 |
| 내 상황에 대한 추정 | "내 코드가 왜 안 되는지" (코드를 안 보여 줌) | 코드·에러 전문을 그대로 붙이기 |
| 자기 능력에 대한 질문 | "너 이거 확실해?" | 모델의 자기 평가는 근거가 아님. 실행·대조로 확인 |

### 3. 검증 세 가지

**(1) 실행해 본다** — 코드는 돌려 보면 안다. 가장 싸고 확실하다. 작은 단위로 시키고 바로 실행하는 것이 바이브 코딩의 기본 루프(12-1).

**(2) 출처와 대조한다** — 명령어·옵션·API는 공식 문서에서 그 줄을 찾는다. 이 커리큘럼이 "확인일"과 URL을 적는 이유. Claude Code에게 "공식 문서 URL을 가져와서 그 페이지 기준으로 다시 답해"라고 시킬 수 있다.

**(3) 반대로 묻는다** — 같은 질문을 다른 모델(ChatGPT, Gemini)에게, 또는 같은 모델에게 "이 답에서 틀렸을 수 있는 부분을 찾아 봐"라고 묻는다. 두 답이 다르면 둘 중 하나가(또는 둘 다) 틀렸다는 신호. **같다고 맞는 건 아니다**(둘 다 같은 자료로 학습됐을 수 있다).

**왜 중요한가**: 검증 비용은 작고, 안 한 비용은 크다. 잘못된 주문 코드 하나가 실제 돈이다.

### 4. 개인정보와 비밀: 주지 않는다

AI 서비스에 입력한 내용은 **서비스 약관에 따라** 저장·검토·학습에 쓰일 수 있다. 무엇이 쓰이는지는 서비스·플랜마다 달라서 **공식 개인정보 처리방침을 직접 읽어야** 한다(아래 더 보기). 그 전까지 안전한 기본 규칙:

- **절대 안 줌**: API 키, 비밀번호, 계좌번호 전체, 주민번호, 인증서. (4-2)
- **가명으로**: 매매 복기를 분석시킬 때 종목·금액은 그대로여도 되지만, 계좌·이름·연락처는 뺀다.
- **클라우드 세션**: Claude Code 웹 세션은 내 저장소를 클라우드 컴퓨터로 가져간다. `.env`가 저장소에 없으면 올라가지 않는다. 그래서 `.gitignore`가 중요했다.
- **설정 확인**: claude.ai 설정에서 데이터 사용 관련 옵션을 확인하고 원하는 대로 설정한다(7-1).

### 5. 저작권과 책임: 받은 것을 그대로 쓰지 않는다

- AI가 만든 코드·글의 **저작권 처리는 나라와 서비스마다 다르고 아직 정리 중**이다. 상업적으로 쓰기 전에 서비스 약관(사용 권한 조항)을 읽고, 중요한 결정은 전문가에게 확인한다.
- AI가 **남의 코드를 거의 그대로** 내놓을 수도 있다(학습 데이터에 있던 것). 라이선스가 있는 코드(GPL 등)를 모르고 섞으면 13과정 판매 때 문제가 된다. 긴 코드 블록이 "너무 완성돼" 보이면 출처를 물어보고, 오픈소스를 쓸 때는 라이선스를 확인한다(12-2).
- 책임은 내게 있다. "AI가 짰다"는 변명이 되지 않는다. 4-3의 증권사 면책 문구와 같은 논리다.

### 6. 안전한 사용 습관 요약

1. 질문 전에: 환각 유형인가? → 자료를 붙인다.
2. 답을 받으면: 실행 / 출처 / 반대 질문 중 하나 이상.
3. 입력 전에: 비밀·개인정보가 섞여 있나? → 지우거나 가명.
4. 쓰기 전에: 상업 이용·라이선스 문제 없나? → 약관·라이선스 확인.
5. 틀린 답을 받으면: 모델 탓보다 **질문에 자료가 부족했나**를 먼저 본다(6-3).

## 따라하기

### 1. 환각 유도 실험 (30분)

claude.ai(검색 끄고)에 다음을 물어 본다.
- "파이썬 requests 라이브러리의 `get_json()` 함수 사용법 알려 줘" (없는 함수)
- "git에서 마지막 커밋을 취소하는 `--undo` 옵션 설명해 줘" (없는 옵션)
모델이 "그런 건 없다"고 바로잡으면 좋은 신호, 그럴듯하게 설명하면 환각. 두 경우 모두 **공식 문서에서 확인**하는 데까지 해 본다.

### 2. 세 가지 검증 돌려 보기 (40분)

6-1 숙제 3에서 저장한 "자신 있게 틀린 답"을 꺼낸다(없으면 1번 실험 결과).
- 실행: 코드라면 돌려 본다.
- 출처: 관련 공식 문서 페이지를 찾아 해당 내용을 확인한다.
- 반대 질문: 같은 모델에게 "이 답에서 틀린 부분을 찾아 줘"라고 묻고, 다른 모델에게도 같은 질문을 한다.
세 방법 중 어느 것이 가장 빨리 틀림을 잡았는지 메모.

### 3. 내 데이터 분류표 (30분)

내가 AI에 넣을 법한 것들을 세 칸으로 나눠 적는다: **절대 안 줌 / 가명으로 / 그대로 줘도 됨**. 예: API 키(절대), 매매 복기(가명), 이 저장소 코드(그대로). 이 표를 `docs/ai-data-policy.md`로 저장해 두면 7과정에서 템플릿 만들 때 쓴다.

### 4. 약관 읽기 (20분)

claude.ai의 개인정보 처리방침과 이용약관 페이지에서 "입력 데이터가 어떻게 쓰이는지"와 "출력물의 사용 권한" 부분을 찾아 읽는다. 어려운 문장은 Claude에게 "이 조항을 쉬운 말로 설명해 줘"라고 시킨다. **단, 그 설명도 원문과 대조한다.** 이 단원의 핵심이다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 자신 있는 말투를 근거로 믿음 | 틀린 코드·수치 사용 | 말투와 정확도는 무관. 실행·출처로만 판단 |
| "확실해?"라고 되물음 | 모델이 또 자신 있게 답함 | 자기 평가 대신 문서 원문을 요구 |
| 에러를 설명으로만 전달 | 모델이 추측으로 고침 | 에러 메시지 전문과 코드를 그대로 붙임 |
| 매매 기록을 통째로 업로드 | 계좌·이름 노출 | 필요한 열만, 식별 정보 제거 |
| AI 코드를 상업 제품에 그대로 | 라이선스 분쟁 가능 | 약관·라이선스 확인, 긴 블록은 출처 질문 |

## 확인 퀴즈

**1. 환각이 "버그가 아니라 부작용"이라는 말의 뜻은?**

<details><summary>정답과 해설</summary>
모델은 사실 여부가 아니라 그럴듯함으로 다음 토큰을 고르는 구조라서, 모르는 것도 그럴듯하게 채우는 것이 그 구조의 자연스러운 결과라는 뜻. 고쳐서 없애는 것이 아니라 검증으로 다루는 대상이다.
</details>

**2. 다음 질문 중 환각 위험이 가장 높은 것은? (a) "for 반복문 설명해 줘" (b) "한국투자증권 API에서 해외주식 잔고 조회 tr_id 알려 줘" (c) "이 함수 이름 더 좋게 지어 줘"**

<details><summary>정답과 해설</summary>
(b). 희귀하고 정확한 식별자이며 바뀔 수 있는 정보다. 공식 샘플 저장소에서 찾아야 한다. (a)와 (c)는 언어 작업이라 모델이 잘한다.
</details>

**3. 두 모델이 같은 답을 했다. 맞다고 봐도 되나?**

<details><summary>정답과 해설</summary>
아니다. 같은 자료로 학습됐으면 같은 오류를 공유할 수 있다. 일치는 신호일 뿐, 확인은 실행과 공식 출처로 한다.
</details>

**4. 매매 복기 CSV를 AI에게 분석시키려 한다. 지우거나 바꿔야 할 열은?**

<details><summary>정답과 해설</summary>
계좌번호, 이름, 연락처 등 식별 정보. 종목·수량·가격·메모는 분석에 필요하면 남긴다. 서비스의 데이터 처리 방침도 확인한다.
</details>

**5. AI가 만든 코드를 유료 앱에 넣기 전에 확인할 두 가지.**

<details><summary>정답과 해설</summary>
(1) 서비스 약관의 출력물 사용 권한 (2) 코드에 섞였을 수 있는 오픈소스 라이선스. 불확실하면 전문가 확인.
</details>

## 숙제

1. **환각 노트 시작** — `docs/hallucination-log.md`를 만들어, 앞으로 AI가 틀린 것을 발견할 때마다 "질문 / 틀린 답 / 실제 / 어떻게 잡았나"를 한 줄씩 적어라. 한 달 뒤 유형을 세어 본다.
2. **데이터 정책 확정** — 따라하기 3의 표를 완성해 저장소에 커밋하라. 7과정 템플릿의 머리말로 쓴다.
3. **6-3 예습** — 같은 질문을 "짧게" 한 번, "맥락·형식·예시를 넣어" 한 번 던져 보고 답의 차이를 저장해 두라.
