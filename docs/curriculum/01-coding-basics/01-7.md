# 1-7. 에러와 디버깅: 에러 메시지 읽는 법, console.log, 브라우저 디버거, 검색하고 AI에게 묻는 법

| 과정 | 1. 코딩의 기본 개념 (JavaScript로) |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 1-6 |
| 경험치 | 60 |

## 이 단원을 마치면

- 빨간 에러 메시지를 "종류 / 설명 / 파일:줄:칸" 세 조각으로 읽고, 어느 줄을 봐야 하는지 바로 찾는다.
- `ReferenceError`, `TypeError`, `SyntaxError`가 각각 무슨 뜻인지 알고 원인을 추측할 수 있다.
- `console.log`를 의심 지점에 꽂아 "지금 이 값이 뭔지" 확인하는 추적을 할 수 있다.
- 브라우저 디버거에서 중단점(breakpoint)을 찍고 멈춘 자리의 변수 값을 볼 수 있다.
- `try...catch`로 프로그램이 죽지 않게 막을 수 있다.
- 검색엔진과 클로드에게 **답이 나오는 질문**을 쓸 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

코딩 시간의 절반은 "왜 안 되지?"에 쓰인다. 클로드가 코드를 써 줘도 마찬가지다. 실행해 보면 에러가 나고, 안 나더라도 결과가 이상할 때가 있다. 그 순간 두 종류의 사람이 갈린다. 에러 메시지를 읽고 줄 번호를 찾아 `console.log`를 꽂는 사람과, "안 돼요"라고만 하는 사람.

매매로 치면 복기다. "왜 손실이 났지?"를 체결 내역(에러 메시지), 당시 차트(변수 값), 내 규칙(코드)으로 되짚는 것. 디버깅(debugging)은 그 복기를 코드에 하는 것이다. 이 단원의 기술은 2과정부터 매일 쓰고, 8과정에서 Claude Code에게 버그를 설명할 때 그대로 쓰인다. 이걸 못 하면 AI에게 "안 돼요"밖에 못 말한다.

## 핵심 개념

### 1. 에러의 두 종류

**한 줄 정의.** MDN 입문 문서는 에러를 둘로 나눈다. **구문 오류**는 "코드에 잘못된 철자가 있으면 발생하는 오류로, 프로그램이 아예 구동하지 못하거나 중간에 멈춰버리는 현상을 일으키며, 모종의 오류 메시지도 나타"난다. **논리 오류**는 "구문은 올바르지만 의도한 동작과 실제 코드에 차이가 있는 경우"로 "프로그램은 성공적으로 돌아가지만 잘못된 결과를 낳"고, "보통 오류를 직접 가리키는 메시지가 없기 때문에 구문 오류보다 고치기도 힘든 편"이다.

### 2. 에러 메시지 읽기: 세 조각

**한 줄 정의.** 콘솔의 빨간 메시지는 `[Uncaught] 에러종류: 설명` 한 줄과 `파일:줄:칸` 위치로 이루어진다.

MDN 예제 그대로 보자.

```
Uncaught TypeError: guessSubmit.addeventListener is not a function
number-game-errors.html:86:15
```

MDN의 해설: 첫 부분은 "무엇이 잘못되었는지를 알"려 주고, 둘째 부분은 "코드에서 오류가 발생한 위치를 알려줍니다. 'number-game-errors.html' 파일의 86번째 줄, 15번째 문자입니다." 크롬에서는 이 위치가 **링크**라서 클릭하면 Sources 탭의 그 줄로 바로 간다. `Uncaught`는 "아무도 안 잡은(처리 안 한) 에러"라는 뜻이다(5번 항목의 `try...catch`가 잡는 것).

**자주 보는 세 종류.**

| 종류 | 대표 메시지 | 뜻 (MDN 오류 참고서) | 먼저 의심할 것 |
|---|---|---|---|
| `ReferenceError` | `x is not defined` | "존재하지 않는 변수를 참조하는 곳이 있습니다" | 이름 오타, 대소문자, 스코프 밖(1-5), 선언 전 사용 |
| `TypeError` | `x is not a function` | 함수가 아닌 값을 호출함. "보통 이 오류는 철자를 잘못 적은 경우 발생" | 메서드 이름 오타(`getElementByID`), 배열이 아닌 것에 `map` |
| `TypeError` | `Cannot read properties of undefined (reading 'y')` | `undefined`/`null`의 속성을 읽음 | `find`가 못 찾음, `getElementById`가 `null`, 인수 빠뜨림 |
| `SyntaxError` | `Unexpected token`, `missing ) after argument list` | 문법이 틀려 아예 실행 못 함 | 괄호·따옴표 짝, 쉼표, `JSON.parse`에 깨진 문자열 |

**왜 중요한가.** 에러의 80%는 메시지 첫 줄과 줄 번호만으로 원인이 보인다. 읽지 않고 고치려 드는 게 가장 큰 시간 낭비다.

### 3. `console.log`로 추적하기

**한 줄 정의.** 의심되는 지점 **바로 뒤**에 `console.log("라벨", 값)`을 넣어 그 시점의 값을 보는 것이 가장 기본적인 디버깅이다.

MDN 입문 문서가 정확히 이 방법으로 논리 오류를 잡는다. 변수 `lowOrHi`가 이상하면 그 변수를 만든 줄 **다음에** `console.log(lowOrHi);`를 넣고 새로고침해 `null`이 찍히는 걸 확인한 뒤, 그 줄의 선택자 오타(`.lowOrHi`여야 하는데 `.`이 빠짐)를 찾는다. 난수가 항상 1이 나오는 논리 오류도 `console.log(randomNumber);`로 잡는다.

**요령.** (1) 라벨을 붙인다: `console.log("balance before:", balance)`. (2) 값이 "들어오는" 지점과 "나가는" 지점 양쪽에 찍어 어디서 틀어지는지 좁힌다. (3) 객체 배열은 `console.table`. (4) 오류성 메시지는 `console.error`(빨갛게 표시되고 호출 경로가 함께 나온다). (5) 다 고치면 지운다.

### 4. 브라우저 디버거(debugger)와 중단점

**한 줄 정의.** 디버거는 코드를 지정한 줄에서 **멈추고**, 그 순간의 변수 값과 호출 경로를 보여주는 도구다. MDN: "JavaScript 디버거를 사용하면 변수의 값을 관찰하고 중단점(코드 실행을 일시 중지하고 문제를 식별하려는 지점)을 설정할 수 있습니다."

**여는 법.** 개발자 도구에서 **Sources** 탭(크롬. Firefox는 Debugger 탭). 왼쪽 파일 목록에서 `app.js`를 고른다. 가운데 코드에서 **줄 번호를 클릭**하면 중단점이 찍힌다(MDN: "Click on the line number in the center panel to add a breakpoint"). 새로고침하거나 그 줄이 실행되는 동작을 하면 거기서 멈춘다. 오른쪽에 **Scope**(지금 보이는 변수와 값), **Call Stack**(어떤 함수가 어떤 함수를 불러 여기까지 왔는지)이 보인다. 위쪽 ▶ 버튼으로 계속 진행한다.

코드에 `debugger;`라고 적어도 같은 효과다(MDN: "디버거가 활성화되면 디버거 문의 위치에서 실행이 일시중지됩니다. 스크립트 소스의 중단점과 비슷합니다"). 개발자 도구가 닫혀 있으면 무시된다.

### 5. `try...catch`: 에러를 잡아 프로그램 살리기

**한 줄 정의.** `try { 위험한 코드 } catch (error) { 실패했을 때 할 일 }`은 `try` 안에서 에러가 나면 프로그램을 멈추는 대신 `catch`로 넘긴다. MDN: "`try` 블록 내 코드가 먼저 실행되고, 만약 그 안에서 예외가 발생한다면 `catch` 블록 내 코드가 실행됩니다." `try` 안에서 에러가 없으면 `catch`는 실행되지 않는다. `finally`를 붙이면 "예외가 발생했는지 여부와 관계없이 항상 실행"된다.

**실제 예시.** `app.js`의 `load()`는 저장된 문자열이 깨져 있으면 `JSON.parse`가 `SyntaxError`를 던지고(1-6), 그 줄에서 스크립트가 멈춰 앱 전체가 죽는다. 이렇게 막는다.

```js
function load() {
  const saved = localStorage.getItem(STORAGE_KEY);
  if (!saved) return;
  try {
    entries = JSON.parse(saved);
  } catch (error) {
    console.error("저장된 내역을 읽지 못했습니다:", error);
    entries = [];          // 깨진 데이터는 버리고 빈 상태로 시작
  }
}
```

**주의.** `try...catch`는 외부에서 오는 믿을 수 없는 것(저장소, 네트워크, 입력)에 쓰는 것이지 내 버그를 **감추는** 데 쓰면 안 된다. 빈 `catch`는 에러를 논리 오류로 바꾼다. 최소한 `console.error`는 남긴다. Claude Code 모범 사례 문서도 "근본 원인을 고치고, 에러를 억누르지 말라(address the root cause, don't suppress the error)"고 적는다.

### 6. 검색하는 법

MDN 입문 문서의 조언: "현재 가장 좋은 방법은 자주 사용하는 검색 엔진에서 'mdn 기능 이름'으로 검색하는 것입니다." 예: `mdn array filter`. 에러는 **메시지를 그대로** 검색하되 내 파일명·줄 번호·변수명은 뺀다: `TypeError: Cannot read properties of undefined (reading 'textContent')`. MDN·공식 문서·Stack Overflow 채택 답변을 먼저 보고, 블로그는 날짜를 확인한다.

### 7. AI에게 묻는 법

**한 줄 정의.** 좋은 질문에는 네 가지가 들어 있다. (1) **하려던 것**, (2) **한 것**(고친 코드 또는 코드 전체), (3) **나온 것**(에러 메시지 전문, 또는 "기대 vs 실제"), (4) **이미 해 본 것**.

Claude Code 문서의 예가 정확히 이 원칙이다. 빠른 시작 문서는 "fix the bug" 대신 "fix the login bug where users see a blank screen after entering wrong credentials"처럼 **구체적으로** 쓰라고 한다. 모범 사례 문서는 증상·위치·완료 기준을 함께 적으라고 한다. "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it". 일반 워크플로 문서의 버그 수정 절차는 (1) 에러를 공유하고 (2) 수정 방안을 묻고 (3) 적용하는 세 단계이며, "재현하는 명령과 스택 트레이스를 알려 주라", "간헐적인지 항상 나는지 말해 주라"고 조언한다.

**스크린샷도 된다.** claude.ai는 `+` 버튼 → "Add files or photos", 드래그 앤 드롭, 클립보드 붙여넣기로 이미지(JPEG, PNG, GIF, WebP)를 올릴 수 있다(Claude 고객지원 문서). 다만 **텍스트를 복사할 수 있으면 텍스트**가 낫다.

**받은 답은 검증한다.** 고쳐 준 코드를 붙여넣고 새로고침해 **직접** 확인한다. Claude Code 모범 사례 문서: "검증할 수 없으면 배포하지 말라(If you can't verify it, don't ship it)".

**질문 템플릿.**

```
[하려던 것] 가계부 잔액 아래에 "수입/지출 합계"를 보여주려고 한다.
[한 것] app.js의 render()에 아래 두 줄을 추가했다. (코드 붙여넣기)
[나온 것] 새로고침하면 콘솔에 이 에러가 뜬다:
  Uncaught TypeError: Cannot set properties of null (setting 'textContent')  app.js:118
[해 본 것] index.html에 id="summary"를 넣었다고 생각했는데, 확인해 달라.
[원하는 것] 원인과 고친 코드. 왜 그런지 한 줄 설명도.
```

## 따라하기

재료: `app.js`, 콘솔, Sources 탭. 실습마다 고친 뒤에는 **원래대로 되돌린다**.

### 실습 1. 세 가지 에러를 일부러 만들고 읽기 (25분)

**(a) TypeError: not a function.** `deleteEntry` 안의 `entries.filter(`를 `entries.filtr(`로 바꾼다. 저장, 새로고침, 내역 하나의 × 를 누른다. 콘솔에 `Uncaught TypeError: entries.filtr is not a function`과 `app.js:NN`이 뜬다. 종류(함수가 아닌 것을 호출), 설명(`filtr`라는 메서드는 없다), 줄 번호를 읽고, 오른쪽 링크를 클릭해 그 줄로 간다. 고친다.

**(b) SyntaxError.** `calculateBalance`의 마지막 `}`를 지운다. 저장, 새로고침. 앱이 아예 동작하지 않고 `SyntaxError`가 뜬다. 줄 번호가 지운 자리가 아니라 파일 끝 근처를 가리킬 수 있다는 점을 본다(괄호 짝은 "어디서 부족한지"를 끝에 가서야 안다). VS Code에서 `{`를 클릭하면 짝이 강조되는 기능으로 찾는다. 고친다.

**(c) TypeError: Cannot read properties of null.** `index.html`에서 `id="balance"`를 `id="balanc"`로 바꾼다. 새로고침. `Cannot set properties of null (setting 'textContent')`가 뜬다. 자바스크립트는 멀쩡한데 HTML의 id가 틀려서 `getElementById`가 `null`을 돌려준 것이다. 에러가 난 줄(`balanceText.textContent = ...`)이 아니라 **그 변수를 만든 줄**(2번 구역)과 HTML을 봐야 한다는 걸 체감한다. 고친다.

### 실습 2. 논리 오류를 `console.log`로 잡기 (15분)

`calculateBalance`에서 `+`와 `-`를 서로 바꾼다. 에러는 없는데 잔액이 반대로 나온다. 이제 `for` 안에 `console.log(entry.type, entry.amount, "→", balance);`를 넣고 새로고침. 수입인데 잔액이 줄어드는 줄이 보인다. 원인을 찾았으면 고치고 `console.log`를 지운다.

### 실습 3. 디버거로 멈춰 보기 (20분)

1. 개발자 도구 → **Sources** → 왼쪽에서 `app.js` 클릭.
2. `calculateBalance`의 `if (entry.type === "income")` 줄 번호를 클릭(파란 표시).
3. 새로고침. 그 줄에서 멈춘다. 오른쪽 **Scope**에서 `entry`를 펼쳐 지금 처리 중인 내역을, `balance`에서 누적 중인 값을 본다. **Call Stack**에서 `calculateBalance` ← `render` ← (최상위)를 읽는다.
4. ▶(Resume)을 누르면 다음 바퀴에서 또 멈춘다. `balance`가 어떻게 변하는지 본다.
5. 줄 번호를 다시 클릭해 중단점을 지운다.

### 실습 4. `try...catch`로 앱 살리기 (20분)

1. 콘솔에서 저장소를 일부러 깨뜨린다: `localStorage.setItem("ledger-entries", "{깨진 데이터")`.
2. 새로고침. `SyntaxError`가 뜨고 앱이 죽는다(버튼이 안 먹는다). `load()`의 `JSON.parse`에서 멈춘 것이다.
3. `load()`를 5번 항목의 코드로 바꾼다. 저장, 새로고침. 콘솔에 `console.error` 메시지는 남지만 앱은 빈 목록으로 살아난다.
4. 정리: `localStorage.removeItem("ledger-entries")`로 깨진 데이터를 지운 뒤 내역을 다시 넣는다.

### 실습 5. 클로드에게 제대로 묻기 (20분)

실습 1의 (c) 상황을 다시 만든 뒤(`id="balanc"`), 7번 항목의 템플릿으로 질문을 써서 claude.ai에 보낸다. 코드는 `app.js` 2번 구역과 `render()`의 해당 줄, `index.html`의 잔액 카드 부분만 붙인다(전체를 다 붙이지 않아도 된다). 답을 받으면 **직접 고쳐서 새로고침**으로 확인한다.

## 흔한 실수와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| 에러를 봤는데 뭘 해야 할지 모름 | 첫 줄을 안 읽음 | 종류 / 설명 / 파일:줄 세 조각으로 읽고 줄 링크를 클릭 |
| 고쳤는데 그대로 에러 | 저장 안 함, 새로고침 안 함, 캐시 | `Ctrl+S` → `F5`. 그래도 안 되면 `Ctrl+Shift+R` |
| `try...catch` 후 조용히 이상 동작 | `catch`가 비어 있어 에러가 숨음 | 최소 `console.error`. 근본 원인을 고친다 |
| AI가 엉뚱한 답을 줌 | 에러 전문·코드·맥락 없이 물음 | 4요소 템플릿. 텍스트로 복사 |
## 확인 퀴즈

**1. `Uncaught TypeError: entries.filter is not a function  app.js:62:21`을 세 조각으로 나누어 읽고, 가장 먼저 의심할 것을 말하라.**

<details><summary>정답과 해설</summary>

종류 `TypeError`, 설명 `entries.filter is not a function`(함수가 아닌 것을 호출), 위치 `app.js` 62번째 줄 21번째 글자. `filter`는 배열 메서드이므로 `entries`가 배열이 아닌 상태(예: `JSON.parse` 결과가 객체이거나 `null`)일 가능성을 먼저 의심한다. 62번째 줄 앞에 `console.log(typeof entries, entries)`를 꽂아 확인한다.
</details>

**2. 구문 오류와 논리 오류의 차이, 그리고 각각을 잡는 1차 도구는?**

<details><summary>정답과 해설</summary>

구문 오류는 문법이 틀려 실행이 멈추고 메시지가 뜬다 → 메시지와 줄 번호. 논리 오류는 실행은 되지만 결과가 틀리고 메시지가 없다 → `console.log`나 디버거로 중간값을 확인해 어디서 틀어지는지 좁힌다.
</details>

**3. `load()`에 `try...catch`를 넣는 것은 좋은데, `calculateBalance()` 전체를 `try...catch`로 감싸고 `catch`를 비워 두는 것은 왜 나쁜가?**

<details><summary>정답과 해설</summary>

`load()`는 외부(저장소)에서 온 믿을 수 없는 데이터를 다루므로 실패에 대비하는 게 맞다. 반면 `calculateBalance()`의 에러는 내 코드의 버그이고, 빈 `catch`는 그 버그를 숨겨 "에러 없이 틀린 잔액"이라는 더 나쁜 논리 오류로 바꾼다. 에러는 억누르지 말고 근본 원인을 고친다.
</details>

**4. 디버거의 Scope와 Call Stack은 각각 무엇을 보여주는가?**

<details><summary>정답과 해설</summary>

Scope는 멈춘 지점에서 보이는 변수들과 그 값(지역/블록/전역). Call Stack은 어떤 함수가 어떤 함수를 불러 여기까지 왔는지의 경로(예: `calculateBalance` ← `render`). 전자는 "지금 값이 뭔가", 후자는 "여기 어떻게 왔나"에 답한다.
</details>

**5. "잔액이 안 나와요"를 답이 나오는 질문으로 바꿔라.**

<details><summary>정답과 해설</summary>

하려던 것(잔액 표시), 한 것(고친 코드 붙여넣기), 나온 것(에러 메시지 전문과 줄 번호, 또는 기대값 vs 실제값), 해 본 것(확인한 내용)을 적고, 원하는 답의 형태(원인 + 고친 코드 + 한 줄 설명)를 말한다. 텍스트로 복사할 수 있는 것은 스크린샷보다 텍스트로.
</details>
