# 4-1. HTTP와 REST API: 요청/응답, 메서드, 상태 코드, 헤더, JSON 본문

| 과정 | 4. 데이터와 API, 자동화 |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 3-6 |
| 경험치 | 60 |

## 이 단원을 마치면

- HTTP 요청 한 통과 응답 한 통이 각각 어떤 부품(시작 줄·헤더·본문)으로 되어 있는지 종이에 그릴 수 있다.
- GET/POST/PUT/PATCH/DELETE 메서드가 각각 무슨 뜻인지, 주식 주문(조회·신규·정정·취소)에 빗대어 설명할 수 있다.
- 상태 코드를 2xx/3xx/4xx/5xx로 나눠 읽고, 401·403·404·429·500을 보고 "누구 책임이고 다시 시도해도 되는지"를 판단할 수 있다.
- URL의 쿼리 문자열, 헤더(Content-Type, Accept, Authorization), JSON 본문이라는 세 가지 '데이터 전달 통로'를 구분한다.
- 처음 보는 API 문서를 열어 기본 주소·엔드포인트·메서드·파라미터·응답 모양·호출 한도 여섯 가지를 찾아낼 수 있다.
- 터미널(curl / Invoke-RestMethod)과 파이썬(requests)으로 공개 API를 호출하고 상태 코드·헤더·본문을 눈으로 확인한다.

## 왜 배우나 (나에게 어떤 쓸모)

4과정에서 만날 것들을 나열해 보자. 공공데이터포털의 주가·환율 데이터, 한국투자증권 Open API의 시세 조회와 주문, 텔레그램 봇 알림, 그리고 10과정의 Claude API. 서비스는 전부 다르지만 **대화하는 방식은 하나**다. HTTP(HyperText Transfer Protocol)라는 규격으로 "요청 한 통"을 보내고 "응답 한 통"을 받는다. 2-6에서 `fetch`로, 3-5에서 `requests`로 이미 호출은 해 봤다. 그때는 "어떻게 부르나"를 배웠고, 이 단원은 "그 안에 **무엇이** 오가나"를 배운다.

왜 안을 알아야 할까. 클로드에게 "한투 API로 삼성전자 현재가 가져오는 코드 짜 줘"라고 하면 코드는 금방 나온다. 문제는 그 코드가 401을 뱉을 때다. 헤더가 빠졌는지, 토큰이 만료됐는지, 메서드가 틀렸는지, 호출 한도를 넘었는지는 **요청과 응답을 읽을 줄 아는 사람**만 가려낼 수 있다. AI가 짜 준 코드를 검증하는 눈이 이 단원의 목표다.

주식 비유로는 **주문 전표**다. HTS 화면 뒤에서 증권사 서버와 주고받는 전문(電文)에는 정해진 칸이 있다. 어느 계좌가(헤더), 무엇을(경로), 어떻게(메서드), 얼마에 몇 주(본문) 사겠다고 적고, 돌아온 전표에는 접수·거부·오류 코드(상태 코드)가 찍힌다. 전표 양식을 한 번 익히면 창구가 바뀌어도(증권사, 공공기관, 텔레그램, Anthropic) 같은 양식으로 통한다.

## 핵심 개념

### 1. HTTP: 요청 한 통, 응답 한 통

**한 줄 정의.** MDN 한국어 'HTTP 개요': "HTTP는 HTML 문서와 같은 리소스들을 가져올 수 있도록 해주는 프로토콜입니다." 여기서 리소스(resource)는 문서뿐 아니라 JSON 데이터, 이미지, 무엇이든 서버가 내주는 것이다. 그리고 "클라이언트-서버 프로토콜이란 (보통 웹브라우저인) 수신자 측에 의해 요청이 초기화되는 프로토콜을 의미합니다." 즉 **항상 내 쪽(클라이언트)이 먼저 말을 걸고**, 서버는 대답만 한다.

**비유.** 은행 창구. 번호표를 뽑고(연결), 전표를 내고(요청), 창구 직원이 처리해서 영수증을 준다(응답). 중요한 성질이 하나 더 있다. MDN: "HTTP는 상태를 저장하지 않습니다(Stateless)." 창구 직원은 **매번 당신을 처음 보는 사람처럼** 대한다. 방금 전에 신분증을 보여 줬어도 다음 전표에 또 붙여야 한다. 그래서 4-3의 증권사 API는 **모든 요청마다** 토큰·앱키 헤더를 다시 붙인다. 귀찮지만 이 덕분에 서버는 수백만 명을 기억할 필요가 없다.

**실제 예시.** 요청과 응답을 글자 그대로 펼치면 이렇게 생겼다(2-6에서 호출한 GitHub API).

```http
GET /repos/mdn/content HTTP/1.1
Host: api.github.com
Accept: application/vnd.github+json
User-Agent: my-ledger-app
```

```http
HTTP/1.1 200 OK
content-type: application/json; charset=utf-8
x-ratelimit-remaining: 59

{"id": 123, "name": "content", "stargazers_count": 1234, ...}
```

MDN 'HTTP 메시지'에 따르면 요청의 "시작 줄은 다음과 같이 세 가지 요소로 이루어져 있습니다": 메서드(`GET`), 요청 타겟(`/repos/mdn/content`), HTTP 버전(`HTTP/1.1`). 그 아래 줄들이 헤더, 빈 줄 다음이 본문이다. "모든 요청에 본문이 들어가지는 않습니다." 조회(GET)는 보통 본문이 없다. 응답은 "HTTP 응답의 시작 줄은 '상태 줄(status line)'이라고 불리며" 버전·상태 코드·상태 텍스트(`HTTP/1.1 404 Not Found` 같은 꼴)로 되어 있다. 응답도 "모든 응답에 본문이 들어가지는 않습니다." MDN은 201, 204 응답이 보통 본문이 없다고 적는다.

| 부품 | 요청(내가 보냄) | 응답(서버가 보냄) |
|---|---|---|
| 시작 줄 | 메서드 + 경로 + 버전 | 버전 + 상태 코드 + 상태 메시지 |
| 헤더 | 부가 정보(형식, 인증, 내 프로그램 이름) | 부가 정보(형식, 남은 호출 횟수, 캐시) |
| 본문 | 보낼 데이터(있을 때만, 보통 JSON) | 받은 데이터(JSON, HTML, 이미지 등) |

**왜 중요한가.** 오류가 났을 때 "어느 부품이 잘못됐나"를 짚는 지도다. 401이면 헤더(인증), 404면 경로, 400이면 본문이나 파라미터, 405면 메서드. 이 표만 머리에 있어도 디버깅 시간이 반으로 준다.

### 2. URL과 쿼리 문자열: 어디로, 어떤 조건으로

**한 줄 정의.** URL(Uniform Resource Locator)은 "어느 서버의 어느 자원"인지 적는 주소이고, 쿼리 문자열(query string)은 `?` 뒤에 `이름=값`을 `&`로 이어 붙이는 **조건 메모란**이다.

**비유.** 택배 송장. `https://`는 배송 방식(보안 연결), 호스트는 건물 주소, 경로는 호수, 쿼리는 송장 메모란("문 앞에 두세요"). 메모가 둘 이상이면 `&`로 잇는다.

**실제 예시.** GitHub 문서의 예를 쪼개 보자.

```
https://api.github.com/events?per_page=2&page=1
└─┬─┘   └─────┬──────┘└──┬──┘ └────────┬─────────┘
스킴        호스트       경로          쿼리 문자열
```

GitHub REST 문서(Getting started): 쿼리 파라미터는 URL 뒤에 `?`를 붙이고 `&`로 구분하며, `per_page=2&page=1`은 "한 페이지에 2건, 첫 페이지"라는 뜻이다. 경로 안의 `{owner}`, `{repo}` 같은 중괄호는 **경로 파라미터**로, 실제 값으로 바꿔 넣어야 한다(`/repos/{owner}/{repo}` → `/repos/mdn/content`).

포트(port)가 붙는 경우도 있다. 4-3에서 쓸 한국투자증권의 실전 주소는 `https://openapi.koreainvestment.com:9443`, 모의투자는 `https://openapivts.koreainvestment.com:29443`이다(공식 샘플 저장소의 설정 파일 기준). `:9443`이 포트다. 보통 `https`는 443이 기본이라 생략하지만, 이렇게 다른 번호를 쓰면 반드시 적어야 한다. 같은 건물의 다른 출입구라고 생각하면 된다.

파이썬에서는 쿼리를 손으로 이어 붙이지 않는다. 3-5의 `requests`가 딕셔너리를 받아 만들어 준다(공식 퀵스타트의 `payload = {'key1': 'value1', 'key2': 'value2'}` → `requests.get(url, params=payload)`). 한글이나 공백이 들어가도 알아서 인코딩해 주므로 직접 붙이는 것보다 안전하다.

**왜 중요한가.** 조회형 API는 거의 전부 쿼리로 조건을 받는다. 종목코드, 날짜, 페이지 번호. 4-3의 시세 조회도 `FID_INPUT_ISCD=005930`처럼 쿼리 파라미터로 종목을 지정한다.

### 3. 메서드: 조회·신규·정정·취소

**한 줄 정의.** 메서드(method)는 "이 자원에 무엇을 하겠다"는 동사다. MDN 한국어 'HTTP 요청 메서드' 설명을 그대로 옮긴다.

| 메서드 | MDN 설명 | 주식 주문 비유 |
|---|---|---|
| GET | "GET 메서드는 특정 리소스의 표시를 요청합니다. GET을 사용하는 요청은 오직 데이터를 받기만 합니다." | 잔고·시세 조회 |
| HEAD | "HEAD 메서드는 GET 메서드의 요청과 동일한 응답을 요구하지만, 응답 본문을 포함하지 않습니다." | "체결 내역 있나?"만 묻기 |
| POST | "POST 메서드는 특정 리소스에 엔티티를 제출할 때 쓰입니다. 이는 종종 서버의 상태의 변화나 부작용을 일으킵니다." | 신규 주문 |
| PUT | "PUT 메서드는 목적 리소스 모든 현재 표시를 요청 payload로 바꿉니다." | 주문 전체 정정(통째로 교체) |
| PATCH | "PATCH 메서드는 리소스의 부분만을 수정하는 데 쓰입니다." | 가격만 정정 |
| DELETE | "DELETE 메서드는 특정 리소스를 삭제합니다." | 주문 취소 |
| OPTIONS | "OPTIONS 메서드는 목적 리소스의 통신을 설정하는 데 쓰입니다." | 2-6의 CORS 사전 요청이 이것 |

**비유.** 창구에 내는 전표의 종류. 조회 전표는 아무리 많이 내도 계좌가 안 바뀌지만, 주문 전표는 한 장마다 돈이 움직인다. 그래서 **GET은 안전하고, POST는 두 번 보내면 두 번 일어난다.** 네트워크가 끊겨 "응답이 없어서 다시 보냈더니" 주문이 두 건 들어가는 사고가 여기서 난다. 주문을 다시 보내기 전에 체결 여부부터 조회하는 규칙은 이 단원 퀴즈 5에서, 같은 스크립트가 두 번 돌아도 안전하게 만드는 장치는 4-4에서 다룬다.

**실제 예시.** 우리 가계부 `app.js`의 함수를 API로 바꾼다면 메서드가 이렇게 정해진다.

| app.js 함수 | 하는 일 | API라면 |
|---|---|---|
| `load()` + `render()` | 내역 전부 읽기 | `GET /entries` |
| `addEntry(type, category, title, amount)` | 내역 한 건 추가 | `POST /entries` (본문에 JSON) |
| `deleteEntry(id)` | id로 한 건 삭제 | `DELETE /entries/{id}` |
| (아직 없는 기능: 내역 수정) | 금액만 고치기 | `PATCH /entries/{id}` |

실제 서비스도 같은 규칙으로 설계되어 있다. 한국투자증권 공식 샘플의 주문 함수 설명에는 "POST API의 경우 BODY값의 key값들을 대문자로 작성하셔야 합니다"라고 적혀 있다. 주문은 POST, 시세 조회는 GET이다.

**왜 중요한가.** 메서드를 틀리면 405(Method Not Allowed)가 온다. 그리고 "GET인데 왜 본문을 넣었지?", "POST인데 왜 쿼리에 데이터를 넣었지?" 같은 AI 코드의 어색함을 잡아낼 수 있다.

### 4. 상태 코드: 결과를 세 자리 숫자로

**한 줄 정의.** 상태 코드(status code)는 응답 시작 줄의 세 자리 숫자로, 첫 자리가 **결과의 종류**를 말한다. MDN 한국어 'HTTP 상태 코드'의 다섯 묶음: 정보 응답(1xx), 성공 응답(2xx), 리다이렉션 메시지(3xx), 클라이언트 에러 응답(4xx), 서버 에러 응답(5xx).

**비유.** 주문 체결 통보. 2xx는 "접수·체결", 3xx는 "다른 창구로 가세요", 4xx는 "전표가 잘못됐어요(내 탓)", 5xx는 "전산 장애(저쪽 탓)". **4xx는 고치기 전에 다시 내도 똑같이 거부되고, 5xx는 잠시 뒤 다시 내면 될 수 있다.** 이 구분이 자동화 스크립트의 재시도 규칙이 된다.

**실제 예시.** 자주 보는 코드와 MDN 설명.

| 코드 | 이름 | MDN 설명 | 내 해석 |
|---|---|---|---|
| 200 | OK | "요청이 성공적으로 되었습니다." | 됐다 |
| 201 | Created | "요청이 성공적이었으며 그 결과로 새로운 리소스가 생성되었습니다." | POST로 만들기 성공 |
| 204 | No Content | "요청에 대해서 보내줄 수 있는 콘텐츠가 없지만, 헤더는 의미있을 수 있습니다." | DELETE 성공 등, 본문 없음 |
| 301 | Moved Permanently | "이 응답 코드는 요청한 리소스의 URI가 변경되었음을 의미합니다." | 주소가 바뀜 |
| 304 | Not Modified | "이것은 캐시를 목적으로 사용됩니다." | 전에 받은 것 그대로 써라 |
| 400 | Bad Request | "이 응답은 잘못된 문법으로 인하여 서버가 요청을 이해할 수 없음을 의미합니다." | 파라미터·본문 형식 오류 |
| 401 | Unauthorized | "의미상 이 응답은 "비인증(unauthenticated)"을 의미합니다." | 누구인지 증명 안 됨(토큰 없음·만료) |
| 403 | Forbidden | "클라이언트는 콘텐츠에 접근할 권리를 가지고 있지 않습니다." | 누군지는 알지만 권한 없음 |
| 404 | Not Found | "서버는 요청받은 리소스를 찾을 수 없습니다." | 경로 오타, 없는 종목 |
| 405 | Method Not Allowed | "요청한 메소드는 서버에서 알고 있지만, 제거되었고 사용할 수 없습니다." | GET/POST를 바꿔 씀 |
| 429 | Too Many Requests | "사용자가 지정된 시간에 너무 많은 요청을 보냈습니다("rate limiting")." | 호출 한도 초과 |
| 500 | Internal Server Error | "서버가 처리 방법을 모르는 상황이 발생했습니다." | 서버 버그 |
| 502 / 503 | Bad Gateway / Service Unavailable | 503: "서버가 요청을 처리할 준비가 되지 않았습니다." | 점검·과부하. 기다렸다 재시도 |

401과 403은 초보가 가장 헷갈린다. 401은 "신분증 좀 보여 주세요"(헤더에 토큰이 없거나 만료), 403은 "신분증은 확인했는데 이 창구는 이용 못 하십니다"(권한·요금제·IP 제한). 429는 호출 한도다. GitHub 문서에 따르면 응답 헤더 `x-ratelimit-remaining`(남은 횟수)과 `x-ratelimit-reset`(초기화 시각)으로 한도를 알 수 있다.

도구마다 상태 코드를 다루는 방식이 다르다는 것을 2-6에서 봤다. 브라우저의 `fetch`는 404여도 거부(reject)되지 않아 `response.ok`를 직접 봐야 했다. 파이썬 `requests`는 `r.status_code`로 숫자를 보고, 퀵스타트의 `r.raise_for_status()`를 부르면 4XX·5XX에서 예외를 던져 준다. 한 가지 더. **200이어도 안심하면 안 되는 API가 있다.** 한국투자증권 공식 샘플은 HTTP 200을 확인한 뒤 응답 본문의 `rt_cd`가 `"0"`인지 한 번 더 검사하고, 실패면 `msg_cd`·`msg1`을 읽는다. 전표는 접수됐지만(200) 내용이 거부된(rt_cd≠0) 경우가 있다는 뜻이다. 문서에서 "응답 본문 안의 결과 코드"를 꼭 찾아보자.

**왜 중요한가.** 자동화는 사람이 안 보는 동안 돈다. "상태 코드별로 무엇을 할지"를 코드에 미리 적어 둬야 한다. 2xx는 진행, 4xx는 멈추고 알림, 429·5xx는 기다렸다 재시도. 이 규칙이 4-4의 실패 알림으로 이어진다.

### 5. 헤더: 봉투 겉면의 메모

**한 줄 정의.** MDN 한국어 'HTTP 헤더': "HTTP 헤더는 클라이언트와 서버가 요청 또는 응답으로 부가적인 정보를 전송할 수 있도록 해줍니다." `이름: 값` 한 줄이 헤더 하나다.

**비유.** 전표 봉투 겉면. 안의 내용(본문)과 별개로 "보내는 사람", "내용물 종류", "취급 주의"를 겉에 적는다. 창구는 봉투를 뜯기 전에 겉면부터 본다.

**실제 예시.** 자주 쓰는 헤더(MDN 설명을 요약).

| 헤더 | 뜻 | 어디서 쓰나 |
|---|---|---|
| `Content-Type` | 본문의 형식(미디어 타입). JSON이면 `application/json` | POST 본문 보낼 때, 응답 읽을 때 |
| `Accept` | 내가 받을 수 있는 형식 | GitHub: `Accept: application/vnd.github+json` |
| `Authorization` | 서버에 나를 증명하는 자격 증명. 문법은 `Authorization: <type> <credentials>` | 거의 모든 유료·개인 API |
| `User-Agent` | 요청하는 프로그램·OS 식별 문자열 | 일부 API가 요구 |
| `Content-Length` | 본문 크기(바이트) | 도구가 자동으로 붙임 |

`Authorization`의 `<type>`으로 MDN이 "보통 타입은 "Basic"이며"라고 적은 Basic 외에, 요즘 API는 거의 **Bearer**를 쓴다. GitHub 문서: `Authorization: Bearer YOUR-TOKEN`. Claude API 문서도 `Authorization: Bearer YOUR_API_KEY`(예전 방식 `x-api-key`도 지원). 한국투자증권 샘플도 `authorization: Bearer {토큰}`이다. "Bearer(소지자)"라는 말 그대로, **이 토큰을 들고 있는 사람은 누구든 통과**시킨다. 그래서 토큰이 새면 끝이다. 4-2의 주제다.

서비스마다 자기만의 헤더를 추가로 요구한다. 문서에서 찾아 적어야 하는 것들이다.

- GitHub: `X-GitHub-Api-Version` — 문서는 "이 헤더로 사용할 REST API 버전을 지정해야 한다"고 안내한다.
- Claude API: `anthropic-version: 2023-06-01`, `content-type: application/json`.
- 한국투자증권(공식 샘플 `kis_auth.py`): `Content-Type: application/json`, `authorization: Bearer ...`, `appkey`, `appsecret`, `tr_id`(어떤 거래인지 식별), `custtype: P`(개인).

파이썬에서는 딕셔너리로 넘긴다(퀵스타트: `headers = {'user-agent': 'my-app/0.0.1'}` → `requests.get(url, headers=headers)`).

**왜 중요한가.** 인증, 버전, 형식이 전부 헤더로 간다. 헤더 하나가 빠지면 401이나 400이 오고, 본문을 아무리 고쳐도 안 풀린다. "AI가 짠 코드가 401을 낸다"의 절반은 헤더 이름 오타나 누락이다.

### 6. 본문과 JSON, 그리고 'REST API'라는 말

**한 줄 정의.** 본문(body)은 요청이나 응답에 실어 보내는 실제 데이터이고, 오늘날 API 본문의 표준 형식은 1-6에서 배운 JSON(JavaScript Object Notation)이다.

**비유.** 봉투 안의 전표 본문. 우리 가계부의 내역 한 건이 그대로 본문이 된다.

**실제 예시.** `addEntry`가 만드는 객체를 POST 본문으로 보내면 이런 모양이다.

```http
POST /entries HTTP/1.1
Host: example.com
Content-Type: application/json

{"type": "expense", "category": "food", "title": "점심", "amount": 9000, "date": "2026-10-21"}
```

파이썬은 `requests.post(url, json=payload)` 한 줄로 끝난다. 퀵스타트에 따르면 `json=`은 딕셔너리를 JSON으로 바꿔 본문에 넣고, `Content-Type`도 알아서 붙인다. 응답 본문은 `r.json()`으로 파이썬 객체로 푼다(2-6의 `response.json()`과 같은 역할). 단, 퀵스타트의 주의처럼 JSON으로 잘 풀렸다고 요청이 성공한 것은 아니므로 상태 코드를 같이 본다.

이제 'REST API'라는 말. MDN 용어집: REST(Representational State Transfer)는 "효율적이고 신뢰할 수 있으며 확장 가능한 분산 시스템을 만들어 내는 소프트웨어 아키텍처 설계 제약의 묶음"이다. 엄격한 정의가 있지만 MDN은 많은 HTTP API가 모든 제약을 따르지 않아도 'RESTful'이라 불린다고 하면서, 이렇게 정리한다. "초보자는 REST API란 표준 웹 라이브러리와 도구로 호출할 수 있는 HTTP 서비스라고 생각해도 된다." 우리에게 실용적인 뜻은 두 가지다. (1) 경로는 **자원 이름(명사)**, 동작은 **메서드(동사)**로 표현한다(`/entries` + `GET`, `/entries/17` + `DELETE`). (2) 주고받는 형식은 보통 JSON이다.

**API 문서 읽기 체크리스트.** 어떤 API 문서를 열든 이 여섯 가지를 찾아 메모하면 코드를 쓸(또는 AI 코드를 검증할) 준비가 끝난다.

| 찾을 것 | GitHub REST 예 | 한국투자증권 시세 조회 예(공식 샘플 기준) |
|---|---|---|
| 기본 주소(base URL) | `https://api.github.com` | 실전 `https://openapi.koreainvestment.com:9443` / 모의 `...vts...:29443` |
| 엔드포인트 경로 | `/repos/{owner}/{repo}` | `/uapi/domestic-stock/v1/quotations/inquire-price` |
| 메서드 | GET | GET |
| 필수 헤더 | `Accept`, `X-GitHub-Api-Version`, (`Authorization`) | `authorization`, `appkey`, `appsecret`, `tr_id`(`FHKST01010100`), `custtype` |
| 파라미터 | 쿼리 `per_page`, `page` | 쿼리 `FID_COND_MRKT_DIV_CODE`(J: KRX 등), `FID_INPUT_ISCD`(종목코드, 예 005930) |
| 응답 모양·한도 | JSON, `x-ratelimit-*` 헤더 | JSON, 본문의 `rt_cd`/`msg1`, 호출 한도(모의투자는 더 낮음) |

**왜 중요한가.** "API 연동"이란 결국 이 표를 채우고 코드로 옮기는 일이다. 표가 채워지지 않는 항목이 있으면 문서를 더 읽거나 서비스에 물어야지, AI에게 추측하게 하면 안 된다.

## 따라하기

재료는 2-6에서 쓴 GitHub 공개 API(키 없이 호출 가능, 비인증 한도 시간당 60회), 연습용 가짜 서버 JSONPlaceholder, 그리고 우리 가계부 데이터다. 3-1에서 만든 가상환경을 켜고 `requests`가 설치되어 있는지(3-5) 확인하고 시작한다.

### 1. 브라우저로 응답 한 통 뜯어보기 (10분)

1. 브라우저 주소창에 `https://api.github.com/repos/mdn/content`를 입력한다. HTML이 아니라 **JSON 본문이 그대로** 보인다. `"stargazers_count"`를 찾아보자.
2. 2-2에서 쓴 개발자 도구(F12)를 열고 네트워크(Network) 패널을 찾은 뒤 페이지를 새로고침한다(패널 이름은 브라우저와 버전에 따라 조금 다를 수 있다). 목록에서 `content` 요청을 누르면 요청 메서드(GET), 상태 코드(200), 응답 헤더(`content-type: application/json...`, `x-ratelimit-remaining`)가 보인다. 핵심 개념 1의 표와 하나씩 대조한다.
3. 주소를 `https://api.github.com/repos/mdn/this-repo-does-not-exist`로 바꿔 본다. 상태 코드 404와 "Not Found" 류의 JSON 본문이 온다. **404도 응답이다.** 본문이 있고 헤더가 있다.

### 2. 터미널에서 호출하기 (20분)

GitHub 문서의 curl 예제 형식(`--request`, `--url`, `--header`)을 그대로 쓴다.

Mac(터미널):

```bash
curl --request GET \
  --url "https://api.github.com/repos/mdn/content" \
  --header "Accept: application/vnd.github+json"
```

Windows(PowerShell)에는 `Invoke-RestMethod`가 있다. 공식 문서 설명대로 "RESTful 웹 서비스에 HTTP 또는 HTTPS 요청을 보내는" 명령이고, JSON 응답을 PowerShell 객체로 자동 변환해 준다.

```powershell
$r = Invoke-RestMethod -Uri "https://api.github.com/repos/mdn/content" -Headers @{ Accept = "application/vnd.github+json" }
$r.stargazers_count
$r.name
```

둘 다 본문이 쏟아진다. 쿼리 문자열도 붙여 보자. 문서의 예 `https://api.github.com/events?per_page=2&page=1`을 URL 자리에 넣으면 2건만 온다. `per_page=5`로 바꾸면 5건. **URL 뒤 글자 몇 개가 결과를 바꾼다**는 감각이 목표다.

### 3. 파이썬으로 상태 코드·헤더·본문 세 가지를 찍는 탐침 만들기 (40분)

프로젝트 폴더 안에 `tools/api_probe.py`를 만든다(폴더가 없으면 만든다).

```python
# tools/api_probe.py — URL 하나를 찔러 보고 상태 코드, 주요 헤더, 본문 앞부분을 보여 준다
import sys
import requests


def probe(url):
    print("=" * 60)
    print("요청:", "GET", url)
    try:
        r = requests.get(
            url,
            headers={"Accept": "application/vnd.github+json", "User-Agent": "my-ledger-probe"},
            timeout=10,                         # 10초 넘게 기다리지 않는다
        )
    except requests.exceptions.RequestException as e:   # 네트워크 자체가 안 됨(오프라인, 오타 도메인)
        print("네트워크 오류:", e)
        return

    print("상태 코드:", r.status_code)           # 2xx/4xx/5xx 구분
    print("content-type:", r.headers.get("content-type"))
    print("남은 호출:", r.headers.get("x-ratelimit-remaining"))

    if r.status_code >= 400:
        print("실패 본문:", r.text[:200])         # 실패도 본문이 있다
        return

    data = r.json()                              # JSON → 파이썬 객체
    if isinstance(data, dict):
        print("본문 키:", list(data.keys())[:10])
    else:
        print("본문: 목록, 길이", len(data))


if __name__ == "__main__":
    targets = sys.argv[1:] or [
        "https://api.github.com/repos/mdn/content",
        "https://api.github.com/repos/mdn/this-repo-does-not-exist",
        "https://api.github.com/events?per_page=2&page=1",
    ]
    for t in targets:
        probe(t)
```

실행(Windows PowerShell / Mac 공통, 3-1에서 정한 파이썬 실행 명령으로):

```
python tools/api_probe.py
```

확인할 것 세 가지. (1) 첫 번째는 200, 두 번째는 404, 세 번째는 200에 "목록, 길이 2". (2) `남은 호출` 숫자가 실행할 때마다 줄어든다. 60이 0이 되면 429 대신 403과 rate limit 메시지가 올 수 있다(2-6 표 참고). (3) 404일 때 `r.json()`을 부르지 않고 `r.text`를 찍은 이유를 설명해 본다(오류 본문이 JSON이 아닐 수도 있어서).

연습: 아무 URL이나 인자로 넘겨 보자. `python tools/api_probe.py https://api.github.com/rate_limit` 처럼. 본문 키가 어떻게 생겼는지 보고, 문서를 안 읽고도 "이 API는 이런 모양을 준다"를 탐침으로 알아내는 습관을 들인다.

### 4. POST로 매매 복기 한 건 보내 보기 (30분)

JSONPlaceholder는 공식 README에서 "GET, POST, PUT, PATCH, DELETE and OPTIONS verbs"를 지원하는 연습용 가짜 API라고 밝힌 서비스다(기본 주소 `https://jsonplaceholder.typicode.com`, 실제 저장은 되지 않는다). 글(post)을 만드는 경로는 사이트 첫 화면에서 확인하고(이 글은 `/posts`로 가정), 매매 복기 한 건을 보내 보자.

```python
# tools/post_review.py — 오늘 매매 복기 한 건을 POST로 보낸다 (연습용 서버)
import requests

review = {
    "title": "2026-10-21 삼성전자 단타",
    "body": "9시 5분 돌파 진입, 손절 -1.2%. 뉴스 확인 안 한 것이 원인.",
    "userId": 1,
}

r = requests.post("https://jsonplaceholder.typicode.com/posts", json=review, timeout=10)
print("상태 코드:", r.status_code)        # 201이면 '생성됨'
print("응답 헤더 content-type:", r.headers.get("content-type"))
print("응답 본문:", r.json())              # 보낸 내용 + 서버가 붙인 id
```

보는 포인트. 200이 아니라 **201**(Created)이 온다. 응답 본문에 내가 보낸 것 + `id`가 들어 있다. `json=review` 덕분에 `Content-Type: application/json`을 내가 쓰지 않아도 됐다. 같은 코드를 두 번 실행하면 "두 건 생성"으로 취급된다(진짜 서버라면 중복). 이것이 핵심 개념 3에서 말한 POST의 성질이다.

### 5. 내 가계부를 'API 응답'으로 바꿔 보기 (40분)

실제 서버를 만들기 전에, 가계부 데이터를 **API가 주는 모양 그대로** 파일로 두고 HTTP로 받아 보자. 3-3에서 localStorage의 `ledger-entries`를 JSON 파일로 내보낸 적이 있다. 그 파일을 `data/entries.json`으로 둔다(없으면 아래처럼 손으로 만든다).

```json
[
  {"id": 1697000000000, "type": "expense", "title": "점심", "amount": 9000, "date": "2026-10-21"},
  {"id": 1697000100000, "type": "income", "title": "배당", "amount": 32000, "date": "2026-10-21"}
]
```

프로젝트 폴더에서 파이썬 내장 정적 서버를 띄운다(공식 문서의 `python -m http.server [port]` 형식, Windows/Mac 공통).

```
python -m http.server 8000
```

브라우저에서 `http://localhost:8000/data/entries.json`을 연다. 이것은 `GET /data/entries.json` 요청이고, 응답은 200과 JSON 본문이다. 개발자 도구 네트워크 패널에서 응답 헤더의 `Content-Type`을 확인한다. 이제 2-6에서 만든 `fetch` 코드가 "진짜 API"를 부르는 것과 **구조적으로 같은 일**을 하고 있다는 것을 안다. 서버가 파일을 그대로 주느냐, 계산해서 주느냐의 차이일 뿐이다.

마무리로 종이에 '나의 가계부 API 명세'를 적어 본다. 핵심 개념 6의 체크리스트 여섯 칸을 채우되, 기본 주소는 `http://localhost:8000`, 엔드포인트는 `GET /entries`, `POST /entries`, `DELETE /entries/{id}`, 본문 모양은 `app.js`의 `entry` 객체. 이 명세가 로드맵 8단계(AI 직원실)에서 서버를 만들 때의 설계도가 된다.

| 증상 | 원인 | 해결 |
|---|---|---|
| 401 Unauthorized | 인증 헤더 없음·오타·토큰 만료 | 문서의 헤더 이름을 글자 단위로 대조. 토큰 재발급(4-3) |
| 403 Forbidden | 권한·요금제·한도(GitHub 비인증 60회) | 응답 본문 메시지 읽기. `x-ratelimit-*` 확인. 반복문 안 호출 금지 |
| 404인데 URL은 맞는 것 같음 | 경로 파라미터 `{owner}`를 안 바꿈, 끝에 `/` 유무, 대소문자 | 브라우저에 그 URL을 직접 쳐서 확인 |
| 400 Bad Request | 쿼리 이름 오타, 본문이 JSON이 아님, 필수 파라미터 누락 | `json=`을 썼는지, 파라미터 이름이 문서와 같은지(대문자 포함) |
| 405 Method Not Allowed | GET/POST를 바꿔 씀 | 문서의 메서드 확인 |
| 429 Too Many Requests | 호출 한도 초과 | `time.sleep`으로 간격, 결과 캐시, 4-4의 스케줄로 횟수 설계 |
| 200인데 데이터가 이상함 | 본문 안 결과 코드가 실패(예: `rt_cd` ≠ "0") | 문서에서 '응답 코드 필드' 찾아 함께 검사 |
| `r.json()`에서 예외 | 응답이 JSON이 아님(HTML 오류 페이지) | 먼저 `status_code`와 `content-type` 확인, 실패면 `r.text` 출력 |
| 응답이 영원히 안 옴 | `timeout` 없음 | 항상 `timeout=` 지정(퀵스타트 예: `timeout=0.001`은 일부러 짧게 한 예) |
| 한글 쿼리가 깨짐 | URL에 손으로 이어 붙임 | `params=` 딕셔너리로 넘겨 인코딩 맡기기 |

## 확인 퀴즈

**1. 아래 요청에서 메서드, 경로, 쿼리 파라미터, 헤더를 각각 짚어라.**

```http
GET /uapi/domestic-stock/v1/quotations/inquire-price?FID_COND_MRKT_DIV_CODE=J&FID_INPUT_ISCD=005930 HTTP/1.1
tr_id: FHKST01010100
custtype: P
```

<details><summary>정답과 해설</summary>
메서드 GET. 경로 `/uapi/domestic-stock/v1/quotations/inquire-price`. 쿼리 파라미터 `FID_COND_MRKT_DIV_CODE=J`(시장 구분, J는 KRX), `FID_INPUT_ISCD=005930`(종목코드). 헤더 `tr_id`, `custtype`. 실제 호출에는 `authorization`, `appkey`, `appsecret` 헤더도 더 필요하다(4-3).
</details>

**2. 스크립트가 새벽에 돌다가 503을 받았다. 400을 받았을 때와 처리 방식이 왜 달라야 하나?**

<details><summary>정답과 해설</summary>
503은 서버 에러 응답(5xx)으로 "서버가 요청을 처리할 준비가 되지 않았습니다." 즉 내 요청은 멀쩡할 수 있으니 잠시 뒤 재시도가 합리적이다. 400은 클라이언트 에러(4xx)로 "잘못된 문법으로 인하여 서버가 요청을 이해할 수 없음"이므로 고치기 전에는 몇 번을 보내도 같은 결과다. 재시도 대신 멈추고 알림을 보내야 한다.
</details>

**3. 401과 403의 차이를 창구 비유로 설명하라.**

<details><summary>정답과 해설</summary>
401은 "비인증": 신분증(토큰)이 없거나 만료되어 누군지 확인이 안 된 상태. 403은 신분은 확인됐지만 "콘텐츠에 접근할 권리를 가지고 있지 않"은 상태(권한, 요금제, 한도). 401은 헤더·토큰을 고치고, 403은 권한·한도를 본다.
</details>

**4. `requests.post(url, json=review)`와 `requests.post(url, data=review)`의 차이는? (힌트: Content-Type)**

<details><summary>정답과 해설</summary>
`json=`은 딕셔너리를 JSON 문자열로 바꿔 본문에 넣고 `Content-Type: application/json`을 붙인다. `data=`에 딕셔너리를 주면 폼 형식(`application/x-www-form-urlencoded`)으로 보낸다. JSON을 기대하는 API에 `data=`로 보내면 400이 날 수 있다.
</details>

**5. 네트워크가 잠깐 끊겨 응답을 못 받았다. GET 시세 조회와 POST 매수 주문 중 "그냥 다시 보내도 되는 것"은 어느 쪽이고 왜인가?**

<details><summary>정답과 해설</summary>
GET은 "오직 데이터를 받기만" 하므로 다시 보내도 안전하다. POST는 "서버의 상태의 변화나 부작용을 일으"키므로, 첫 요청이 서버에 도달해 체결됐는데 응답만 못 받은 경우 재전송하면 주문이 두 건이 된다. 주문은 재전송 전에 반드시 체결·미체결 조회(GET)로 상태를 확인해야 한다.
</details>
