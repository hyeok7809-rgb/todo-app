# 8-6. 좋은 요청 쓰는 법: 바이브 코딩에서 요구사항과 검증 기준 적기, 결과 검증 루틴

| 과정 | 8. Claude Code 기초 |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 8-5 |
| 경험치 | 80 |

## 이 단원을 마치면

- 6-3의 네 요소를 Claude Code용으로 확장한 **여섯 칸 요청문**(목표, 위치, 제약, 검증, 범위 밖, 결과 형태)을 쓸 수 있다.
- "Claude가 스스로 확인할 수 있는 검증"(테스트, 실행 결과, 스크린샷 비교)을 요청에 넣어, 내가 매번 검사하지 않아도 되게 만들 수 있다.
- 큰 기능은 **스펙 먼저**(Claude가 나를 인터뷰해 SPEC을 쓰게) → 새 세션에서 구현하는 흐름을 돌릴 수 있다.
- 공식 문서의 다섯 가지 실패 패턴을 알아보고 피할 수 있다.

## 왜 배우나 (나에게 어떤 쓸모)

바이브 코딩의 실력은 코드가 아니라 **요청문과 검증**에서 갈린다. 이 단원은 8과정의 종합이자 11과정 AI 직원의 "업무 지시서"의 원형이다. 지금 요청문을 잘 쓰면 그대로 스킬(9-2)이 되고, 그대로 AI 직원의 지시서가 된다. 그리고 검증을 요청에 넣으면 Claude가 **스스로 고치는 루프**가 돌아 내 시간이 준다. 공식 문서의 표현: "Claude에게 돌릴 수 있는 검사를 줘라. 지켜보는 세션과 자리를 비워도 되는 세션의 차이다."

## 핵심 개념

(공식 best practices·quickstart, 확인일 2026-10-23.)

### 1. 여섯 칸 요청문

| 칸 | 내용 | 예 |
|---|---|---|
| 목표 | 무엇이 되면 끝인가 | "인사부에 5번째 루틴 '독서'를 추가" |
| 위치 | 어느 파일·함수 | "routine.js의 ROUTINES 배열" |
| 제약 | 지킬 것 | "CLAUDE.md 규칙. 다른 파일은 건드리지 말 것" |
| **검증** | Claude가 확인할 방법 | "Playwright로 체크 5개가 보이고 새로고침 후 유지되는지 확인해서 결과를 보여 줘" |
| 범위 밖 | 하지 말 것 | "경험치 규칙은 바꾸지 마" |
| 결과 형태 | 무엇을 돌려줄지 | "diff와 검증 출력, 커밋은 아직" |

6-3의 역할·맥락은 CLAUDE.md와 프로젝트 지침이 맡고, 코딩 요청에서는 위 여섯 칸이 중심이다.

### 2. 검증을 요청에 넣는다

공식 문서의 전·후 예:

| 전 | 후 |
|---|---|
| "이메일 검증 함수 만들어" | "validateEmail 함수를 써. 테스트 케이스: user@example.com은 true, invalid는 false, user@.com은 false. 구현 후 테스트를 돌려" |
| "대시보드 예쁘게" | "[스크린샷] 이 디자인을 구현하고, 결과 스크린샷을 찍어 원본과 비교해 차이를 고쳐" |
| "빌드가 실패해" | "빌드가 이 에러로 실패해: [에러]. 고치고 빌드 성공을 확인해. 에러를 숨기지 말고 원인을 고쳐" |

우리 앱에서 검증의 종류: (1) 브라우저 자동 확인(Playwright 스크립트, CLAUDE.md 검증 방법) (2) `node -e`로 문법 확인 (3) 스크린샷 비교 (4) "콘솔 에러 0건". 검증이 있으면 Claude가 **실패를 읽고 다시 고친다.** 끝나면 "검증 출력을 보여 줘"로 **증거**를 받는다. 증거를 읽는 게 내가 다시 돌리는 것보다 빠르다.

더 강하게: `/goal 조건`을 걸면 조건이 충족될 때까지 턴을 이어 가고, Stop 훅(9-3)으로 검사가 통과할 때까지 끝내지 못하게 할 수도 있다(공식 문서). 지금은 "요청에 검증 넣기"까지만.

### 3. 풍부한 재료 주기

- `@파일`로 참조하면 Claude가 그 파일을 먼저 읽는다(공식 "@ 참조").
- 스크린샷·이미지를 붙여 넣기(드래그).
- 문서 URL을 주기. 자주 쓰는 도메인은 `/permissions`에 허용.
- `cat error.log | claude -p "이 에러 설명해"`처럼 파이프로 넣기.
- 기존 패턴 가리키기: "routine.js가 하는 방식대로 study.js도".

### 4. 큰 기능은 스펙부터: 인터뷰 패턴

공식 문서의 프롬프트(우리말로):
> "나는 [기능]을 만들고 싶다. AskUserQuestion 도구로 나를 자세히 인터뷰해. 기술 구현, UI/UX, 예외 상황, 걱정되는 점, 트레이드오프를 물어봐. 뻔한 건 묻지 말고 내가 생각 못 했을 어려운 부분을 파고들어. 다 다루면 완전한 스펙을 SPEC.md에 써."

스펙이 나오면 **새 세션**에서 구현한다(책상이 깨끗, 8-5). 좋은 스펙은 파일·인터페이스를 이름으로 적고, 범위 밖을 명시하고, 끝에 **끝에서 끝까지 검증 단계**가 있다. "스펙을 정확히 쓰는 시간이 구현을 지켜보는 시간보다 남는다"(공식 문서).

### 5. 두 번째 의견: 리뷰 세션

공식 문서의 Writer/Reviewer 패턴: 세션 A가 구현, 세션 B(새 컨텍스트)가 "@파일을 리뷰해서 예외·경쟁 조건·기존 패턴과의 일관성을 봐". A에 B의 결과를 넘겨 고친다. 자기가 쓴 코드에는 편향이 생기니 **다른 책상**에서 본다. 6-2의 "반대로 묻기"를 Claude Code에서 하는 법이다. 번들 스킬 `/code-review`가 이걸 서브에이전트로 해 준다(9-1).

### 6. 다섯 가지 실패 패턴 (공식)

| 패턴 | 증상 | 처방 |
|---|---|---|
| 잡탕 세션 | 한 세션에 관련 없는 일 여러 개 | 작업마다 `/clear` |
| 교정 반복 | 두 번 넘게 같은 교정 | `/clear` 후 더 좋은 첫 요청 |
| 과잉 CLAUDE.md | 규칙이 묻힘 | 가지치기, 훅으로 전환 |
| 믿고 안 봄 | 그럴듯하지만 예외 처리 없음 | 검증 없으면 배포 없다 |
| 무한 탐색 | "조사해 봐"로 수백 파일 읽음 | 범위 좁히기, 서브에이전트 |

### 7. 직관은 나중에

공식 문서의 마지막: 이 패턴들은 출발점이지 법이 아니다. 때로는 컨텍스트를 쌓아야 하고, 때로는 계획 없이 탐색해야 하고, 때로는 모호한 요청이 맞다. **잘 됐을 때 내가 뭘 했는지**(요청 구조, 재료, 모드)를 적어 두면 직관이 쌓인다. 6-2의 환각 노트와 짝이 되는 "성공 노트"를 만들자.

## 따라하기

### 1. 여섯 칸으로 다시 쓰기 (30분)

8-5 숙제 3의 "가장 안 좋았던 요청"을 여섯 칸으로 다시 써서 **새 세션**에서 보낸다. 결과 차이를 적는다.

### 2. 검증 넣기 (60분)

"인사부에 5번째 루틴 '독서' 추가"를 검증 포함으로 요청한다: "Playwright로 (a) 루틴 5개 표시 (b) 체크 후 새로고침 유지 (c) 연속 달성일이 5개 기준으로 계산되는지 확인하고 출력을 보여 줘." Claude가 검증을 돌리고 실패하면 스스로 고치는지 관찰한다. 증거(출력)를 읽고 승인.

### 3. 인터뷰로 스펙 쓰기 (60분)

"기획부 월별 그래프"를 4절 프롬프트로 인터뷰받아 `docs/specs/report-room.md`를 만든다. 범위 밖과 검증 단계가 들어 있는지 확인. **구현은 하지 않는다**(기획부 확장은 로드맵 6·7단계 뒤에).

### 4. 리뷰 세션 (40분)

따라하기 2의 변경을 커밋하지 않은 상태에서 `/clear` → "routine.js의 변경을 리뷰해. 예외 상황, 기존 패턴과의 일관성, CLAUDE.md 위반을 찾아. 스타일 취향은 빼고." 결과를 원래 세션(또는 같은 세션)에 넘겨 고친다. 또는 `/code-review`를 돌려 비교.

### 5. 성공 노트 시작 (20분)

`docs/success-log.md`에 이번 단원에서 잘 된 요청 2개를 "요청문 / 왜 잘 됐나(재료·검증·모드)"로 적는다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 검증 없는 요청 | 내가 매번 검사 | 검증 칸 필수 |
| "됐다"는 말만 믿음 | 예외에서 깨짐 | 증거(출력·스크린샷) 요구 |
| 큰 기능을 한 요청에 | 방향 오류, 재작업 | 인터뷰 → 스펙 → 새 세션 |
| 같은 세션에서 자기 리뷰 | 편향 | 새 세션/서브에이전트 리뷰 |
| 리뷰 지적을 전부 반영 | 과잉 설계 | "정확성·요구사항에 영향 있는 것만" |
| 성공을 기록 안 함 | 직관이 안 쌓임 | 성공 노트 |

## 확인 퀴즈

**1. 여섯 칸 중 Claude가 스스로 고치는 루프를 만드는 칸은?**

<details><summary>정답과 해설</summary>
검증. 돌릴 수 있는 검사가 있으면 Claude가 결과를 읽고 통과할 때까지 반복한다.
</details>

**2. "빌드가 실패해"를 공식 문서 방식으로 고쳐 보라.**

<details><summary>정답과 해설</summary>
"빌드가 [에러 전문]으로 실패한다. 고치고 빌드 성공을 확인해. 에러를 숨기지 말고 원인을 고쳐." 에러 전문·검증·금지(숨기기)가 들어가면 정답.
</details>

**3. 스펙을 쓴 세션에서 바로 구현하지 않고 새 세션을 여는 이유.**

<details><summary>정답과 해설</summary>
구현 세션의 컨텍스트를 깨끗하게 유지하기 위해(8-5). 스펙 파일이 있으니 다시 설명할 필요가 없다.
</details>

**4. 리뷰 세션이 "지적을 몇 개 만들어 낸다"는 문제의 대처는?**

<details><summary>정답과 해설</summary>
리뷰어에게 "정확성과 요구사항에 영향 있는 것만 보고, 나머지는 선택"이라고 지시하고, 지적을 전부 반영하지 않는다(과잉 설계 방지).
</details>

**5. "조사해 봐"가 위험한 이유와 대안.**

<details><summary>정답과 해설</summary>
범위 없는 탐색으로 수백 파일을 읽어 컨텍스트가 찬다. 범위를 좁히거나 서브에이전트(9-1)에 맡겨 요약만 받는다.
</details>

## 숙제

1. **요청문 10개** — 2주간 모든 코딩 요청을 여섯 칸으로 쓰고 `docs/prompts.md`에 쌓아라. 검증 칸이 비어 있는 요청은 보내지 않는다.
2. **스펙 → 구현** — 따라하기 3의 스펙을 새 세션에서 1단계만 구현해 보라(브랜치에서, 5-2).
3. **9-1 예습** — 이번 주 요청 중 "Claude가 파일을 너무 많이 읽었다" 싶은 순간을 적어 두라. 서브에이전트가 그 답이다.
