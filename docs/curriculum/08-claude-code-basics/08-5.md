# 8-5. 슬래시 명령과 컨텍스트 관리: /init, /clear, /compact, 비용·사용량 확인

| 과정 | 8. Claude Code 기초 |
|---|---|
| 예상 시간 | 3시간 |
| 선수 단원 | 8-4 |
| 경험치 | 60 |

## 이 단원을 마치면

- 매일 쓰는 슬래시 명령 15개를 "언제 치는지"로 분류해 말할 수 있다.
- 컨텍스트가 차는 과정을 `/context`로 보고, `/clear`·`/compact`·`/btw`·`/rewind`로 다스릴 수 있다.
- `/usage`로 내 플랜 사용량과 세션 토큰을 읽고, 공식 문서의 "토큰 줄이는 법"을 내 습관으로 옮길 수 있다.
- 세션에 이름을 붙이고(`/rename`) 이어 가며(`/resume`) "작업마다 세션 하나" 습관을 만든다.

## 왜 배우나 (나에게 어떤 쓸모)

8-1에서 세션 = 책상이라 했다. 이 단원은 책상을 **정리하는 도구**다. 정리 안 된 책상에서는 Claude가 앞 규칙을 잊고(6-1), 토큰(돈·한도)이 새고, 품질이 떨어진다. 공식 모범 사례의 첫 문장이 "대부분의 모범 사례는 하나의 제약에서 온다: 컨텍스트 윈도우는 빨리 차고, 차면 성능이 떨어진다"이다. 명령 몇 개로 그 제약을 다루는 법을 익히면 구독 한도도 훨씬 오래 간다.

## 핵심 개념

(공식 commands·costs·best practices 문서, 확인일 2026-10-21. `/`를 치면 지금 쓸 수 있는 목록이 보이니 그게 최종 기준.)

### 1. 명령을 "언제"로 묶기

| 언제 | 명령 | 하는 일 |
|---|---|---|
| 시작할 때 | `/init` | CLAUDE.md 초안 생성(8-3) |

| | `/model` | 모델 바꾸기(6-4). 좌우 화살표로 effort 조절 |
| 작업 중 | `/plan` | 플랜 모드로(8-4) |
| | `/diff` | 지금까지의 변경 전체 보기 |
| | `/btw 질문` | 대화에 안 남는 **곁다리 질문**. 컨텍스트를 안 늘린다 |
| | `/rewind` | 대화·코드를 체크포인트로 되돌리기(8-2). 별칭 `/undo` |

| | `/effort` | 생각 노력 수준(low~max). 낮추면 토큰 절약 |
| 설정 | `/config`, `/permissions`, `/memory`, `/hooks`, `/mcp`, `/skills` | 각 설정 화면 |
| 도움 | `/help`, `/doctor` | 명령 목록, 설치·설정 점검 |

### 2. 컨텍스트는 어떻게 차나

시작할 때 시스템 지시 + CLAUDE.md + (MCP 도구 이름들)이 들어가고, 이후 **내 말, Claude 답, 읽은 파일 전문, 명령 출력**이 전부 쌓인다. `app.js` 600줄을 읽히면 그 자리에 1만 토큰이 들어가고 **세션 끝까지 남는다.** 테스트 출력 2,000줄도 마찬가지. 공식 문서 "왜 긴 세션에서 사용량이 치솟나": 매 요청마다 대화 전체를 다시 보내기 때문(캐시 요금이지만 0은 아님).

`/context`가 이걸 색 격자로 보여 주고 "메모리 비대", "용량 경고" 같은 제안을 준다.

### 3. 비우기 vs 요약하기

| | `/clear` | `/compact` |
|---|---|---|
| 결과 | 빈 책상 | 요약본만 남은 책상 |
| 비용 | 0 | 요약 자체가 큰 요청(대화를 다 읽음) |
| 언제 | **다른 작업**으로 넘어갈 때 | 같은 작업을 이어 가되 공간이 필요할 때 |

공식 best practices: 관련 없는 작업은 `/clear`. 같은 문제로 두 번 넘게 교정했다면 `/clear` 하고 더 좋은 첫 요청으로. `/compact 코드 변경과 테스트 명령은 꼭 남겨`처럼 지시를 붙일 수 있고, CLAUDE.md에 "compact 때 보존할 것"을 적어 둘 수도 있다. 자동 compact는 한도에 가까워지면 알아서 돈다(`/autocompact`로 기준 조절).

`/rewind`의 요약 옵션: 특정 지점부터(또는 그 전까지)만 요약해 **최근 대화는 그대로** 두는 방법도 있다.

### 4. 사용량 읽기

`/usage`의 Session 블록: 모델별 입력/출력/캐시 토큰과 달러 추정(구독자는 "청구와 무관", 플랜 막대가 실제). Pro/Max는 **사용량 분석**이 붙는다: 스킬·서브에이전트·MCP별 비중, "CLAUDE.md를 줄이면 요청당 N토큰 절약" 같은 **추천**, 그리고 `f`를 누르면 일부를 자동 적용. 한 주/하루 전환은 `d`/`w`.

`/insights`는 최근 세션들을 분석해 "어디서 막혔나, 어떤 기능을 써 보면 좋나" HTML 보고서를 만든다(클라우드 세션에서는 불가).

### 5. 토큰 줄이는 습관 (공식 costs 문서 요약)

1. 작업 사이 `/clear`. 상태줄에 컨텍스트 사용량을 띄워 두기(`/statusline`).
2. 모델 맞추기: 대부분은 Sonnet, 설계·복잡한 추론만 Opus(6-4).
3. 안 쓰는 MCP 서버 끄기(`/mcp`). CLI 도구가 MCP보다 컨텍스트를 덜 쓴다.
4. CLAUDE.md는 200줄 아래. 가끔 필요한 절차는 스킬로(9-2).
5. 긴 출력(테스트, 로그)은 서브에이전트(9-1)나 훅(9-3)으로 걸러서 요약만 받기.
6. 단순 작업은 `/effort low`. 생각 토큰은 출력 토큰으로 과금.
7. 구체적 요청(8-2): "이 코드베이스 개선해"는 전부 읽게 만든다.
8. 플랜 모드로 방향을 먼저 맞춰 재작업 방지(8-4). 잘못 가면 `Esc` 즉시.

### 6. 세션 운영법

공식 best practices: 세션을 **브랜치처럼** 다룬다. 작업 흐름마다 세션 하나, `/rename oauth-migration`처럼 이름, `claude --resume`으로 복귀. 큰 기능은 "스펙 쓰는 세션"과 "구현하는 세션"을 분리하면 구현 세션의 책상이 깨끗하다. `/branch`로 현재 대화를 갈라 다른 방향을 시험할 수도 있다.

## 따라하기

### 1. `/context` 관찰 (20분)

새 세션에서 `/context` → `app.js`와 `sprites.js`를 읽게 한 뒤 `/context` → 두 파일이 차지한 양을 본다. 8-4 숙제 3의 캡처와 비교.

### 2. `/btw` (10분)

작업 중에 `/btw 자바스크립트에서 ===와 ==의 차이?` 같은 곁다리 질문을 한다. 답이 대화에 남지 않는 걸 `/context`로 확인.

### 3. `/compact`와 `/clear` 체험 (30분)

세션을 20~30턴 써서 채운 뒤 `/compact 변경한 파일 목록과 검증 명령은 꼭 남겨`. `/context`로 줄어든 양 확인. 그다음 전혀 다른 작업("커리큘럼 단원 요약")으로 넘어가며 `/clear study-summary`. `/resume`에 이름이 뜨는지.

### 4. `/usage` 읽기 (30분)

`/usage`를 열어 Session 블록, 플랜 막대, 사용량 분석을 읽는다. 추천 행이 있으면 무엇을 뜻하는지 Claude에게 `/btw`로 물어본다. `d`/`w` 전환. 적용해도 되는 추천이 있으면 `f`.

### 5. 세션 분리 운영 (40분)

"자산관리부 그래프" 기능을 (a) 스펙 세션: `/rename assets-chart-spec`, 플랜 모드로 스펙만 작성해 `docs/specs/assets-chart.md`에 저장 → (b) `/clear` 후 구현 세션: `/rename assets-chart-impl`, "docs/specs/assets-chart.md를 읽고 1단계만 구현". 구현 세션의 `/context`가 얼마나 가벼운지 본다. (실제 구현은 4단계 기획부에서 하니 1단계만.)

### 6. 상태줄 (15분)

`/statusline`을 실행해 컨텍스트 사용량이 보이게 설정한다. 이후 세션에서 항상 보인다.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 하루 종일 한 세션 | 품질 저하, 한도 소진 | 작업마다 `/clear`, 세션 이름 |
| 큰 파일 반복 읽기 | 컨텍스트 폭증 | 필요한 부분만, 서브에이전트 |
| `/compact`를 `/clear` 대신 | 요약 비용 + 잔재 | 다른 작업이면 `/clear` |
| 곁다리 질문을 본문에 | 대화 오염 | `/btw` |
| 사용량 안 봄 | 주간 한도 갑자기 소진 | `/usage` 주 2회, 상태줄 |
| 모든 작업 Opus·max effort | 비용·한도 낭비 | 작업별 모델·effort |

## 확인 퀴즈

**1. `/clear`와 `/compact`를 고르는 기준은?**

<details><summary>정답과 해설</summary>
다른 작업으로 넘어가면 `/clear`(비용 0, 빈 책상). 같은 작업을 이어 가되 공간이 필요하면 `/compact`(요약 비용 있음).
</details>

**2. 세션 끝까지 컨텍스트에 남는 것의 예 두 가지.**

<details><summary>정답과 해설</summary>
읽은 파일 전문, 명령·테스트 출력. 그래서 긴 출력은 서브에이전트·훅으로 걸러 요약만 받는다.
</details>

**3. `/btw`는 왜 토큰을 아끼나?**

<details><summary>정답과 해설</summary>
답이 대화 기록에 들어가지 않아 이후 모든 요청에 반복 전송되지 않는다.
</details>

**4. `/usage`의 달러 금액이 구독자에게 "청구와 무관"한 이유와, 그럼 무엇을 봐야 하나.**

<details><summary>정답과 해설</summary>
구독자는 사용량이 구독에 포함되고 금액은 정가 기준 추정일 뿐이다. 플랜 사용량 막대(세션·주간)와 사용량 분석의 추천을 본다.
</details>

**5. "같은 문제로 두 번 넘게 교정했다"면 공식 문서의 권고는?**

<details><summary>정답과 해설</summary>
`/clear` 하고, 배운 것을 반영한 더 좋은 첫 요청으로 다시 시작. 실패한 시도들이 컨텍스트를 오염시키기 때문.
</details>

## 숙제

1. **일주일 사용량 일지** — 매일 `/usage`를 한 번 열어 플랜 막대 %를 적고, 가장 많이 쓴 날 무엇을 했는지 한 줄.
2. **명령 치트시트** — 내가 실제로 쓴 명령만 모아 `docs/claude-code-cheatsheet.md`를 만들어라(공식 치트시트와 비교).
3. **8-6 예습** — 이번 주에 한 요청 중 "결과가 가장 안 좋았던 것"의 요청문을 그대로 저장해 두라.
