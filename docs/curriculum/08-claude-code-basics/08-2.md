# 8-2. 첫 프로젝트: 폴더 열기, 요구사항 말하기, 변경 내용 확인, git 커밋 요청까지

| 과정 | 8. Claude Code 기초 |
|---|---|
| 예상 시간 | 4시간 |
| 선수 단원 | 8-1 |
| 경험치 | 80 |

## 이 단원을 마치면

- 저장소 폴더에서 세션을 열고, 코드 질문 → 작은 변경 → 변경 확인 → 커밋까지 **혼자** 한 바퀴 돌 수 있다.
- Claude가 보여 주는 변경(diff)을 읽고 승인/거부를 판단할 수 있다.
- "되돌리고 싶다"를 세 가지 방법(Esc 중단, `/rewind`, git)으로 처리할 수 있다.
- 공식 퀵스타트의 추천 프롬프트 패턴("구체적으로", "단계별로", "먼저 탐색하게")을 내 요청에 적용한다.

## 왜 배우나 (나에게 어떤 쓸모)

지금까지 Claude Code가 한 일을 **옆에서 보기만** 했다면, 이 단원부터는 운전석에 앉는다. 작은 변경 한 바퀴를 혼자 돌려 보면 "AI가 코드를 짠다"가 어떤 느낌인지 몸으로 안다. 앞으로 커리큘럼의 모든 따라하기는 이 한 바퀴의 변형이다.

## 핵심 개념

(공식 quickstart·best practices, 확인일 2026-10-21.)

### 1. 한 바퀴의 다섯 단계

```
① 폴더에서 열기   cd ~/todo-app && claude
② 알아보기       "what does this project do?" 류의 질문
③ 변경 요청      작고 구체적으로
④ 확인           diff 읽기 + 브라우저/실행으로 검증
⑤ 커밋           "commit my changes with a descriptive message"
```

공식 퀵스타트가 이 순서 그대로 안내한다(Step 2~5). 이 저장소의 CLAUDE.md도 "작은 단위, 검증, 한국어 커밋 메시지"를 규칙으로 적어 뒀으니 Claude가 그 규칙을 따른다.

### 2. 알아보기: 먼저 읽게 한다

**왜**: 공식 문서 "Let Claude explore first — 변경 전에 코드를 이해하게 하라". 모델은 파일을 읽어야 내 코드를 안다(6-1). 퀵스타트의 예시 질문:
- `what does this project do?`
- `explain the folder structure`
- `where is the main entry point?`
한국어로 해도 된다. "이 프로젝트 구조 설명해 줘", "경험치 계산이 어디서 되는지 찾아 줘".

### 3. 변경 요청: 구체적으로, 단계별로

퀵스타트의 대비 예시:
- 나쁨: `fix the bug`
- 좋음: `fix the login bug where users see a blank screen after entering wrong credentials`

우리 식으로:
- 나쁨: "가계부 좀 좋게 해 줘"
- 좋음: "재무부 잔액 카드 아래에 '이번 달 지출 건수: N건'을 한 줄 추가해 줘. app.js의 renderMonth()에서 계산하고, index.html의 이번 달 카드 안에 넣어. 기존 한국어 주석 스타일 유지."

큰 일은 번호 목록으로 쪼갠다(퀵스타트 "Use step-by-step instructions"):
```
1. 계좌 종류에 "연금"을 추가
2. 순자산 계산에서 연금을 자산으로 포함
3. 브라우저에서 확인하는 방법 알려 줘
```

### 4. 확인: diff를 읽는다

Claude는 고치기 전(또는 후)에 **변경 비교(diff)** 를 보여 준다. `-` 줄이 지워진 것, `+` 줄이 새로 들어간 것(5-1). 읽을 때 체크 세 가지:
1. **내가 시킨 범위만** 바뀌었나? (엉뚱한 파일·함수가 섞이면 거부)
2. 지워진 줄 중 **필요한 것**이 없나?
3. 주석·스타일이 CLAUDE.md 규칙대로인가?

권한 모드가 Manual이면 파일 수정 전에 Yes/No를 묻는다. auto 모드면 묻지 않고 하되, 끝나고 `/diff`로 전체 변경을 볼 수 있다(공식 명령 목록). 8-4에서 자세히.

그다음 **실제로 돌려 본다**: 이 앱은 `index.html` 새로고침. 공식 best practices는 "검증 기준을 요청에 넣어라"고 한다. "고친 뒤 브라우저에서 확인하는 순서를 알려 줘" 또는 Playwright가 있으면 "자동 확인 스크립트로 검증해 줘"(이 저장소 CLAUDE.md의 검증 방법).

### 5. 되돌리기 세 가지

| 상황 | 방법 |
|---|---|
| 진행 중인데 방향이 틀림 | `Esc` 한 번: 즉시 중단, 대화는 유지 |
| 방금 한 변경을 코드·대화째 되돌림 | `Esc` 두 번 또는 `/rewind`: 체크포인트로 복원(대화만/코드만/둘 다) |
| 커밋 전 전부 버리기 | `git restore .` (5-1) |
| 커밋 후 | `git revert` (5-1) |

공식 문서 주의: 체크포인트는 Claude의 파일 편집 도구로 한 변경만 추적한다. Bash 명령으로 바뀐 것은 추적하지 않으니 **git의 대체가 아니다.** 그래서 5과정을 먼저 배웠다.

### 6. 커밋: 시키되 확인한다

`commit my changes with a descriptive message` 또는 "한국어로 커밋해 줘". 끝나면 `git log --oneline -1`과 `git show --stat HEAD`로 **무엇이 커밋됐는지** 본다(5-1 따라하기 5). `.env` 같은 게 섞였으면 즉시 되돌린다(4-2).

### 7. 퀵스타트의 단축키

- `/`를 치면 명령·스킬 목록. Tab 자동완성, ↑ 이전 입력.
- `Shift+Tab`: 권한 모드 순환(8-4).
- `/help`, `/clear`, `/exit`(또는 Ctrl+D 두 번).

## 따라하기

### 1. 한 바퀴: 문구 바꾸기 (40분)

8-1 숙제 3에서 정한 작은 변경으로.
1. `cd` 저장소 → `claude`
2. "index.html에서 재무부 잔액 카드의 '현재 잔액' 문구가 어디 있는지 찾아 줘" (알아보기)
3. "그 문구를 '지금 쓸 수 있는 돈'으로 바꿔 줘. 다른 건 건드리지 마." (변경)
4. diff 확인 → 브라우저 새로고침으로 확인
5. "한국어로 커밋해 줘" → `git log --oneline -1`

### 2. 한 바퀴: 작은 기능 (60분)

"재무부 이번 달 카드에 '지출 건수 N건'을 추가. renderMonth()에서 계산, 한국어 주석 유지." → diff에서 **범위 확인**(다른 함수가 바뀌지 않았는지) → 브라우저 확인 → 커밋. 이번에는 "브라우저에서 확인하는 순서도 알려 줘"를 요청에 넣어 검증 단계를 Claude가 제안하게 한다.

### 3. 되돌리기 연습 (40분)

"style.css의 모든 색을 보라색 계열로 바꿔 줘"처럼 **일부러 큰 변경**을 시키고, 중간에 `Esc`로 멈춘다. 그다음 `/rewind`로 코드를 되돌린다. 마지막으로 git으로도 확인(`git status`가 깨끗한지). 세 방법의 차이를 메모.

### 4. 단계별 요청 (40분)

"자산관리부에 '연금' 종류 추가"를 번호 3개로 쪼개 요청한다(3단계 숙제 1과 같은 과제). 각 단계 끝에 확인하고 다음 단계로. 한 번에 시켰을 때와 비교해 어느 쪽이 diff 읽기 쉬웠는지 적는다.

### 5. 커밋 검사 습관 (20분)

위 커밋들에 대해 `git show --stat HEAD~2..HEAD`로 어떤 파일이 바뀌었는지 보고, 의도 밖 파일이 없는지 확인. 있으면 `git revert`.

## 흔한 실수와 해결

| 실수 | 증상 | 해결 |
|---|---|---|
| 읽기 없이 바로 변경 요청 | 엉뚱한 곳 수정 | 먼저 "어디에 있는지 찾아 줘" |
| 모호한 요청 | 큰 diff, 범위 이탈 | 파일·함수·결과 명시 |
| diff 안 읽고 Yes | 필요한 줄 삭제됨 | 세 가지 체크 후 승인 |
| 검증 없이 커밋 | 깨진 앱이 이력에 | 새로고침·테스트 후 커밋 |
| Bash로 바꾼 걸 /rewind로 되돌리려 함 | 복원 안 됨 | git 사용 |
| 커밋에 .env 포함 | 비밀 유출 | 4-2 절차 |

## 확인 퀴즈

**1. 변경 요청 전에 "읽게 하는" 단계를 두는 이유는?**

<details><summary>정답과 해설</summary>
모델은 읽지 않은 파일을 모른다(6-1). 먼저 탐색하게 하면 엉뚱한 위치 수정을 막고, 내가 코드 구조를 같이 이해하게 된다(공식 best practices "explore first").
</details>

**2. diff를 읽을 때 확인하는 세 가지.**

<details><summary>정답과 해설</summary>
시킨 범위만 바뀌었나, 지워진 줄 중 필요한 게 없나, 규칙(주석·스타일)대로인가.
</details>

**3. `/rewind`가 git을 대체하지 못하는 이유.**

<details><summary>정답과 해설</summary>
체크포인트는 Claude의 파일 편집 도구로 한 변경만 추적하고, Bash 명령이나 외부 프로그램이 바꾼 것은 추적하지 않는다(공식 문서). 커밋된 이력은 git만이 안전하게 되돌린다.
</details>

**4. "가계부 좀 좋게"를 구체적 요청으로 바꿔 보라.**

<details><summary>정답과 해설</summary>
예: "재무부 이번 달 카드에 지출 건수를 추가. app.js renderMonth()에서 계산해 index.html 카드에 표시. 한국어 주석 유지. 확인 방법 포함." 파일·함수·결과·검증이 들어가면 정답.
</details>

**5. 커밋을 시킨 뒤 반드시 확인하는 명령 두 개.**

<details><summary>정답과 해설</summary>
`git log --oneline -1`(메시지)과 `git show --stat HEAD`(바뀐 파일 목록). 의도 밖 파일이 있으면 revert.
</details>

## 숙제

1. **한 바퀴 5회** — 닷새 동안 하루 한 번 작은 변경을 한 바퀴 돌려라. 각 회차의 요청문을 `docs/prompts.md`에 모은다.
2. **거부 경험** — 일부러 모호한 요청을 해서 범위를 벗어난 diff를 받아 보고, **거부**한 뒤 요청을 고쳐 다시 시켜라. 두 diff 크기를 비교.
3. **8-3 예습** — 이 저장소의 `CLAUDE.md`를 읽고, "내가 매번 말하게 되는 규칙"인데 거기 없는 것을 하나 찾아 두라.
